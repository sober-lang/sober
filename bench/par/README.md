# Sober の並列の数字

- Skynet（111 万 task）: Go より 5 倍速く、RSS は 1/17〜1/500（W1 0.209 s vs 1.079 s・W8 0.065 s vs 0.395 s・RSS W8 7.7 MB vs 132 MB・W1 0.4 vs 211 MB）。task 1 つの費用は 636 cycles（Go は 2,693）・W8 でも 1,054（Go 3,643）
- binary-trees 並列: W8 で Go の 2.5 倍速く、RSS は 0.40 倍（2.41 s vs 6.09 s・128 vs 320 MB）。並列版の W1 は逐次と 6% 差（前回 +44%）
- コンパイラ自身: `sober check` は W8 で 3.7 倍（12.7 → 3.4 s — W1 自体が 19.8 → 12.7 s と速くなり倍率は縮んだ）、`sober build` は W8 で 1.6 倍（5.6 → 3.5 s）。並列度の設定項目はない。あるのは予算だけで、判定・ELF は W1 ≡ W8 のバイト一致
- メモリの天井を細めても死なない・空回りしない: 天井が細ると並列だけが細り、逐次の速さまで滑らかに落ちる（user ≈ wall・値は全点で一致）。Go は GOMEMLIMIT が生きたヒープを下回ると GC が回り続け、wall 4〜8 倍・user 最大 10 s で、RSS も上限を守れない

## 保証つきの数字であること

ここの数字は、並列の網の下で測った。selfpar（自己 check / build の W1 ≡ W8 ≡ 天井 0）、schedfuzz（40 通りのスケジュール × W 1/2/4/8）、seqpar（逐次 ≡ 並列）、parbudget（縮退しても値が同じ）の 4 つである。
並列にしても出力のバイトは変わらない。各計測スクリプトも、走らせるたびに Sober ≡ Go ≡ 逐次の出力一致を確かめている。

## 環境と計測の規律

- AMD Ryzen AI MAX PRO 390（12 物理コア × SMT 2）・32 GB・WSL2・Go 1.26.1
- 物理コアごとに 1 論理 CPU、その最後の 8 つに固定した（taskset）。SMT の兄弟を踏むと「W8 ≈ W4」の偽の頭打ちが出る。W = `SOBER_WORKERS` / `GOMAXPROCS`
- wall は周波数と同居の負荷で ±50% 揺れる（同じ点を 5 回測って 0.23〜0.43 s）。そのため主の物差しは cycles:u / 命令数（perf — 決定的）とし、wall は交互の多数回の最小を参考に置く
- RSS は /usr/bin/time の %M。parbench / parcurve の RSS には taskset 由来の約 1.9 MB の床がある（ru_maxrss は exec をまたいで残る）。sky.sh / btpar.sh は床なしで測る
- 罠: rootless podman は cgroup のメモリ / CPU の制限を黙って無視する（WSL の環境）。コンテナで「上限つき」を測ったつもりでも効いていない。cgroup の memory.max で振る劣化曲線（Go の崖 = OOM kill）は未測
- bench と gates は同時に回さない。Go 側は各題材の素直形（公式が最初に教える形 — チューンしない）。Sober 側も素直縛り（ワーカー数を書かない）

## 1. Skynet — task の生成と合流の費用

| | W1 wall | W8 wall | cycles:u / task（W1 / W8） | 最大 RSS（W1 / W8） |
|---|---|---|---|---|
| Sober | 0.209 s | 0.065 s | 636 / 1,054 | 0.4 / 7.7 MB |
| Go | 1.079 s | 0.395 s | 2,693 / 3,643 | 211 / 132 MB |

100 万の葉に 10 分岐の木で、task は計 1,111,111。Sober は par.Map の木、Go は goroutine + チャネル（atemerev/skynet の形）。再現: `bench/par/sky.sh -n 5`（wall は 5 回の最小）。

- Go の W8 の wall は回ごとに大きく揺れる（同じ日の 3 回で 0.27〜0.40 s — GC のワーカーが 8 コアを分け合う）。W1 の比は安定していて 5.1〜5.2 倍（2026-10-10 の 2 回）。10-08 の取り直し前の値は W1 0.27 / 0.96 s・W8 0.064 / 0.27 s

- W8 の task 単価は 1,681 → 1,060 cycles（10-08 — TCB の共有の予備を束で出し入れ）。RSS の W8 3.8 → 6.2 MB（今は 7.7 MB）は束の予備の分（TCB_KEEP × 2 × ワーカー）
- spawn の固定費（W1・ラチェット照合）: loop（Scope + Spawn + Join の往復）は 780 命令、wide（1 scope に 100 万）は 873 命令・RSS 104 MB（上限 800 / 900 / 110 の内 — 2026-10-10 の sky.sh の raw）。再現: `scripts/spawnbench.sh`
- 全部を逐次へ縮退させた（天井 0）Skynet は 0.888 G 命令（task 形は 1.411 G）。task の器の費用は ≈ 470 命令 / task になる

## 2. 粒度 — どれだけ細かい task まで並列が効くか

| L（葉の足し算の回数） | Sober 葉の仕事 | Sober W8 / W1 | Go W8 / W1 | W8 wall Sober / Go |
|---|---|---|---|---|
| 0 | 0 | 2.0 倍 | 5.0 倍 | 0.116 / 0.221 s |
| 200 | 240 cycles（≈ 0.07 µs） | 4.2 倍 | 4.5 倍 | 0.077 / 0.258 |
| 500 | 570（≈ 0.16 µs） | 4.1 倍 | 4.3 倍 | 0.093 / 0.288 |
| 1,000 | 1,120（≈ 0.31 µs） | 5.6 倍 | 4.9 倍 | 0.114 / 0.328 |
| 2,000 | 2,210（≈ 0.62 µs） | 4.0 倍 | 5.0 倍 | 0.163 / 0.293 |
| 5,000 | 5,560（≈ 1.5 µs） | 7.6 倍 | 7.0 倍 | 0.263 / 0.341 |
| 20,000 | 21,980（≈ 6.1 µs） | 6.8 倍 | 9.7 倍 | 0.935 / 0.716 |

100 万の葉それぞれが L 回の足し算をしてから値を返す（bench/skynet/gran）。「葉の仕事」は Sober の W1 の cycles:u / task から L=0 の分を引き、葉 1 つあたりに直した値（µs は L=20,000 の W1 wall から逆算した 3.6 GHz で換算 — 2026-10-10 から。前回までの wall の差からの換算は揺れで点が前後した）。倍率は wall の 5 回最小の比で、±50% の揺れを含む。再現: `bench/par/sky.sh -n 5`。

- 粒度の閾値: 葉の仕事が約 0.1〜0.6 µs で W8 が 4〜5.6 倍、約 1.5 µs 以上で 7 倍前後（理想は 8）。wall の揺れで点ごとに前後する（L=2,000 の 4.0 倍など）
- 正直に: 葉が太くなると Go が速い（L = 20,000 — 10-08 は L ≥ 5,000）。原因は並列の効率ではなく、葉のループの機械語が Go の 2 倍の命令を出しているため（1 反復 8.3 命令 vs Go ≈ 4.2 — 命令 165.3 G vs 84.4 G。10-08 は 16 命令・321.6 G で、その後の -O2 水準の便で半分になった）。以下の内訳は 10-08 の分析: 本質 5・ループ不変の仮引数のスタックからの再読み 2・キャンセルの検査点 2（間引きの後 — 前は 4）・2 番地形の写しの鎖 4・回転していないループ 1。再読みの 2 種は割り当て器の区間分割の費用モデルの問題で、写しの合併・ループの回転とともに -O2 水準レーン 6.5 の席（局所の直しは 1brc / knucleotide を退行させた）。検査点は、最内で呼び出しの無いループでは戻り辺 N 回に 1 回へ間引いた（N はループ本体の IR 命令数 B から導出し、2 つの検査の間は IR 命令で 1,024 以下と約束する — 葉の命令 −12%）。ただし cycles は、同じ機械語が置かれる番地で 1.4 倍動く（ループの頭の番地 mod 64 で 3 つの類 — 8 通りの配置の分布で測った）。配置の分布の中央では、間引きの有無の差は無い。葉の税の残りは配置と、ループの形（再読み・写しの鎖 — 6.5 の席）にある。Go の L=20,000 の 11 倍は、W1 で GC が同じ 1 コアを分け合う分の超線形
- 細かい粒度（L ≤ 1,000）では Sober の W8 が Go の W8 より 1.9〜3.4 倍速い。task 1 つの費用が 1/4 なので、細かく割っても元が取れる

## 3. binary-trees — 並列のアロケーションの競合

| | W1 | W2 | W4 | W8 | 最大 RSS |
|---|---|---|---|---|---|
| Sober 逐次 | 13.5 s / 35.8 G cycles | | | | 128 MB |
| Go 逐次 | 46.4 s / 132.2 G | | | | 280 MB |
| Sober 並列 | 13.9 s / 38.1 G | 7.8 | 3.1 | 2.4 | 128 MB |
| Go 並列 | 49.1 s / 133.0 G | 15.2 | 8.2 | 6.1 | 308〜320 MB |

深さ 21（benchmarks game の値）。並列版（bench/binarytreespar）は深さごとに子を 1 つ立てる形で、Sober は par.Map、Go は goroutine。benchmarks game の並列の定番の切り方である。子は 9 つで仕事量はほぼ等しいため、W8 は 2 巡、W4 は 3 巡になる。再現: `bench/par/btpar.sh -n 3`。

- Sober は task ごとの region で確保するので、共有点がない。並列にしても RSS が 128 MB のまま増えない。Go は並列のミューテータ × GC で 271 → 335 MB に増える
- 並列版の W1 の cycles は逐次の +6%（前回 +44% — 関数の入口の軽い region.enter が基底の bump を書かない形に）。W8 は W4 より速くなった（前回は逆）

## 4. 1BRC — 逐次から並列への一本の線

| | W1 | W2 | W4 | W8 | 命令 | 最大 RSS |
|---|---|---|---|---|---|---|
| Sober 逐次（bench/1brc） | 0.46 s | | | | 6.05 G | 134 MB |
| Sober 並列（64 区間 × par.Map） | 0.53 | 0.29 | 0.18 | 0.12 | 6.52 G | 140 MB |
| Sober 並列（検査点なし — 対照） | 0.53 | 0.31 | 0.18 | 0.13 | 6.35 G | 140 MB |
| Go 逐次 | 0.56 | | | | 4.80 G | 240 MB |
| Go 並列（64 goroutine + WaitGroup） | 0.56 | 0.30 | 0.17 | 0.10 | 4.96 G | 247 MB |

1,000 万行で、wall は 5 回の中央値。再現: `scripts/parbench.sh -n 5`。

- 正直に: 1BRC 並列は W8 でまだ Go が 1.2 倍速い — ただし W4 はほぼ互角（1.06 倍）になり、W2 以下は Sober が速い（前回は W8 1.16 倍・W4 1.5 倍、その前は 1.7〜2.2 倍）。逐次は Sober が速い（UTF-8 を保証したうえで 0.46 vs 0.56 s）。並列版の W1 税は 15%（0.53 vs 0.46 — 前回 37%。-O2 水準レーン 6.5 の命令選択とループの形の分）。RSS は Sober が 0.57 倍

## 5. 劣化曲線 — 天井を細めたとき

| 天井（MiB） | Sober brcpar wall / user | Go brcpar wall / user | Sober Skynet wall / user / 縮退した task | Go Skynet wall / user |
|---|---|---|---|---|
| 0 | 0.78 / 0.71 s | 0.42 / 1.70 s | 0.12 / 0.12 s / 全部（111 万） | 1.28 / 8.07 s |
| 1 | 0.77 / 0.71 | 0.42 / 1.31 | 0.11 / 0.11 / 全部 | 1.45 / 8.97 |
| 4 | 0.28 / 0.88 | 0.33 / 1.11 | 0.06 / 0.31 / 53 万 | 1.55 / 9.84 |
| 16 | 0.27 / 0.86 | 0.32 / 1.11 | 0.06 / 0.36 / 9 万 | 1.64 / 10.32 |
| 64 | 0.30 / 0.90 | 0.33 / 1.21 | 0.08 / 0.54 / 2.5 万 | 0.63 / 3.77 |
| 256 | 0.28 / 0.89 | 0.14 / 0.78 | 0.08 / 0.54 / 0 | 0.19 / 1.08 |
| 既定 | 0.26 / 0.87 | 0.12 / 0.75 | 0.13 / 0.87 / 0 | 0.36 / 1.95 |

W8 で固定し、3 回の最小をとった。Sober は `SOBER_BUDGET_MB`（根の天井）、Go は `GOMEMLIMIT`。再現: `scripts/parcurve.sh -n 3`。

- Sober: 入場できない子はその場で親の上の逐次へ縮退するので、死なない・待たない・値は変わらない。天井 0 では Skynet の 111 万 task が全部縮退し、0.12 s・RSS 2 MB（床つき）になる。user ≈ wall で空回りもしない
- Go: 上限が生きたヒープ（≈ 200〜240 MB）を下回ると GC が回り続ける。Skynet は wall 4〜8 倍・user 8〜10 s（8 コアを GC が食う）で、RSS は上限を超える（ソフトな上限なので守れない）
- 物差しの違い: Sober の天井は task の入場だけを縛り、main の region のデータ（1BRC の 136 MB の読み込み）は数えない。そのため brcpar の RSS は天井で動かない。Go の上限はヒープ全体にかかる

## 6. fail-fast — 死んだら残りを切る

| | W1 | W4 | 命令（W1） |
|---|---|---|---|
| 切る（既定） | 0.29 s | 0.18 s | 1.71 G |
| 切らない（検査点なし — 対照） | 1.47 s | 0.41 s | 7.20 G |

par.Map の 16 の子のうち子 3 が死に、他の子は 3,000 万回の剰余のループを回す（bench/par/failfast）。wall は 5 回の最小。

切るのは死んだ子より後ろの純な子だけ（正準順）なので、子 0〜2 は走り切る。io に届く子は切らない（観測を動かさない）。

## 7. コンパイラ自身 — `-j` のないツールチェーン

| | W1 | W2 | W4 | W8 | 命令（W1） | peak RSS W1 / W8 |
|---|---|---|---|---|---|---|
| `sober check`（自分のソース一括） | 12.7 s | 7.5 | 5.1 | 3.4 | 164.1 G | 285 / 911 MB |
| `sober build`（自分の ELF） | 5.6 s | 4.7 | 3.8 | 3.5 | 58.6 G | 245 / 652 MB |

compiler/ + std を写した木で測った。W の順に交互で 2 回の最小をとり、判定 JSON と ELF が W ごとにバイト一致することも確かめている。再現: `bench/par/selfw.sh -n 2`。

- check は W8 で 3.7 倍（-O2 水準レーン 6.5 で W1 自体が 19.8 → 12.7 s と速くなり、倍率は 6.4 倍から縮んだ。命令は 156.7 → 164.1 G — レーンで足した走査の分）。Def の区間の脱糖 + 検査（P6-1 / P6-3）と層の並走（P6-2）が効いている。並列度の設定項目はなく、各段の budget: は親が事前に計算する
- build の並列: W8 で 1.6 倍（5.6 → 3.5 s）。lower の関数ごとのパスの束（B1 = optimizeSsa・B2 = 展開の後の cfgClean〜cmpDup）を群の子で回す（関数の本体を詰めて渡し・詰めて返す）・x86 の段はヒープを凍らせて写さずに子へ（table.Freeze）
- W2 が W1 より遅い形は解消した（4.7 vs 5.6）。build の直列部 = 詰め・積み直し（束あたり ≈ 1 G）・展開（irInline 1.6 G）・rtlower・x86 の切替の関数
- P6 全体の伸び（17.4 → 6.3 s 等）の大半は、並列化の前に見つけた逐次の病理（指数・2 乗）の直しによる

## 8. 決定性と保証の税

| 税 | 大きさ | どこで測ったか |
|---|---|---|
| キャンセルの検査点 | 命令: brcpar +2.6%（間引き便直後は +0.5% — 6.5 便でループの形が変わった影響とみられる・帰属は未調査）・Skynet +2.1%・粒度の葉 +17%（前は +33%） | 各題材の W1（`--rt-mutant=3` との比 — results の追補 B / C） |

どの税も spawn の回数に比例する固定費で、仕事の重い task（1BRC の 64 区間）では命令数に現れない。

## 9. 負けている軸のまとめ

- 1BRC 並列は W8 で 1.2 倍の負けが残る（W4 はほぼ互角・W2 以下は Sober が速い。並列版の W1 税は 37% → 15% に縮んだ — 残りは区間の集計と合流）
- 粒度の大きい task（葉 ≥ 3 µs）は Go が速い（間引きで葉の命令は −12% になったが、cycles の中央は動かない — 配置と葉の機械語の形・6.5 の席。内訳は 2 節）
- 自己 build の並列は W8 で 1.6 倍（倍率はまだ小さい: 直列部が残る）
- W8 の RSS: 自己 build W8 652 MB（W1 245 MB）— lower の束の子の旧い本体のゴミ・詰めの一時の写し。check W8 911 MB
- W8 = 物理 8 コアの固定で、それより上（12 コア・SMT）は測っていない。前回の表（results-20261007）の W8 は物理 4 コア × SMT だった

## 再現

```sh
scripts/spawnbench.sh                 # spawn の固定費（ラチェット照合）
bench/par/sky.sh -n 5                 # Skynet・粒度・spawn の W 軸（× Go）
bench/par/btpar.sh -n 3               # binary-trees 逐次 / 並列（× Go）
scripts/parbench.sh -n 5              # 1BRC 逐次 / 並列（× Go）+ 検査点の税
scripts/parcurve.sh -n 3              # 劣化曲線
bench/par/selfw.sh -n 2               # 自己 check / build の W 軸
```

perf が PATH に無ければ `PERF=/nix/store/…-perf-linux-…/bin/perf` で指す。fail-fast は `bin/sober build bench/par/failfast/main.sober` と、`--rt-mutant=3` を付けた stage2 の build を比べる（results の 6 節）。
