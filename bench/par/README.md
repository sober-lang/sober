# Soberの並列の数字

- Skynet（111万task）: Goより5倍速く、RSSは1/17〜1/500（W1 0.209 s vs 1.079 s・W8 0.065 s vs 0.395 s・RSS W8 7.7 MB vs 132 MB・W1 0.4 vs 211 MB）。task 1つの費用は636 cycles（Goは2,693）・W8でも1,054（Go 3,643）
- binary-trees並列: W8でGoの2.5倍速く、RSSは0.40倍（2.41 s vs 6.09 s・128 vs 320 MB）。並列版のW1は逐次と6%差（前回 +44%）
- コンパイラ自身: `sober check` はW8で3.7倍（12.7 → 3.4 s — W1自体が19.8 → 12.7 sと速くなり倍率は縮んだ）、`sober build` はW8で1.6倍（5.6 → 3.5 s）。並列度の設定項目はない。あるのは予算だけで、判定・ELFはW1 ≡ W8のバイト一致
- メモリの上限を下げても死なない・空回りしない: 上限が下がると並列だけが細り、逐次の速さまで滑らかに落ちる（user ≈ wall・値は全点で一致）。GoはGOMEMLIMITが生きたヒープを下回るとGCが回り続け、wall 4〜8倍・user最大10 sで、RSSも上限を守れない

最終更新2026-10-10（1節・2節 = commit bc73acd3の木で取り直し — `bench/par/sky.sh -n 5`・load 0.84で開始・raw = out/bench/sky-20261010-090234.tsv。3〜8節は2026-10-08のcommit 4e1bdb65 — -O2水準レーン6.5の第1・2タスクの後。4節と8節の検査点のオーバーヘッドを取り直した）。生データと測り方の詳細は [results-20261008.md](results-20261008.md)（本文 = フェーズ6時点・追補A = アタックのタスクの仕上げ・追補B = 検査点の間引きのタスク・追補C = 6.5のタスクの後の取り直し）、前回分は [results-20261007.md](results-20261007.md)。

## 保証つきの数字であること

ここの数字は、並列の検査一式の下で測った。selfpar（自己check / buildのW1 ≡ W8 ≡ 上限0）、schedfuzz（40通りのスケジュール × W 1/2/4/8）、seqpar（逐次 ≡ 並列）、parbudget（縮退しても値が同じ）の4つである。
並列にしても出力のバイトは変わらない。各計測スクリプトも、走らせるたびにSober ≡ Go ≡ 逐次の出力一致を確認している。

## 環境と計測の規律

- AMD Ryzen AI MAX PRO 390（12物理コア × SMT 2）・32 GB・WSL2・Go 1.26.1
- 物理コアごとに1論理CPU、その最後の8つに固定した（taskset）。SMTの兄弟を踏むと「W8 ≈ W4」の偽の頭打ちが出る。W = `SOBER_WORKERS` / `GOMAXPROCS`
- wallは周波数と同居の負荷で ±50%揺れる（同じ点を5回測って0.23〜0.43 s）。そのため主の指標はcycles:u / 命令数（perf — 決定的）とし、wallは交互の多数回の最小を参考に置く
- RSSは /usr/bin/timeの %M。parbench / parcurveのRSSにはtaskset由来の約1.9 MBの下限がある（ru_maxrssはexecをまたいで残る）。sky.sh / btpar.shは下限なしで測る
- 罠: rootless podmanはcgroupのメモリ / CPUの制限を黙って無視する（WSLの環境）。コンテナで「上限つき」を測ったつもりでも効いていない。cgroupのmemory.maxで振る劣化曲線（Goの崖 = OOM kill）は未測
- benchとgatesは同時に回さない。Go側は各題材の素直形（公式が最初に教える形 — チューンしない）。Sober側も素直縛り（ワーカー数を書かない）

## 1. Skynet — taskの生成と合流の費用

| | W1 wall | W8 wall | cycles:u / task（W1 / W8） | 最大RSS（W1 / W8） |
|---|---|---|---|---|
| Sober | 0.209 s | 0.065 s | 636 / 1,054 | 0.4 / 7.7 MB |
| Go | 1.079 s | 0.395 s | 2,693 / 3,643 | 211 / 132 MB |

100万の葉に10分岐の木で、taskは計1,111,111。Soberはtask.Mapの木、Goはgoroutine + チャネル（atemerev/skynetの形）。再現: `bench/par/sky.sh -n 5`（wallは5回の最小）。

- GoのW8のwallは回ごとに大きく揺れる（同じ日の3回で0.27〜0.40 s — GCのワーカーが8コアを分け合う）。W1の比は安定していて5.1〜5.2倍（2026-10-10の2回）。10-08の取り直し前の値はW1 0.27 / 0.96 s・W8 0.064 / 0.27 s

- W8のtask単価は1,681 → 1,060 cycles（10-08 — TCBの共有の予備をまとめて出し入れ）。RSSのW8 3.8 → 6.2 MB（今は7.7 MB）はまとめて持つ予備の分（TCB_KEEP × 2 × ワーカー）
- spawnの固定費（W1・ラチェット照合）: loop（Scope + Spawn + Joinの往復）は780命令、wide（1 scopeに100万）は873命令・RSS 104 MB（上限800 / 900 / 110の内 — 2026-10-10のsky.shのraw）。再現: `scripts/spawnbench.sh`
- 全部を逐次へ縮退させた（上限0）Skynetは0.888 G命令（task形は1.411 G）。taskの器の費用は ≈ 470命令 / taskになる

## 2. 粒度 — どれだけ細かいtaskまで並列が効くか

| L（葉の足し算の回数） | Sober葉の仕事 | Sober W8 / W1 | Go W8 / W1 | W8 wall Sober / Go |
|---|---|---|---|---|
| 0 | 0 | 2.0倍 | 5.0倍 | 0.116 / 0.221 s |
| 200 | 240 cycles（≈ 0.07 µs） | 4.2倍 | 4.5倍 | 0.077 / 0.258 |
| 500 | 570（≈ 0.16 µs） | 4.1倍 | 4.3倍 | 0.093 / 0.288 |
| 1,000 | 1,120（≈ 0.31 µs） | 5.6倍 | 4.9倍 | 0.114 / 0.328 |
| 2,000 | 2,210（≈ 0.62 µs） | 4.0倍 | 5.0倍 | 0.163 / 0.293 |
| 5,000 | 5,560（≈ 1.5 µs） | 7.6倍 | 7.0倍 | 0.263 / 0.341 |
| 20,000 | 21,980（≈ 6.1 µs） | 6.8倍 | 9.7倍 | 0.935 / 0.716 |

100万の葉それぞれがL回の足し算をしてから値を返す（bench/skynet/gran）。「葉の仕事」はSoberのW1のcycles:u / taskからL=0の分を引き、葉1つあたりに直した値（µsはL=20,000のW1 wallから逆算した3.6 GHzで換算 — 2026-10-10から。前回までのwallの差からの換算は揺れで点が前後した）。倍率はwallの5回最小の比で、±50%の揺れを含む。再現: `bench/par/sky.sh -n 5`。

- 粒度の閾値: 葉の仕事が約0.1〜0.6 µsでW8が4〜5.6倍、約1.5 µs以上で7倍前後（理想は8）。wallの揺れで点ごとに前後する（L=2,000の4.0倍など）
- 正直に: 葉が太くなるとGoが速い（L = 20,000 — 10-08はL ≥ 5,000）。原因は並列の効率ではなく、葉のループの機械語がGoの2倍の命令を出しているため（1反復8.3命令vs Go ≈ 4.2 — 命令165.3 G vs 84.4 G。10-08は16命令・321.6 Gで、その後の -O2水準のタスクで半分になった）。以下の内訳は10-08の分析: 本質5・ループ不変の仮引数のスタックからの再読み込み2・キャンセルの検査点2（間引きの後 — 前は4）・2番地形のコピーのチェーン4・回転していないループ1。再読み込みの2種類は割り当て器の区間分割の費用モデルの問題で、コピーの合併・ループの回転とともに -O2水準レーン6.5の対象（局所の直しは1brc / knucleotideを退行させた）。検査点は、最内で呼び出しの無いループでは戻り辺N回に1回へ間引いた（Nはループ本体のIR命令数Bから導出し、2つの検査の間はIR命令で1,024以下と約束する — 葉の命令 −12%）。ただしcyclesは、同じ機械語が置かれる番地で1.4倍動く（ループの頭の番地mod 64で3つの類 — 8通りの配置の分布で測った）。配置の分布の中央では、間引きの有無の差は無い。葉のオーバーヘッドの残りは配置と、ループの形（再読み込み・コピーのチェーン — 6.5の対象）にある。GoのL=20,000の11倍は、W1でGCが同じ1コアを分け合う分の超線形
- 細かい粒度（L ≤ 1,000）ではSoberのW8がGoのW8より1.9〜3.4倍速い。task 1つの費用が1/4なので、細かく分けても元が取れる

## 3. binary-trees — 並列のアロケーションの競合

| | W1 | W2 | W4 | W8 | 最大RSS |
|---|---|---|---|---|---|
| Sober逐次 | 13.5 s / 35.8 G cycles | | | | 128 MB |
| Go逐次 | 46.4 s / 132.2 G | | | | 280 MB |
| Sober並列 | 13.9 s / 38.1 G | 7.8 | 3.1 | 2.4 | 128 MB |
| Go並列 | 49.1 s / 133.0 G | 15.2 | 8.2 | 6.1 | 308〜320 MB |

深さ21（benchmarks gameの値）。並列版（bench/binarytreespar）は深さごとに子を1つ立てる形で、Soberはtask.Map、Goはgoroutine。benchmarks gameの並列の定番の切り方である。子は9つで仕事量はほぼ等しいため、W8は2巡、W4は3巡になる。再現: `bench/par/btpar.sh -n 3`。

- Soberはtaskごとのregionで確保するので、共有点がない。並列にしてもRSSが128 MBのまま増えない。Goは並列のミューテータ × GCで271 → 335 MBに増える
- 並列版のW1のcyclesは逐次の +6%（前回 +44% — 関数の入口の軽いregion.enterが基底のbumpを書かない形に）。W8はW4より速くなった（前回は逆）

## 4. 1BRC — 逐次から並列への一本の線

| | W1 | W2 | W4 | W8 | 命令 | 最大RSS |
|---|---|---|---|---|---|---|
| Sober逐次（bench/1brc） | 0.46 s | | | | 6.05 G | 134 MB |
| Sober並列（64区間 × task.Map） | 0.53 | 0.29 | 0.18 | 0.12 | 6.52 G | 140 MB |
| Sober並列（検査点なし — 対照） | 0.53 | 0.31 | 0.18 | 0.13 | 6.35 G | 140 MB |
| Go逐次 | 0.56 | | | | 4.80 G | 240 MB |
| Go並列（64 goroutine + WaitGroup） | 0.56 | 0.30 | 0.17 | 0.10 | 4.96 G | 247 MB |

1,000万行で、wallは5回の中央値。再現: `scripts/parbench.sh -n 5`。

- 正直に: 1BRC並列はW8でまだGoが1.2倍速い — ただしW4はほぼ互角（1.06倍）になり、W2以下はSoberが速い（前回はW8 1.16倍・W4 1.5倍、その前は1.7〜2.2倍）。逐次はSoberが速い（UTF-8を保証したうえで0.46 vs 0.56 s）。並列版のW1のオーバーヘッドは15%（0.53 vs 0.46 — 前回37%。-O2水準レーン6.5の命令選択とループの形の分）。RSSはSoberが0.57倍

## 5. 劣化曲線 — 上限を下げたとき

| 上限（MiB） | Sober brcpar wall / user | Go brcpar wall / user | Sober Skynet wall / user / 縮退したtask | Go Skynet wall / user |
|---|---|---|---|---|
| 0 | 0.78 / 0.71 s | 0.42 / 1.70 s | 0.12 / 0.12 s / 全部（111万） | 1.28 / 8.07 s |
| 1 | 0.77 / 0.71 | 0.42 / 1.31 | 0.11 / 0.11 / 全部 | 1.45 / 8.97 |
| 4 | 0.28 / 0.88 | 0.33 / 1.11 | 0.06 / 0.31 / 53万 | 1.55 / 9.84 |
| 16 | 0.27 / 0.86 | 0.32 / 1.11 | 0.06 / 0.36 / 9万 | 1.64 / 10.32 |
| 64 | 0.30 / 0.90 | 0.33 / 1.21 | 0.08 / 0.54 / 2.5万 | 0.63 / 3.77 |
| 256 | 0.28 / 0.89 | 0.14 / 0.78 | 0.08 / 0.54 / 0 | 0.19 / 1.08 |
| 既定 | 0.26 / 0.87 | 0.12 / 0.75 | 0.13 / 0.87 / 0 | 0.36 / 1.95 |

W8で固定し、3回の最小をとった。Soberは `SOBER_BUDGET_MB`（根の上限）、Goは `GOMEMLIMIT`。再現: `scripts/parcurve.sh -n 3`。

- Sober: 入場できない子はその場で親の上の逐次へ縮退するので、死なない・待たない・値は変わらない。上限0ではSkynetの111万taskが全部縮退し、0.12 s・RSS 2 MB（下限を含む）になる。user ≈ wallで空回りもしない
- Go: 上限が生きたヒープ（≈ 200〜240 MB）を下回るとGCが回り続ける。Skynetはwall 4〜8倍・user 8〜10 s（8コアをGCが食う）で、RSSは上限を超える（ソフトな上限なので守れない）
- 基準の違い: Soberの上限はtaskの入場だけを縛り、mainのregionのデータ（1BRCの136 MBの読み込み）は数えない。そのためbrcparのRSSは上限で動かない。Goの上限はヒープ全体にかかる

## 6. fail-fast — 死んだら残りを切る

| | W1 | W4 | 命令（W1） |
|---|---|---|---|
| 切る（既定） | 0.29 s | 0.18 s | 1.71 G |
| 切らない（検査点なし — 対照） | 1.47 s | 0.41 s | 7.20 G |

task.Mapの16の子のうち子3が死に、他の子は3,000万回の剰余のループを回す（bench/par/failfast）。wallは5回の最小。

切るのは死んだ子より後ろの純な子だけ（正準順）なので、子0〜2は走り切る。ioに届く子は切らない（観測を動かさない）。

## 7. コンパイラ自身 — `-j` のないツールチェーン

| | W1 | W2 | W4 | W8 | 命令（W1） | peak RSS W1 / W8 |
|---|---|---|---|---|---|---|
| `sober check`（自分のソース一括） | 12.7 s | 7.5 | 5.1 | 3.4 | 164.1 G | 285 / 911 MB |
| `sober build`（自分のELF） | 5.6 s | 4.7 | 3.8 | 3.5 | 58.6 G | 245 / 652 MB |

compiler/ + stdをコピーした木で測った。Wの順に交互で2回の最小をとり、判定JSONとELFがWごとにバイト一致することも確認している。再現: `bench/par/selfw.sh -n 2`。

- checkはW8で3.7倍（-O2水準レーン6.5でW1自体が19.8 → 12.7 sと速くなり、倍率は6.4倍から縮んだ。命令は156.7 → 164.1 G — レーンで足した走査の分）。Defの区間の脱糖 + 検査（P6-1 / P6-3）と層の並走（P6-2）が効いている。並列度の設定項目はなく、各段階のbudget: は親が事前に計算する
- buildの並列: W8で1.6倍（5.6 → 3.5 s）。lowerの関数ごとのパスのバッチ（B1 = optimizeSsa・B2 = 展開の後のcfgClean〜cmpDup）をグループの子で回す（関数の本体を詰めて渡し・詰めて返す）・x86の段階はヒープを凍らせてコピーせずに子へ（table.Freeze）
- W2がW1より遅い形は解消した（4.7 vs 5.6）。buildの直列部 = 詰め・積み直し（バッチあたり ≈ 1 G）・展開（irInline 1.6 G）・rtlower・x86の切替の関数
- P6全体の伸び（17.4 → 6.3 s等）の大半は、並列化の前に見つけた逐次の病理（指数・2乗）の直しによる

## 8. 決定性と保証のオーバーヘッド

| オーバーヘッド | 大きさ | どこで測ったか |

## 9. 負けている軸のまとめ

- 1BRC並列はW8で1.2倍の負けが残る（W4はほぼ互角・W2以下はSoberが速い。並列版のW1のオーバーヘッドは37% → 15%に縮んだ — 残りは区間の集計と合流）
- 粒度の大きいtask（葉 ≥ 3 µs）はGoが速い（間引きで葉の命令は −12%になったが、cyclesの中央は動かない — 配置と葉の機械語の形・6.5の対象。内訳は2節）
- 自己buildの並列はW8で1.6倍（倍率はまだ小さい: 直列部が残る）
- W8のRSS: 自己build W8 652 MB（W1 245 MB）— lowerのバッチの子の旧い本体のゴミ・詰めの一時のコピー。check W8 911 MB
- W8 = 物理8コアの固定で、それより上（12コア・SMT）は測っていない。前回の表（results-20261007）のW8は物理4コア × SMTだった

## 再現

```sh
scripts/spawnbench.sh                 # spawn の固定費（ラチェット照合）
bench/par/sky.sh -n 5                 # Skynet・粒度・spawn の W 軸（× Go）
bench/par/btpar.sh -n 3               # binary-trees 逐次 / 並列（× Go）
scripts/parbench.sh -n 5              # 1BRC 逐次 / 並列（× Go）+ 検査点の税
scripts/parcurve.sh -n 3              # 劣化曲線
bench/par/selfw.sh -n 2               # 自己 check / build の W 軸
```

perfがPATHに無ければ `PERF=/nix/store/…-perf-linux-…/bin/perf` で指す。fail-fastは `bin/sober build bench/par/failfast/main.sober` と、`--rt-mutant=3` を付けたstage2のbuildを比べる（resultsの6節）。
