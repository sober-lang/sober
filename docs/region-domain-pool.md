# Sober: Region / Place / Pool仕様（文書名は旧称Region / Domain / Poolのまま）

docs/language.mdの11節（現在の見出しは「ビルトインのコルーチン + structured concurrency」）を、Place / Poolの層と接合して詰めたもの。

位置づけ: 2026-09-17に設計メモとして書き始め、その後の決定と実装で一部の節が古くなっている。1節（region）・1b節（defer）・1c節（freeze）・4c節・4d節（lease）は決定済みで実装済み。2節（Handle）と4節（Pool）は2026-09-27にstd/poolの最小形として実装されたが、この文書の元の記述（ピン済み参照を返すacquire）とは形が変わっており、該当箇所に注記を加えた。最新の決定はdocs/language.md 30節を正とする。3節（Place）と4e節の段階2以降（shmチャネル・DMA・GPU）はまだ実装されていない構想で、std/にはまだ存在しない。未決節の各項目は本文の記載どおりいまも未決。

用語の注記（改名の決定2026-11-09）: この文書のPlace（region + executor + Policy。走る場所）は旧称Domain。小文字のdomainはlanguage.md 11節の「直列化された共有状態」を指す（2026-11-08の決定で語を譲った）。棄てた案: Executorへ改名（Placeのフィールド `exec Executor` はspawnの行き先で、これと衝突し、既存のExecutorの意味が動く）

原則: ブロック = リソース境界 / 所有は上位スコープ・利用は下位スコープ / 直接のallocは存在しない / 参照は木であってグラフでない / 参照カウントはPool内部に隠す。

## 層の割り当て

| 概念 | 住む層 | 理由 |
|---|---|---|
| region（スコープごとのアリーナ、escape規則） | コンパイラ（健全必須） | メモリ安全はanalyzerに振れない |
| 世代付きハンドル `Handle[T]` と `get(h) T?` | ランタイム + 型（`T?`） | 越境参照をpanicでなく分岐にする |
| 並列スコープに渡せるのは不変値かチャネルのみ | コンパイラ | data race freedom |
| freeze（mut → 不変の一方向遷移） | 型規則はコンパイラ（薄）、タグ検査はランタイム、use-after-freeze検出と検査除去はanalyzer | 借用検査なしで「mutで構築 → 不変として共有」を可能にする |
| Place（region + executor + Policy。未実装の構想。3節） | ライブラリstruct | 言語仕様にGPU / IOの語を入れない |
| Pool（型付きリソースプール。std/poolの最小形は実装済み。4節） | ライブラリ | 最小形はAcquire / Release / Get / Setのみ。Poolable辞書でbackendを差す形は未実装の構想 |
| lease（poolを外の書き手に貸す — 4c節） | ライブラリ（ioのpool）+ ランタイム（世代の回転・fence） | 貸出中のpoolへの書き・resetはAPIが無いので書けない。言語にleaseの語を入れない |
| ワーカー局所のlease（作業域をtaskをまたいで使い回す — 4d節） | ライブラリ（`task.Local` / `task.Lease`・`pool.Scratch`）+ ランタイム（ワーカーの格納場所・使用中のフラグ・世代の進め）+ loader（ウィンドウの書き換え・格納場所のTの形の検査） | 意味は「ウィンドウのたびに新しいゼロ値」— 割り当ての最適化で、言語の意味（Leanのコア）に現れない |
| block / alloc（ルート領域へのescape）エフェクト | analyzer | メモ12節のエフェクト追跡そのまま |

プリミティブはregionだけ（Placeをプリミティブにする案は採らない）。Placeは「regionを持ち、spawn先を決め、Poolを生む」ただのstruct。CPU / GPU / IOの対称性（design-dev.mdの表）はライブラリ設計として維持する。

## 1. region（言語側）

> 並列の表層は2026-10-05にlanguage.md 11節「表層」へ移った（`parallel scope { spawn }` → `task.Run` / `task.Spawn`・spawnに渡せるのは不変値とチャネルの端点）。この文書の `parallel scope` の綴りは旧表層のまま読む。

- 全ブロックがregionを持つ。ブロック終了で一括解放。if / for / switchの分岐もブロックなので同じ
- 割り当てのデフォルトは囲みスコープのregion。構文なし。`x := T{...}` は現在のregionに置かれる
- escape規則: 親regionの値が子regionの値を参照してはならない（親 → 子参照禁止）。子 → 親は常に可
- region境界を越える書き込みは宛先regionへのコピー（決定2026-09-17）。ブロックの値を親に返す、子ブロックから親のmut変数に代入する、Place間の `receive`（3節）は全部この1規則。コンパイラは宛先regionを字句的に知るので解析は要らず、親 → 子参照は構成的に作れない。移動は最適化
  - 割り当ては所有者に従う: `append(buf, x)` は現在のregionではなく `buf` のregionに割り当てる（参照型がregionを持つ、formal.mdの `Ref ρ T`）。親で宣言した `buf` を子で伸ばしてもescapeにならない
  - コピーを消す最適化: ブロック末尾式の割り当ては親regionに直接置く（`{ setup; build(tmp) }` がゼロコスト）。`y := make(); fill(y); y` のように単一の割り当て点が結果にしか流れないなら、その割り当てを親regionに向ける。ブロック内の局所データフローで判定、call graph不要
  - 消せなかったコピーはanalyzerがlintで示し、fixが宣言を親ブロックへ持ち上げる。関数のエフェクトとしての `escape` はルートregion（グローバル）への書き込みだけ（language.md 12節）。ブロック境界のコピーはエフェクトではなくlint
  - 同一性を持つ型（チャネル・Place・Pool）はコピーできないので子から親へ返せない（コンパイルエラー）。親で作って子へ渡す方向のみ。structured concurrencyの形と一致
  - 棄てた案: Zig式に割り当て先を明示（構文が増えGoの見た目を壊す）、Tofte–Talpinのregion多相（formal.mdで借りないと決めた）、サイズ閾値で自動/明示を切り替える折衷（閾値の規則が要る）
- コルーチンのスタックもregionから取る（メモ11節1項）。コルーチンの寿命 = スコープの寿命
- 並列スコープ `parallel scope { ... }` に渡せるのは不変値かチャネルだけ。mutな値は単一スコープが所有し単一書き手
- **配置先 — parkで死んだ深度を返す**（実装2026-10-23・report-1060〜1062。意味は不変で、変わるのは配置先だけ）:
  - taskが待ちに入って別のtaskへ切り替わるとき（rt.task_wait・協調形のspawnの切替）、そのtaskの今の深度より深いregionのスロットを手放す。今の深度より深いregionは抜けた時点で死んでいる（上の規則）ので、配置先を手放すだけで中身はコピーしない。
  - 手放したスロットは、ワーカーの予備（スロットの表に置いたままの範囲 — 続かない分はプールの深度ごとの列）に入る。同じワーカーで次にその深度へ入るtaskが、さっき手放されたスロットをそのまま使う。
  - 接続のtaskのRSSが「待ちを跨いで生きる深度」の分だけになり（4096接続で115 → 73 MB・json-compで225 → 91 MB）、リクエストごとに触るページが温かい器に寄る（cycles −14〜18%）。
  - main（予約のアリーナ）と既定より大きいスロットのtaskは手放さない。予備をプールへ出すときはmadviseしない。
  - 前提: 待ちに入りうる呼び出しの間、今の深度のレジスタは最内の生きたregionの深度でなければならない。浅い深度へ確保させたいrtの関数（宛先構築のread_file / read_dir）は深度を実引数で受け、レジスタを書き換えない（2026-10-23の直し・report-1086 — 旧形は読む間だけレジスタを宛先へ下げていて、読み込みの待ちが (宛先, 今の深度] の生きたregionを手放し、戻ったtaskが深度を飛ばして入り直して他のtaskのスロットを自前にした。W ≥ 2でioを読むtaskのある利用者のプログラムに影響）。テスト = scripts/nextgen.sh（今のrtを積んだコンパイラでW ≥ 2の自己build。検査つきのrtは深度を飛ばした入り直しをexit 81で止める）。
  - 既定より小さいスロットのtask（std/netのServeの接続 — `region:`・language.md 11節）は、既定のスロット1本を分割した小さいスロットを深度ごとに1本使い、parkでは既定のtaskと同じに予備へ返す。予備のフィールドには大きさのタグがあり、予備を採るのは同じ大きさのtaskだけ（違う大きさのtaskが深く入るときは予備を大きさに合った格納場所へ出してから）。小さいスロットはワーカーの小さいスロットの深度ごとの列（溢れは共有の列 — 既定のスロットの深度ごとのプールと同じ形）に戻り、既定のプールへは返さない。列はスロットの外にあり、返したスロットのページには書かない（中にリストのワードを書くと、列を通ったスロットの先頭のページが全部常駐する — report-1079）。
  - 小さいスロットのtaskの最初の4深度は、taskのチャンク（task 1本ぶんのメモリのまとまり）の末尾のページ（深度ごとに1ページ）を予約ページ（regionの先頭ページ用にあらかじめ確保してあるページ）として使い、溢れたら小さいスロットへ移る（予約ページの中身はその場に残る — language.md 11節「接続のtaskの小さいスロット」）。表の基底は「予約ページの終わり − スロットの大きさ」（偽の基底）なので、確保の上限の検査は無変更で予約ページの終わりを指す。基底をregionの先頭として読む箇所（深度の入りのbump・madvise・使用量・返し）だけが予約ページを見分けて直す。溢れて移した深度は普通のスロット（bumpを予約ページの使った分だけ進めて始める — 上限の和はregion: ちょうど）で、以後は予約ページを見ない。予約ページは予備にもプールにも出さない。parkで手放す深度の予約ページはページを返し、そのtaskでは以後予約ページにしない。
  - 機械スタックも同じ規律で配置先を分ける（2026-11-12 — language.md 11節「接続のtaskのスタック」）: チャンクのスタックの領域（エリア — 接続のtaskの深いフレームを実行する、ワーカーごとのスタック領域）はチャンクごと + ワーカーごとに1枚で、持ち主の間を交換で動く（数は保存）。接続のtaskは本体の枠をチャンクのページ0に置き、本体より下はワーカーのエリアの上で走って、ディープスリープするときにエリアごと持っていく — 走っている間に触るスタックのページがワーカーの温かいエリアに寄る。受けの待ちは本体より下の枠が死んでいるのでエリアを持たずにシャロースリープする（ディープスリープの後なら所有エリア〔taskが保持しているエリア〕とワーカーのエリアを交換してから — スリープしているkeep-aliveの接続のスタックはページ0だけ）。リクエストごとのregionの予約ページもエリアに付ける（エリアの予約ページ — チャンクの頭の最後の4ページ）: 予約ページの中身はエリアと一緒に動き、ディープスリープするtaskはエリアごと持ってスリープする。受けの待ちでは予約ページの深度を空のまま持ってスリープし、ウェイクアップした点でワーカーのエリアが替わっていれば基底を付け替える — スリープしているkeep-aliveの接続の常駐はページ0だけ（4 KB）。regionの予約ページと違い、エリアはtaskの寿命と無関係に持ち主が変わる（チャンクがプールへ戻るときは所有エリアごと戻り、所有エリアの違うチャンクはフラグつきのspawnだけが引く）。
  - 棄てた案:
    - 止まらない部分木の間だけownを下げる（L1-0bの試作）: 呼び出しごとに表の退避と復元が要り、止まる部分木に効かない。
    - parkのたびに1本ずつプールへ返す: 深度ごとの出し入れで命令 +600/リクエスト。
- **配置先 — 借りのクロージャがmutで捕捉する大きい束縛のセルはregionに**（実装2026-10-23・report-1063 / 1065 / 1068。意味は不変で、変わるのは配置先だけ）:
  - `mut z := T{…}` の集合値（64ワード以上）を借りのクロージャがmutで捕捉すると、番地が逃げるのでセルはフレームの専用スロットになり、その枝を通らない呼び出しでも熱いフレームが深くなる（taskのスタックのページが1枚増える — 8-5のcompress + streamで +4 KB/接続）。このセルを今の深度のregionに置く。
  - 今の深度を使うのは、それが束縛の繰り返しを区切るregionのときだけ: 反復のregion・式ブロック・taskのscopeの中か、region透過でない関数の本体（入口の自前のregion）。region透過の関数の本体の直下は呼び手の深度に積もりうるので、スロットのまま。
  - セルは束縛のスコープの間だけ使われ（mut仮引数と借りのクロージャは番地を保持しない）、置いたregionはスコープ以上に生きる。リテラルの全ワードを書くので、regionのページの前の持ち主の値は読めない。
  - 棄てた案:
    - 大きさだけで選ぶ（大きいmutの集合値の束縛すべて）: 自己buildには効かず、tlsのhandshakeの状態（32〜127ワード — 捕捉されない）まで出してjson-tlsのcycles +3%（report-1065）。
    - 冷たい枝の中でだけフレームを延ばす（shrink-wrapping）: x86のフレームの前提（rbpの固定変位）を崩す大きさで、効きは同じクラスの部分集合。
    - 束縛のブロックを1階層のregionで包む（今の深度が使えない形のフォールバック先）: 今は実需が無い — フォールバックした束縛はスロットのままで退行しない。

## 1b. defer（ブロックスコープ）

- `defer` を持つ。Goと違いブロックスコープ（Zig意味論）。全ブロックがリソース境界なのでdeferもブロック終了で走るのが一貫する。Goのforループ内deferが溜まる罠が消える
- 式ブロックでは値の評価後・親に値を渡す前に走る
- Placeの停止も同じ形: `d := newPlace(policy); defer d |> close()`。closeの中でdrain → executor停止 → region解放の順序をライブラリが持つ
- 暗黙に残るのは `parallel scope` 終了時のjoinだけ。structured concurrencyの定義そのものなので例外として明記する

## 1c. freeze（mut → 不変の一方向遷移。決定2026-09-18）

動機: formal.mdの段階3bの形式化で「共有できるのは深く不変（mutFree）な値のみで、構築後に不変化する術がない」ことが最大の性能アッパーと判明した。mutで構築したデータを並列スコープへ渡すには共有直前のO(n) コピーが強制される。freezeはこの一方通行を足す。

- 型規則は薄く: freezeはmut参照を消費して不変参照を返す（`ref mut T → ref T`）。premiseは「格納型がmut参照を含まない（mutFree）」だけ。深い不変性は規則に入れず、bottom-up凍結パターンで出す — 子を先に凍結すれば親セルの格納型は不変参照だけになりpremiseを自然に満たす。region移管も借用追跡も要らない
- 健全性の底は静的な一意性（改定2026-10-10 — language.md 17節・F-al）: 一意でないfreeze（別名の残る束縛・mutの仮引数）と、freezeの後の同じパスへの書きを検査器が拒否し、mutの仮引数は呼び出しを越えて逃げない（26節U3）。実行時タグは模型（formal.mdの機械）にだけ残る観測点で、実装は持たない
- 暗黙のfreeze（2026-10-11 — language.md 17節）: 期待型がimmの位置に置いたmutのパスは `freeze(道)` と同じ。一意性の規則は暗黙の点にも同じく掛かる
- 旧記述（〜2026-10-10）: 「健全性の底は実行時タグ（凍結済みへの書きはpanic）・analyzerはuse-after-freezeの検出とタグ検査の除去」。実行時タグは実装されず、freezeは型の付け替えだけだった — 古い別名から凍結済みを書き換えられた（F-al）。タグを実装する案（D1）とコピーのfreeze（D2）は棄てた（理由はlanguage.md 17節）
- freezeは不可逆（unfreezeなし）。タグの一方向性が形式化側の可換性・共有プレフィクス安定性を守る源泉
- 棄てた案: region移管（Verona式。機構が大きくformalの絶対レベル前提に触る）、借用追跡（Soberが構成的に排除した困難の持ち込み）、deep freezeを型規則に入れる（規則が太る。bottom-upパターンで足りる）
- 実地（2026-10-07夜間・決定2026-10-08確定）: 入れ子の可変コンテナ（`mut []mut []T` — stdのTableのchunkの列）は、中身のある要素を1本ずつ取り出してフィールドを差し替えてからfreezeしてimmの外側の列に積めば、データをコピーせずに凍る（外側の列ごとの `freeze` は格納型にmutが残るのでpremiseで弾かれる — 正しい）。std/table.Freezeがこの形（取り出し形 — 元の表は空に戻る）

## 2. Handle（region越境の唯一の手段）

- `Handle` は「Poolのスロットindex + 世代」の値型（`struct{idx int; gen int}`）。ポインタではないのでregion規則に触れない（どのregionにコピーしてもよい）
- 解決は `Get(mut p, h)` で `T?` を値のコピーとして返す（決定2026-09-27・language.md 30節）。スロットが返却・再利用済みなら世代不一致で `nil`。書き換えは `Set(mut p, h, v) bool` に新しい値を渡して行う。役割はスコープを越えて保存したHandleの解決に限る（LRUリスト、索引、親所有のレジストリ）。getと使用の間に他のコルーチンがreleaseしないことは、必要なら `@noblock` 区間（language.md 11節）で主張する
  - 旧案（〜2026-09-27）: `get` が `*T?`（スロットの中身へのピン済み参照）を返す案だった。Soberにはポインタ・参照の型が無い（docs/spec/02-types.ja.md・docs/value-oriented.ja.md）ため採られず、std/poolの実装はGet / Setの値コピーに決まった（language.md 30節）。4節・4b節のうちピン済み参照を前提にした記述は、実装されていない構想として読む
- 世代チェックはランタイム層。コンパイラは `T?` のflow typingで分岐を強制するだけ
- 組み込みかstdか: stdのstructで書けるならstd。言語が知る必要があるのは「値型であること」だけで、それはstructなら自明。→ std（言語組み込みにしない）。Zig製のゲームのHandle値型 + 世代チェックがそのまま前例

## 3. Place（未実装の構想）

いまのstd/に `Place` 型は無い（src/compiler/desugar/split.soberの `type Place struct` はコンパイラ内部の脱糖用の同名structで、この節とは無関係）。design-dev.mdのPhase 3以降でPool（4節）の次に実装する想定のまま、着手していない。以下は当初案。

```
type Place struct {
    region  Region          // 言語側のハンドル。Place を作ったスコープの region
    policy  Policy          // 定数辞書
    exec    Executor        // spawn の行き先（スレッドプール / コマンドキュー / イベントループ）
}
type Policy struct {
    threads     int
    scheduling  Scheduling
    memory      Memory      // host / host_visible / device_local
    transfer    Transfer    // direct / staged
    completion  Completion  // immediate / fenced
}
```

- comptimeで評価する形にしない — Policyは 定数struct。分岐は最適化器の定数伝播で消える（メモ3節「辞書が定数なら単相化と同じ」と同じ賭け）
- Placeのスコープ終了 = executor停止 + `drain` + region解放。順序はライブラリが持つ
- Place間転送 `receive(dst, src, v)` は (src.policy.memory, dst.policy.memory) の辞書ルックアップ。ユーザーコードは同じ、方式は表で決まる。コピーか移動か: region規則上「別regionへの値」は常にコピー。移動は最適化
  - Place越境のコピー除去（決定2026-09-17）: 言語にムーブは無い。割り当て点を宛先に向ける。arenaモデルでは1オブジェクトの所有権を別regionへ移せない（メモリは元のarenaに残る）ので、区分はコピーか「最初から宛先に置く」の2つだけ。Rust的なムーブは後者の特殊ケース。`receive(gpu, cpu, buf)` のコピーを消すなら `buf` を最初から宛先Placeのstaging（host_visible）に置く（Vulkanの「マップ済みstagingに直接書く」定石）
  - 判定は ブロック内の局所データフロー（1節の再標的と同じ）: `buf` の割り当て点がこのブロックにあり、`receive` にしか流れない（他へ代入されず、receive後に使われない）なら宛先に向けられる。割り当て点が局所なら参照の出所が全部見えるのでエイリアスも閾内。引数やフィールド経由の値は出所不明で対象外（unknownにdegrade。`@unique` のような「他に参照が無い」注釈は借用検査の入口になるので入れない）
  - ブロック境界と違い、最適化器が黙って再標的するのではなくanalyzerがlintで示しfixがソースを書き換える: `buf := make([]Vertex, n)` → `h, buf := gpu.staging |> acquire(n)?; defer gpu.staging |> release(h)`。Place越境のコピーは性能を決めるので、消えたかどうかがソースに見えるべき。ブロック境界の小さなコピーは見せず最適化器、Place境界はfixで明示、の線引き（「見えるものは人が書く、見えないものは最適化器」）
  - stagingは宛先PlaceのPoolから取る（下記の未決を閉じる）。Placeのregionに直接置くと寿命がPlaceと同じになりstagingが溜まる。Pool管理ならfenced Placeの「fence完了後に再利用」の既存規則に乗る。`receive` は同一メモリなら所有の引き渡し（Poolの返却先が変わるだけ）でコピーしない

## 4. Pool（決定2026-09-27・std/poolの最小形・language.md 30節）

実装済みの形: std/poolはregion-domain-pool.md 2・4節の内容をPhase 3を待たずに前倒しで実装した最小形で、下の「未実装の構想」より単純である。

```
type Pool[T] struct {
    slots mut []T
    gens  mut []int
    free  mut []int
    nfree int
    out   int
}
type Handle struct { idx int; gen int }

func Acquire[T](p mut Pool[T], v T) Handle
func Release[T](p mut Pool[T], h Handle)
func Get[T](p mut Pool[T], h Handle) T?   // コピーで返す
func Set[T](p mut Pool[T], h Handle, v T) bool
func Len[T](p mut Pool[T]) int
```

- `Poolable` 型クラス（create / destroy / canReuse / resetの辞書）は実装されていない。std/poolはAcquire / Release / Get / Setの最小形だけで、backendを差す仕組みは持たない
- `pool.Acquire(mut p, v)` はHandleだけを返す。ピン済み参照 `*T` は実装しない（Soberにポインタ・参照の型が無いため。2節を参照）。スロットの中身の読み書きはGet（コピーで読む）/ Set（コピーして書き戻す）で行う
- Tはstring / slice / mapを含んでよい（R1。`Pool[string]` はexamples/pool_string）
- 世代は偶数 = 空き・奇数 = 使用中。世代の一致しないHandleへのReleaseはpanicする
- 規則R-a（analyzerの局所照合。実装済み）: `h := pool.Acquire(...)` の直後の文が、同じpとhの `defer pool.Release(p, h)` でなければ拒否する。早すぎるrelease・二重release・別名経由は形の上で書けない。対応するreleaseのないacquireも拒否され、fixがdefer行を書く（GoのBody.Close忘れ検出と同型）。警告ではなく拒否で、言語の「analyzerの通過が受理の定義」に乗る
- release忘れは安全側: 実体はPool（親スコープ）が所有するので「Poolのスコープ終了まで再利用されない」だけ。ダングリングも二重解放も起きない
- 返却先はPoolのあるスコープS、利用は子スコープC。Cのregionが消えてもTの実体はSのPoolにある。Cから漏れた `Handle` は次のacquireで世代が進んで `nil` になる。「所有と利用の分離」がregion + Handleで構成的に成立
- 動的オラクル: Pool自身の未返却カウンタで「analyzerが受理したなら実行終了時の未返却は0」を検証する（scripts/pool_oracle.sh）

未実装の構想（Place / GPU / IOのbackendに広げるときの設計案。2026-09-17の当初案のまま、実装も決定もされていない）:

```
type Poolable[T, A] struct {
    create    func(A) (T, error?)  @effects(...)   // 必須
    destroy   func(T)                              // 必須
    canReuse  func(T, A) bool?                     // nil = 再利用しない
    reset     func(T)?                             // nil = 何もしない
}
```

- 型クラス `class Poolable` を関数値のstruct（辞書）にする案。デフォルト値は `T?` フィールドの `nil`。「can_reuseがデフォルトならPoolはフリーリストを持たない」を、comptime分岐ではなく辞書定数の定数伝播 + dead code除去で表す案
- `pool := place |> pool(backend)` でPlaceのregionにPoolを置く案（3節のPlaceが未実装なので、この経路も未実装）
- fence紐づき遅延再利用: `completion: fenced` のPlaceのPoolは返却時に現在のfenceを記録し、`canReuse` の前にfence完了を確認する案（Pool実装の中のPolicy分岐で、利用側コードはCPU / GPUで同一にする）。leaseのpool（4c節）はこの構想の一部を「宣言した世代の数kを超えたら待つ」という形で先に実装済み
- 外部依存リソース（swapchain、接続プール）もPoolのbackendにする案。「待ち → 提供 → 返却」を双方向yieldのジェネレータで表す形は採らない。for-yieldはpush型で双方向yieldを持たないため、`create` / `canReuse` が `block` エフェクトを持つbackendとして書く案

## 4b. Poolのホットパス: 動的検査のはしご（未実装の構想。当初案2026-09-18）

freeze（1c節）と同じパターン「動的検査が健全性の底、静的検査は検査を剥がす最適化」をPoolに適用する案。安全性と性能を別の層に置くので、analyzerの精度が上がるほど速くなり、証明できなくても遅いだけで壊れない、という設計。レベル1（acquireのピン済み参照）は2026-09-27の決定（4節・2節参照）でピン済み参照自体が採られなかったため実装されていない。いま実装されているのは、`Get(h)` が毎回世代比較と `nil` 分岐を行うレベル0相当の形（4節のstd/pool.Get）と、acquire / releaseの対応を検査するR-a（4節）だけである。R-aは `Get` の分岐を消す最適化ではなく、release漏れを拒否する別の検査である。

以下は当初案のまま、実装も決定もされていない:

| レベル | 形 | 検査コスト | 保証の出所 |
|---|---|---|---|
| 0 | `Get(h)` → `T?` | 世代比較 + `nil` 分岐が毎回 | ランタイム（常に健全） |
| 1 | acquireのピン済み参照 | スコープ内ゼロ | 型（regionの狭め替え）。不採用（2節） |
| 2 | analyzerの有効性導出で `Get` の分岐を除去 | ゼロ | analyzerの証明。底はレベル0 |

- レベル2の判定を局所照合にする案: 「hが同一ブロックのacquire由来（または有効性導出済みのhのコピー）で、区間内にそのPoolへのrelease / closeが届かない」。他コルーチンのreleaseを排除したい区間は `@noblock`（language.md 11節）で主張する案。導出できなければレベル0にdegradeするだけで正しさは変わらない、という設計
- B木探索のような「Handleを保存して辿る」ホットパスはレベル2が本命になる想定（SoberSQLの性能を決める項目）
- レベル2が効いた/効かなかった場所をlintで可視化する案（Place越境コピーと同じ「性能を決めるものは見える」の方針）

## 4c. 貸出（lease）— 外の書き手にpoolを貸す（決定2026-10-13 — IO設計。実装はIOのタスクのフェーズ2 (c) から — 下の「段取り」）

完了ベースのio（io_uring）は、提出から完了までカーネルがバッファに非同期に書く。プログラムの検査が見えない書き手が、時間の穴をまたいでメモリを持つ — regionの「スコープを抜けたら解放」とも、Poolの「返却 = プログラムのrelease」とも衝突する（language.md未決「IOブロッキングとスケジューラの結合方式」の「region × in-flightバッファ」）。これをPoolの第三の状態とpool単位の世代で受ける。外の書き手の梯子（カーネル → プロセス〔shm〕→ DMA → GPU）の最初の段階で、4節のfenced Placeの遅延再利用は同じ形の特殊例として読み替える。

- スロットの状態は3つ: **空き / プログラムが持つ / 外の書き手に貸出中**（4節のPoolは空き / 使用中の2つ）
- leaseの単位は **pool**（スロットごとではない）: 「このpoolの世代gは、外の書き手に貸出中」。ioのpoolは宣言で世代の数kを持つ — `io.NewPool(slots: 64, size: 64 * KB, gens: 2)`（名前つき引数で属性を境界に書く。`gens:` の既定は2 = ダブルバッファ）
- 登録 = pool丸ごと1回（io_uringのregistered buffersの一括登録と形が一致する。ringはワーカーごとなので、同じメモリを各ワーカーのringに登録する — language.md 28節）
- 世代の回転は **スコープの境界で起きる**: ストリームのforの反復の境目・`task.Run` の出口で、rtは「次に使う世代の完了が全部届いた」ことを待ってから（fence）その世代を使う。回転はrtの中の動作で、利用者のコードにresetの語は無い — **「貸出中のpoolをresetする」は構文的に書けない**（DESIGN柱1「メモリの詳細は構造と宣言から導出」の、外の書き手の時代の論拠: 手で書く「貸出中」「世代」は検査できない主張だが、構造から導出した世代は定理になる）
- 非同期の解放の契機（外の合図）はpoolの境界の内側に封じる。個体ごとの遅延回収の列は持たない — 寿命は「poolの本数と回し方」の宣言から導出される
- poolの空きが尽きたら、空きが出るまでtaskが待つ（有界 = 背圧 — chanの有界と同じ方針）。デッドラインがあれば待ちは `io.Timeout` で終わる（language.md 28節）。上の未決「fenced Placeでfence未完了のとき」は、leaseのpoolについては「k世代を超えたら待つ」にフォールバックする

検査の形（何を拒否するか）:

| 規則 | 形 | 層 |
|---|---|---|
| L1貸出中のpoolに書かない | 第1タスクは読み込みのパスだけ（カーネルが書き・プログラムは完了で渡されたViewで読む）。プログラムがpoolのスロットへmutで触るAPIが無いので書けない | 型（APIが無い） |
| L2貸出中のpoolをresetしない | resetは回転の中だけ — 語が無い | 構造 |
| L3 Viewを世代の外へ持ち出さない | Viewはforの反復のブロックのregionの型（祖先regionの値を現在ブロックのregionとして見る狭め替え。新しい型規則なし。4節の旧案「acquireのピン済み参照」が意図していたのと同じ狭め替えだが、Viewでは実装されている）。外へはコピーしてだけ出せる | 型（既存のregion規則） |
| L4書きのlease（フェーズ4d — 大きい本体のゼロコピー。小さいレスポンスの `io.Send(c, b)` は同期のコピーでleaseではない — language.md 28節のnet） | 枠を埋めて `io.Send(conn, buf)` に渡したらbufは消費される — 17節のfreezeの一意性の検査（渡すパスが一意・渡した後に同じパスを使わない）を流用 | 検査器（既存の機構） |

- 新しく足す検査はL4の「消費」だけで、それもfreezeと同じ機構に載せる（1c節の棄てた案「借用追跡」の方針を保つ）
- 動的検査の底は持たない（4b節のはしごのレベル0に当たる「Viewに世代の番号を持たせ、回転後の読み込みでpanic」は入れない — L3が型で閉じるので底が要らない。入れるならgatesのミューテーションのテストとして）
- 最適化の前提を1文で書く: **ioの関数の呼び出しが書きうるのは、貸出中のpoolのスロットと、その関数の戻りの値だけ**。rtの関数の「書かないものの表」（hloop / rlim / cpfwdが読む「既知のrtは書かない」）に1行で足し、ioの呼び出しをまたいで、貸していないメモリのloadを保持・巻き上げられる。正しさはL1〜L4が保証し、最適化は前提を読むだけ（検査を足さない）
- 段取り（2026-10-13・IOのタスクのフェーズ2 (c)・決定U1 = 案P。フェーズの番号はlanguage.md 28節のioのフェーズ）: 最初の実装は **ストリームの私有のpool**（1本のforがgens個のスロットを持つ — 既定64 KiB × 2・APIは後続のタスク）。
  世代の回転 = 反復の境目（前の切片を返して次の読み込みを出す）・fence = forの出口のchunk_closeとtaskの死の出口のchunk_drain（貸出中の読み込みの完了を待ってからスロットを返す）。
  スロットはstd/taskのプログラムでワーカーにringがあればワーカーのアリーナ（16 × 64 KiB — ワーカーの最初のChunksでmmapし、ringに固定バッファとして1回だけ
  登録 — READ_FIXED）から取り、無ければ記録と同じregionから取る（READ / 同期のread）。共有のpool（`io.NewPool` をtaskとワーカーの間で1本・空き切れの背圧）は
  Webのマイルストーンの実需と `pool:` 引数で。棄てた案: 案Sを今入れる（行き先のない往復 — language.md 28節）・ストリームごとに自分のスロットを登録する（BUFFERS_UPDATE —
  5.15 は外した登録のmemlockの戻りが遅延workなので、短いストリームが続くとENOMEMでREADにフォールバックする — 実測report-608）
- netの受信のpool（決定2026-10-14 — netの決定N10・language.md 28節のnet。実装2026-10-14 — 4b-1・report-665。増分消費の形2026-11-02 — report-rt-0〜2）: ワーカーごとのPBUF_RING 1本（登録はpool丸ごと1回 — 上の形そのまま。カーネルがバッファを選ぶ）。
  **既定は増分消費のリング**（IOU_PBUF_RING_INC — カーネル6.12以上）: ワーカーごと16 KiB × n本をそのワーカーの全接続で分け合い（n = clamp(1024 ÷ W, 16, 64) を2の冪へ切り下げ — 全ワーカーの和をWに依らず ≈ 16 MiBに。要る量は接続 / ワーカー × リクエストの大きさで、接続の総数が同じならWに反比例する — 決定2026-11-02 report-rt-2）、カーネルは頭のバッファの続きに受けを書く（受け1回は届いた分だけ使い、バッファの残りで切れる）。
  受けの単位は**区間**（バッファ・始まり・長さ）で、接続の受信の列は区間の連鎖。区間の始まりはrtがバッファごとに持つ「カーネルが書いた位置」から出す（完了は始まりを運ばない）。
  バッファは「カーネル済み（F_BUF_MOREの無い完了）かつ未読の区間0」でリングへ戻す（バッファごとの参照数）。区間は1バイト以上なので、生きている区間の数はリングの総バイトを越えない — 区間の表はその大きさで取り、尽きない。
  Recvは列の区間を頭から求められた長さまで続けてコピーする（バッファの境目で分かれた受けを1回で返す。分かれたまま返すと、呼び手〔std/http/server〕が未完のリクエストを持ち越して持ち越しの列を取る — 実測で接続ごとに270 KB常駐した）。
  固定費のRSS = リングの総バイト（リングが一巡すると全バイトが触られる — W ≤ 16で1 MiB / ワーカー・W 64で256 KiB / ワーカー = 和16 MiB）。リクエストの大きさに依らず、フォールバック（下のread）は接続の数ではなく未読のバイトで決まる。
  遅い接続（読まれないまま区間を持つ）はバッファを丸ごと押さえる。押さえは本数で吸収し、全部押さえられたら下の空き切れ → readのパスへ縮退する（悪くて固定スロットのリングと同じ振る舞い）。
  登録が断られたら（6.12より前は未知のflagsをEINVAL）**固定スロットのリング**で登録し直す。開発用のオプション `SOBER_PBUF_INC=0` はこちらに固定する（httpcheckが両方のパスを回す）。
  棄てた案（2026-11-02 — report-rt-0 / 1）: (A) 固定スロットの本数の下限を接続の数に合わせて上げる（フォールバックを消すには ≈ ワーカーあたりの接続数 = 512本級が要り、全種目が常駐を払う — W 64で +120 MiB）・
  (B) 需要で育てるリング（空を見たら本数を足す — 山の高さだけ常駐が残る。増分消費が使えない環境の救済として温存）・(D) 空きが戻るまで張り直しを待つ（受けの待ちが無界になり、待ちの上限の規律とぶつかる）。
  押さえの追い出し（押さえている区間を別の格納場所へコピーしてバッファを放す）と接続ごとの未読の上限は、押さえによるフォールバックが観測されたら設計提案する。
  固定スロットのリング: 大きさ = ワーカーごと16 KiB × n・n = clamp(2048 ÷ W, 32, 256) を2の冪へ切り下げ（決定2026-10-24 — report-1102。全ワーカーの和をWに依らず ≈ 2048本に）。
  小さい受けでもリングが一巡すると全スロットの先頭のページが触られるので、固定費のRSS ≈ n × 4 KiB / ワーカー（W ≤ 7で1 MiB・W 64で128 KiB）。
  棄てた案: 固定の256（決定D1）— 固定費がWに比例し、W 65で ≈ 65 MiB（report-1092 / 1099）。
  **受けは届いたスロットから反復のregionの先端へコピーし、コピーし終えたスロットはその場でリングへ返す**（コピー1回 — カーネルのコピーと合わせ同期のreadと同じ回数・決定2026-10-14 report-665）。
  スロット（増分消費のリングではバッファと区間）の状態は「カーネルに貸出中（リングの中）/ 接続の受信の列にある（届いてコピーしていない）」の2つで、プログラムの値はスロットを指さない。
  世代の回転は受信には適用しない — 多数の独立した接続が1つのpoolを共有するので、世代ごとのfenceは最も遅い接続に全員を待たせる。
  空き切れ = カーネルがmultishot RECVをENOBUFSで止める（F_MOREの無い完了）。張り直しは次のRecvで、その時点でリングの空きが0なら今のread（EAGAIN → POLL_ADDの待ち）へフォールバックする —
  張り直しを空きの戻りに賭けないので進行を保証する（有界の背圧 — 上の「空きが尽きたら待つ」のnet版）。世代 `gens:` の既定2は
  ファイルのパスと送信の枠に残る。送りとenterのファイルの参照は登録済みのring fdと固定のファイル表で省く（language.md 28節のnet — 2026-11-02）。epollのパス（フェーズ4a）はワーカーの作業スロットを使わず反復のregionへ直にreadする（同じコピー1回）。
  棄てた案（4b-1の時点）: スロットのViewを反復のregionの型で貸し出し、反復の境界でスロットごとにリングへ返す（決定2026-10-14の当初の形 — std/netのRecvの形とrtの返しのAPIが要り
  instが乗る一方、syscallの対象に効かない。大きい本体のゼロコピー〔4d〕のタスクで再訪。返却の契機が構造の境界なので下の棄てた案〔個体の遅延回収の列〕には当たらないことは当初の論のとおり）
- 棄てた案: スロットごとのlease（個体の遅延回収の列が要り、非同期の解放の契機がプログラムの全域へ漏れる — GPUの段階で要ると分かったら再評価）・leaseを借用追跡で検査（1c節と同じ理由）・利用者が書くreset / fence（手で書く「貸出中」は検査できない主張 — Vulkanの規約文書 + validation layerの世界）・バッファの持ち込み（Goの `Read(p []byte)` — バッファの管理の詳細がコードに漏れ、貸出中のバッファへのプログラムの書きを型で止められない）

## 4d. ワーカー局所のlease — 作業域をtaskをまたいで使い回す（決定2026-10-16 — report-717の決定6点 + report-719の決定 (A)〜(D)。実装 = `pool.Scratch` 2026-10-16〔report-718〕・ウィンドウの綴りと書き換えreport-719a・ワーカーごとの領域と使用中のフラグ〔rt — lower/lease.sober〕report-719b）

実需: keep-aliveの接続のtaskが圧縮の符号器の作業域（≈ 84 KB）を自分のregionに持つと、作業域は接続の数だけ居座る（16384接続で1.3 GB分 — report-716）。
同時に符号化しているのはワーカーの数だけで、符号化の本体はioを跨がない。region（流れ — 空間局所性の器）では畳めない「taskをまたいで同じ場所を使い回す」時間を、
世代（時計）として明示に持つのがPool（滞在 — 時間局所性の器）で、leaseはそのウィンドウの間だけ時間を構文（字面のブロック）へ畳み直す。

```
// 置き場を作る（T の package の整えの関数 — 欄は宣言の package でだけ書ける）
gzw := task.NewLocal((w mut compress.flate.Work) => compress.flate.NewWork(mut w))
…
// 窓 = mut 仮引数 1 つの inline ラムダ — 借りる / 返すが 1 つの式の入口と出口・値は本体の値
z := task.Lease(gzw, (w mut compress.flate.Work) => compress.flate.EncodeWith(mut w, body, level))
```

- **意味の約束 = 「lease ≡ 新しい値」**: `task.Lease(lp, body)` は `{ mut w := T{}; 整え(mut w); body(mut w) }` と観測上同じ（スカラーのフィールドはゼロ値・
  Scratchは整えた容量で全部0）。leaseは「新しい割り当て」の最適化で、言語の意味に現れない（Leanのコアは無変更）。帰結: 決定性（Kahn・schedfuzz）を壊さない
  （どの接続が前にそのワーカーで使ったかが出力に漏れない）・ウィンドウの途中の死（panic・ChildDied）で後始末が要らない（次のleaseが「まっさら」に見せるので、壊れた中身を戻さない）
- 実装の形（report-719a）: **loaderが呼び出し点を脱糖の固定テンプレートで書き換える**（loader/lease.sober — namedargs・η 展開と同じ層。checkとbuildが同じ木を読む）:
  `{ $lp := lp; $at := $task.LeaseTake($lp, <T の指紋>); defer $task.LeaseGive($lp, $at); mut w := T{}; $pool.LeaseAttach(mut w.f, $task.LeaseBlock($lp), $at, i) …; 本体 }`。
  テンプレートの形そのものが約束で、格納場所の使い回しは書き換え先（LeaseTakeが領域を返す・LeaseAttachが領域の列を付けて世代を進める）の中だけの最適化。
  格納場所の列の形 = [指紋, n, 容量 × n, W, 領域 × W]・領域 = [フラグ, リスト, フィールドごとに (tag, ワード × 容量)]。rtの関数は2つ（lower/lease.sober — stdの書き換え先だけが宣言する
  `@intrinsic`）: `lease_op`（ワーカーの数・今のワーカーの番号・フラグを取る / 返す・領域のワードの生の読み書き — immの列のワードを書くので不透明なrtの呼び出し）と
  `lease_view`（領域のワードを指すmut []int — 深度は列のまま。バイト版の `lease_bytes` = blkのoffワード目からnバイトを指すmut []byte — std/tlsの送りのバッチ・2026-10-25）。使用中のフラグは今のtaskのリスト（TCBのワードTC_LEASE — ウィンドウは字面のブロックなのでLIFO）に積み、
  taskの死の出口（fd_drainの隣）と縮退した子の死（入る前の頭まで）で外す。taskの無いプログラムはリストを持たない（死 = プロセスの終わり）。
  テスト: schedfuzzのミュータント15（フラグを見ない — ウィンドウの中でチャネルを待つtaskの格納場所を同じワーカーの別のウィンドウが共有する形をexamples/lease_yieldが捕まえる）・
  iterregion ⑧（ウィンドウの反復のRSS）。整えのウィンドウはNewLocalで1度走り（Tを1つ作って容量を読む — 1回きりのコスト）
- 「まっさらに見える」は毎回の全消しでなく **世代タグ**で: 格納場所のTが持てる容器は `pool.Scratch`（世代タグつきの固定容量のintの列 — 1ワード = 世代32ビット ‖ 値32ビット・
  読み込みは世代が今と違えば0・leaseの入口で世代を1つ進めるだけ〔O(1)〕・世代が一周〔2^32回〕したときだけ本当に消す — zlibのheadの手）
  - ウィンドウの中の `pool.Renew` は進めた世代を格納場所へ書き戻す（Scratchが格納場所の住所を持つ — 書き戻さないと次のウィンドウのLeaseAttachが同じ世代を配り、
    Renewの後の書きが次のウィンドウに見えた〔report-720で修理・回帰例examples/lease_renew〕）
  - 生のアクセサ（世代に触れない — 鮮度は呼び手が持つ）: ワードの `LoadRaw` / `StoreRaw` と、ワードを16 / 32ビットの項目の列と見る `LoadRaw16` / `StoreRaw16` /
    `LoadRaw32` / `StoreRaw32`（添字は項目の単位・容量はワードのまま — 格納場所の容量の宣言とLeaseAttachはワードで数える）。表の足跡を詰めるAPI（deflateのチェーンと
    ハッシュの表 = 16ビット）。棄てた案: 1ワードに4項目をshift / maskで詰めるstdだけの形 — 項目ごとの読み込み‐変え‐書きで命令が利得を食う
- 最初の利用者 = std/compress/flateの `Work`（記号・頻度・チェーン・ハッシュの表のScratch 4本 + スカラー — `compress.flate.NewWork` が最大の容量 ≈ 200 KBに整える — 記号と頻度は32ビット・チェーンとハッシュの表は16ビットの項目）と
  `compress.flate.EncodeWith` / `compress.gzip.EncodeWith`（Encodeは `Work{}` を作って呼ぶ形 — 出力のバイト列は同じ）。httpのAPIはServeConnの名前付き引数 `work:`
  （compression: と組み — 無しならpanic(WorkNoCompress)・省略はリクエストごとに作業域を取る今までの形）。json-compのRSS / 接続は150 → ≈ 70 KB（report-720）。
  コスト: 作業域は1ワード1項目（世代タグの容器）に戻したので、work: を渡さない既定のパスはリクエストごとの作業域が詰めた形（report-716）より大きい
  （json-compのRSS / 接続150 → 200 KB — ユーザー決定2026-10-16で受理。接続数に比例させたくない利用者はwork: を渡す）
- **フォールバックの形（ウィンドウの中の譲りは禁止しない）**: ウィンドウの中でio・sleep・chan・spawnの待ちに譲ると、同じワーカーの別のtaskが同じ格納場所を借りに来うる。rtは格納場所の
  「使用中」のフラグを見て、後から来たleaseを **新しい割り当て（そのtaskのregion）にフォールバックする** — 意味の約束で観測は同じで、遅く（重く）なるだけ。正しさに動的検査の底も
  静的検査も要らない（4b節のはしごと同じ方針: 証明できなくても遅いだけで壊れない）。analyzerは性能のlintを2つだけ出す: ① blockエフェクト（language.md 12節）が届くウィンドウ
  （フォールバックしうる）② ウィンドウの中で同じLocalをもう一度借りる（必ずフォールバックする — 入れ子の2つ目が新しい割り当て）。ioを跨いでleaseを持ちたい用途（DBのbuffer pool）は下のSharableのタスク
  - lintの形（実装2026-10-16 — analyzer/lease.sober）: **警告**（`<位置>: warning: … (Analyzer)` — 受理は変えない。受理した `sober check` だけが判定の前にstderrへ出す。
    言語に警告を出す仕組みはこれが最初 — 拒否のanalyzerの指摘と同じ列にwarnのマークを付けた）。① のblockエフェクトはcall graphの推移閉包（desugar.MayBlock — 葉 = std/taskの
    Scope・Join・Try・Send・Recvとrtの待つ関数sleep・wait_fd・net_op・read_fd）で、1つのウィンドウに1回だけ警告する。近似: 関数値の呼び出しは見えない（鳴らない側）・
    Localの同一性は名前の字面（別名・関数をまたぐ入れ子は見ない）・ウィンドウの中でspawnした子のラムダは別のtaskとしてウィンドウの外に数える。棄てた案: 拒否（意味は同じなので
    受理を変える理由が無い）・`--lint` の開発用フラグ（見えないlintは効かない）
- **格納場所 = ワーカー局所・NewLocalで先取り**（決定 (B)）: NewLocalはその場でW個のTを呼び手のregionに作る — 格納場所はNewLocalを呼んだregionに住み、子taskは
  そのscopeより長生きしない（structured concurrency）ので、ワーカーの寿命の領域（rtがSoberの値を置く新しい住所）が要らない。接続のtaskはワーカーに固定され、ウィンドウは譲らなければ
  割り込まれない（協調スケジューリング）ので **原子操作なし**。容量 = 1つ × W（使わなくてもW × 作業域を取る — コスト）。使用中のフラグはtaskの死の出口で外す
- **置けるT = スカラー（int・byte・bool・float）と `pool.Scratch` のフィールドだけのstruct**（loaderの検査 — diag.Par 26）。slice / string / mapを持つTは拒否:
  ウィンドウの中のコピーの規則（若いregionの値を古い格納場所へ書くとコピー — language.md 21節）で格納場所が伸び続ける
- **容量の宣言 = NewLocalの整えのウィンドウ**（決定 (B)）: ウィンドウの本体はScratchのフィールドごとに `pool.NewScratch(mut w.f, 定数)` をちょうど1回（定数 = 字面・constの名前・括弧・+ - * <<）。
  フィールドは宣言のpackageでだけ書ける（language.md 20節）ので、Tが別のpackageならウィンドウはTのpackageの関数1つ `F(mut w)` を呼ぶ形で、その本体を同じ規則で検査する（diag.Par 27）。
  Fの本体が1文の転送 `G(mut w)`（wはFの唯一のmut仮引数そのもの）ならGへ辿る（深さ4まで — 決定2026-10-22・report-1043 A4）。Tがstd/internalの型で
  公開の名前が型の別名（language.md 32節）のとき、整えの関数の本体はTのpackage（internal）に置き、公開のpackageには転送を置く — `compress.flate.NewWork(mut w)` が
  `deflate.NewWork(mut w)` を呼ぶ形。棄てた案: 別名を宣言したpackageも「Tのpackage」と数える（別名は宣言のpackageを変えない — 転送の本体はTのフィールドを書けないので、検査は結局Tのpackageの本体に要る）
  テンプレートが組むフィールドの場所（容量の読み取り・領域の付け外し）はloaderのフラグ（EMutArgのb）でフィールドの書きの規則の外 — 形はloaderが検査済み
- **NewScratchは1回だけ**（決定 (C)）: 容量のあるScratchに呼ぶとpanic(ScratchSized{})。ウィンドウの中で作り直すと、新しい列がtaskのregionに取られて長命の格納場所から
  宙吊りになる — 呼ぶ関数は別のpackageにあり局所の検査では届かないので、動的な不変条件にする（フォールバックのパスでも同じ振る舞い — 観測は分かれない）
- **Localの値 = regionに住むimmの列**（決定 (D)）: 端点のような同一性の型にしない — 約束のもとではコピーしても観測は変わらない（どのコピーから借りても中身は「まっさら」）。
  immの列なのでregionの規則がそのまま効き（外へ出すと列ごとコピーされる = 別の格納場所・遅いだけ）、捕獲・spawnへの受け渡しはimmのデータの既存のパスで通る。ゼロ値 `task.Local{}` は
  何も指さない偽物として拒否（同一性の型の種類のゼロ値の規則 — NewLocalだけが作る）。rtが使用中のフラグをimmの列に書く点は、rtの「書かないものの表」で書き換え先を「書く」側に置く
- **task.Localは型引数を持たない**（実装の制約 — report-719a）: Tはmutの列（Scratch）を持つstructで、型引数に置けない（language.md 25節 — 型引数はコピーできる型）。
  Tの同一性はloaderが型の名前（packageのpath + 名前）から焼いた指紋を格納場所に持たせ、LeaseTakeがウィンドウのTの指紋と照合する（違えばpanic(LocalType{}) — 呼び手の契約違反・
  静的な照合の代わりの1比較）
- ウィンドウの綴り（決定 (A)）: ラムダの仮引数に `mut` を書ける（仮引数宣言と同じ綴り — syntax.mdのLambdaParams）が、**task.Lease / task.NewLocalのウィンドウの位置だけ**（他はloaderの拒否 —
  diag.Par 25）。関数型にmut仮引数は足さない（stdのLease / NewLocalの宣言の署名は柵 — 呼び出し点は全部書き換えられる）。逃げない保証はmut仮引数のU3がそのまま閉じ、
  早すぎる返し・二重の返しは形の上で書けない（4節のwithPageの形）。30節R-a（Acquire / Releaseの局所照合）の対象は広げない・新しい拒否規則も足さない
- std/poolのPool[T]（Acquire / Getのコピー / Release）はそのまま残す — 「Handleを保存して後で引く」（索引・LRU）の用途で、leaseとは別の道具
- 棄てた案: 中身の持ち越しを許すlease（速いが「どのtaskが前に使ったか」が観測に漏れ、決定性の約束の外）・ウィンドウの中の譲りを拒否する（`@noblock` のウィンドウ — 拒否の規則が1つ増え、
  フォールバックの形で足りる）・Acquire / Releaseのhandleで借りてGet / Setでコピーする（毎回のコピー — 84 KBの作業域では本末転倒）・ピン済み参照 `*T` を言語に（4節の当初の設計 —
  mut実引数のパスで足りる間は保留）・格納場所を接続のtaskごと（今の形 — 接続数に比例）・Sharable（全ワーカーで1本・原子的な取り出し — 符号器には過剰〔競合・偽共有〕。
  ioを跨ぐlease〔DBのbuffer pool — ピン = 貸出・eviction = 世代のfence〕の用途としてPhase 3の原子性の設計と同時に）・Localをstructのフィールドに置く
  （`http.server.Gzip{level, work}` — httpのAPIはServeConnの名前付き引数 `work:`）・rtがstdの型ごとに暗黙のLocalを持つ（`@worker_local` — グローバル変数に近く、属性を境界に書く柱と緊張）・
  関数型一般にmut仮引数（26節G3・関数値にmutの別名が乗る）・`w =>` で暗黙にmut（表記の無いmut）・型の宣言に容量（フィールドの既定値の構文が無い）・初回のStoreで伸ばす（ウィンドウの中で伸びる）・
  初回のleaseで格納場所を作る（ワーカーの寿命の領域が要る）・Localを端点と同じ同一性の型（give: で1子へ移す — 接続のtaskは数千）・`Local[T]` の型引数でTを照合する（上の25節）・
  desugar（checkの経路）とlower（buildの経路）で別々に書き換える（同じ規則の2実装 — check ⊂/⊃ buildの食い違いの原因。loaderの1か所に）

## 4e. 貸し出しの梯子 — 外の書き手の段階（構想2026-10-12・0.6.0の決定2026-10-17 — IO基盤の壁打ち 論点3）

「プログラムの検査が見えない書き手にメモリを貸す」はio_uring固有でなく、段階のある1つの型。育てる順:

| 段階 | 外の書き手 | 足されるもの | 状態 |
|---|---|---|---|
| 1 | カーネル（io_uring） | 最小の実物 — リング1本・バイト列・世代は読み込みの回転だけ | 読み込みは4c節で実装・書きのleaseはL4（フェーズ4d） |
| 2 | プロセス（shmチャネル） | 相手が対等（双方が読み書き）・プロセスモデルの枠 | 構想（PINS） |
| 3 | デバイス（DMA） | ピンされたページ（動かないメモリ）・デバイスの完了 | 構想 |
| 4 | GPU（Vulkan） | 世代（N-buffering = in-flight多段）・遅延回収（fence後のdeferred deletion）・双方向（storage buffer / readback） | 構想 — 最難関。sujiniのVulkanの実地の痛みが素材 |

- **0.6.0の決定（2026-10-17）: registered buffersはrtの内側に留める**。表面はView貸し（4c節L3）のまま・READ_FIXED / WRITE_FIXEDはrtの性能改善のタスク
  （design-dev.mdのIOのタスク ⑤）・「貸出中 = カーネルが書き手」の第三状態はrtの規律で守る。**言語のlease型を切るのはGPU / shmのマイルストーン** —
  io_uring（段階1）だけから型を切ると、世代・双方向・遅延回収が足される段階で作り直しになる。最小の実物をrtの内側で運用し、2段階目以降の実需が
  形を出してから型にする（io_uring = 前哨戦、の位置づけ）
- pool単位leaseの勝ち筋（2026-10-12の発見 — 型を切るときの出発点としてここに昇格）: ① 登録 = pool丸ごと1回（registered buffersの一括登録と形が一致）
  ② 世代 = poolをin-flightの数だけ回す（fenceが通ったらpoolごとreset — 個体の遅延回収キューが消える。Vulkanのper-frame arenaの実務知の構造への昇格）
  ③ 非同期の解放契機がpoolの境界の内側に封じられ「寿命は構造から導出」と和解する ④ 検査が粗くて安い（「貸出中のpoolに書くな・resetするな」の2つ —
  4c節のL1 / L2がそのまま）。個体単位のleaseはGPUの段階で要ると分かってから再評価（4c節の棄てた案）
- 型が切れた後に開く最適化のバックログ（裏の動機の記録）: 外部の書き手のエフェクトを型が区切ると、ioの呼び出しをまたいで非貸出メモリのloadを保持・巻き上げられる
  （4c節「最適化の前提を1文で」の一般化）・submit / completionを跨ぐソフトウェアパイプライン化・カーネルが書くpoolのfalse sharing回避とNUMA配置

## 5. 並列とデータ分割: SoA強制（決定: 案 (a)）

> 2026-10-05注記: 下の例の「spawnの引数にmutな配列を渡す = 所有の移動」は、今の表層ではspawnのクロージャがmutを捕獲できない（language.md 11節）。所有の移動は端点の引き渡し（`give:`）と同じAPIで書けるかをフェーズ6で確認する。

mutパス（`mut(elem.position)` の非重複検査で同一配列への分割並列書き込みを許す）は採らない。

- 並列スコープに渡せるのは不変値かチャネルのみ、という1項の規則を崩さない。フィールド単位のアクセス権行列（read / atomic / mut）と重複判定を言語から消す
- 結果、ECS型ループ「同じentitiesをpositionとframeで並列更新」はそのままでは書けない。代わりにSoAを強制する: `positions []Vec3` と `frames []int` を別配列に分け、並列スコープごとに1配列を所有させる

  ```
  parallel scope {
      spawn physics(positions, velocities, dt)   // positions を所有、velocities は不変
      spawn animate(frames, dt)                  // frames を所有
  }
  ```

  所有の移動はスコープ境界の明示（`spawn` の引数にmutな配列を渡す = そのスコープの間は親から触れない）。これはregion規則の「単一書き手」で表現でき、新しい型規則は要らない
- 採る理由: (1) メモの「健全性はコンパイラ、その他はanalyzer、ただしメモリ安全とdata race freedomはコンパイラ」の方針に乗る (2) GPU側は元からSoA（SSBOの列）なのでCPU側も揃えると `receive` の転送単位が自然に配列になる (3) 最小権限をlintで段階的に絞るUXを丸ごと不要にする
- 払うもの: AoSで書いた既存コードの移植コスト、struct 1個に纏まっていた「エンティティ」が配列群 + indexになる可読性。ECSはもともとそういう形なので損は小さい
- 撤退条件: SoA化で書けない並列パターンがゲームの移植中に3つ以上出たら、mutパスをanalyzer層の属性（`@mut(.position)` の非重複検査、unknownは拒否）として復活させる。コンパイラ側には入れない

## 6. 採らなかった機構と、その読み替え

| 採らなかった機構 | Sober |
|---|---|
| `class Poolable` / `impl` / 構造的充足 | 関数値structの辞書。省略は `T?` の `nil` |
| comptimeによるPolicy分岐・can_reuse分岐・転送方式選択 | 定数辞書 + 最適化器 |
| `join` 必須、暗黙の待ちなし | スコープ終了で全spawnを暗黙join（structured concurrency）。未joinのハンドルはエラーではなく「スコープ末尾で待つ」 |
| acquireの自動返却（ブロック終了でPoolへ） | `defer release` を明示。忘れはanalyzerが拒否 + fix |
| 双方向yield（`-> yield Out -> In`） | 持たない。ジェネレータはpush型for-yield、待ちはPool backendの `block` エフェクト |
| mutパス、read / atomic / mut行列 | 持たない。不変値orチャネル + SoA強制（5節） |
| `T ! E` エラーユニオン、エラーセット自動合成 | `(T, error?)` + analyzerのラベル導出（メモ13節） |
| 値の精錬 `& nonzero` | 保留。analyzer層に入れるなら別メモ |
| 名前付き引数必須 | 落とす。`\|>` の第1引数省略と噛み合わない |
| 1ファイル1型 | 保留。packageが可視性の単位なので必須ではない |
| `nopanic` | `@effects(!panic)`（メモ12節） |
| 調停コルーチン（frame syncをyieldで書く） | コルーチン + チャネルでそのまま書ける。機構追加なし |
| スロットごとのlease・貸出中の借用追跡・利用者が書くfence / reset | pool単位のlease + 宣言した世代の回転（4c節） |

## 未決

- ~~escapeの自動化~~ → 決定（1節）: 境界越えはコピー、割り当ては所有者に従う、末尾式と単一割り当て点は親に再標的、残りはlint
- fenced Placeで `canReuse` が真だがfence未完了のとき、acquireはブロックするか新規createするか。候補は「fence完了まで再利用しない = 新規create」と「pipeline_depthを超えたらブロック」
  - 2026-10-13: leaseのpool（4c節）は後者 — 宣言した世代の数kを超えたら待つ（背圧）。一般のfenced PlaceのPoolはGPUの段階で同じ形に寄せるかを決定する
- ~~`receive` のstaged転送でstaging bufferをどのregionから取るか~~ → 決定（3節）: 宛先Placeのstaging Poolからacquire。fixがそこへ書き換える
- Handleの `Get` の毎回分岐コスト: 4b節の「動的検査のはしご」構想は未実装のまま。いまの実装は`Get`が毎回世代比較 + `nil`分岐を行う形（4b節のレベル0相当）だけで、スコープ内ゼロコストのacquireもanalyzerによる分岐除去も無い。レベル2の判定精度が実際のホットパスでどこまで効くかはSoberSQLの実装時に計測する未決のまま
- SoA強制のとき、複数配列をまたぐ「1エンティティの削除」（indexの整合）を誰が守るか。世代付きindexをエンティティIDにすればHandleと同じ機構で解ける
- 並列スコープに渡せる第3のクラスSharable（方向づけ2026-09-18、確定はPhase 3のアトミック設計と同時）: 「不変値かチャネルのみ」の規則に、内部同期を持つstd型（チャネル・Pool・アトミック）のマーカーとしてSharableを足す。型システムはマーカーの白リストだけ薄く持ち（mutFree検査の例外）、内部同期の正しさはTLA+（チャネル・joinと同じ枠、design-dev.md Phase 5b）とランタイム検証へ振る。チャネルはformal.mdの段階3cで形式化し、Poolは「チャネルで書いた参照実装と観測等価」を差分テストで見る。これでRDBMS未決の「Poolのスレッド安全性」は (a) 単一書き手 + 共有Poolの形が取れる方向になる。2026-09-18追記: Poolの骨格（acquire / release / 排他 / 待機 / 再利用）が新しい型規則ゼロでchanの派生形として書けることを機械化で確認（formal.md「Sharableの断片」、ex14 / ex15）。白リストはchan 1行のまま。mutスロットの循環は型が付かず、実Poolの可変スロットは4bのはしごが受ける。方向づけの詳細（原子性のレシピ・命名方針）はPINS.local.mdの「Sharable（B2）」に引き継がれている。Phase 3（std実装）は未着手で、型・実装としてのSharableはまだ存在しない

### RDBMS（SoberSQL、ゴールsober/sobersql）を書くと必ず要るもの（2026-09-17洗い出し）

前提: 「並列スコープには不変値かチャネルのみ」はPG / InnoDB式の「共有バッファプール + ラッチ」を構成的に禁じる。取れる形は (a) 単一書き手 + copy-on-write B木（LMDB系。不変ページの共有 = MVCCスナップショット）か (b) thread-per-coreのshared-nothing（Seastar系。Phase 5bのワーカー固定と一致）。SoberSQLの第一形は (a)。これは制約ではなく思想の一致として扱う。相性が良い点: ページのピン/アンピン = Poolのacquire / `defer release`、push型for-yield = push-basedクエリ実行（子 → 親のタプル返しが無いのでregion越境コピーが起きない）、forの反復 = regionなので長い走査でも一時割り当てが溜まらない。以下はdocsに答えが無く、Phase 3のstd設計時点で決める必要があるもの:

- アトミック / ラッチの逃げ道: LSNカウンタ、CoWのルート差し替えは原子的でなければならない。stdにアトミック型を置くか、型システム上どう扱うか（並列スコープに渡せる「第3の種類」になる）。無いと単一書き手ですら書けない
- バイトレイアウトと再解釈: ページのスロット配列、可変長タプル、非アラインの読み込み。Goの `unsafe` 相当が無く、FFI（Phase 6。既定はwasmで線形メモリは別Placeなので、そもそもSober側のメモリを見せる手段ではない）だけでは足りない。候補はZig式: (1) レイアウト定義済みstruct（Zigの `extern struct` / `packed struct`）を `@layout(c)` / `@layout(packed)` アノテーションで与える（9〜10節の方針どおり言語ではなく注釈層。注釈のないstructはレイアウト未規定のまま）、(2) エンディアンを読み込み時に明示するstd関数（Zigの `std.mem.readInt(u32, bytes, .little)`。ホストエンディアン暗黙の再解釈を持たない）、(3) `[]byte` → レイアウト定義済みstructのビューはstd関数で長さとアライン検査つき `T?` を返す（Zigの `bytesAsValue` + アライン付きポインタ型に相当。失敗は `nil`、UBではない）。ポインタ演算は持ち込まない。要検討: ビューが元の `[]byte` を参照するのでregion規則（子 → 親のみ可）にそのまま乗るか、mutビューの単一書き手をどう保つか
- Handleの `get` がホットパス: B木探索は1ステップごとにgetで、世代チェックと `T?` 分岐が毎回乗る。上記「analyzerが有効性を導出して分岐を消す」をSoberSQLでは性能を決める項目に格上げ
- ~~CPU束縛ループのキャンセル~~ → 解決: 中断点を含まないループのバックエッジにコンパイラが検査点を挿す（language.md 11節「キャンセル」）。公平性のためにも要るので追加コストではない
- Poolのスレッド安全性: 複数の並列スコープから同じPoolにacquireしてよいか。可ならPoolが唯一の共有可変オブジェクトになり、実装内にアトミックが要る（上記1項と同じ答えになる）。不可なら (b) の形しか取れない。→ 方向づけ: Sharableクラス（未決の最終項）で「可」に寄せる
- ~~コルーチンスタックの仮想予約~~ → 解決: スタック上界のリンク時計算（language.md 11節）でspawnごとに必要量だけregionから取る。Policyの予約サイズは不要
- 制約にならないもの: トランザクション・カーソルの寿命はセッションのコルーチンに閉じるのでLIFOで足りる。字句的でない寿命はバッファページ（LRU）だけで、Poolに振られている

## 実装との対応

- Phase 1（fib、if/switch式、struct、union、`|>`、for-yield）: 本メモと無関係。今すぐ着手可
- Phase 2（型検査）: regionのescape規則、`T?` flow typing、並列スコープの不変値制約。5節の決定がここに効く
- Phase 3相当: Handle / Place / Poolをstdとして書く。Pool（2・4節）の最小形はPhase 3を待たずに2026-09-27に前倒しで実装済み（language.md 30節）。Place（3節）はまだ未実装
- Phase 5: `parallel scope` のspawn先はPlaceのExecutor。タスクは生成時のワーカーに固定（design-dev.md Phase 5b）。`Policy.threads` = 1なら単一スレッド実行と同じ
- Phase 4以降: ゲームの移植で5節の撤退条件を計測
