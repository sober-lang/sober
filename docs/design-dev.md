# Sober — 設計の記録（開発者向け）

公開の設計の柱は [../DESIGN.md](../DESIGN.ja.md) に、利用者の「なぜ」は [設計ノート](design-notes/) にまとめてある。この文書は、設計の位置づけ・非目標・審査基準・決め方の型・実装計画を、決めた順に記録した開発者向けの台帳。

書くのは普通のコード、検査されるのは型システム級の性質。

Goの倹約（シグネチャ明示・packageが可視性の単位・仕様が小さい）を継いだ式指向言語。
表現力を書き手への新語彙で買わず、安全性はanalyzer（受理の定義に含まれる）と、スコープに閉じた寿命で買う。
名前は態度を言う: 飾らない、誇張しない、流行に飲まれない。拡張子 `.sober`。


## 一言で

値は流れ、構文は分岐せず、振る舞いはデータの外にある。

- if / switch / ブロック / forが式。全部が値を返す
- 多値は分解点まで流せる。`|>` と `_` で経路が一本の線になる
- メソッドなし、型クラスなし。interface = 関数値のstruct、impl = その定数。ディスパッチはただの引数
- constデフォルト。`mut` は `while` に隔離される
- comptimeなし。計算はコンパイラの外、道具（analyzer + fix）が言語に書き込む
- 全ブロックがregion。寿命はスコープの入れ子に一致し、GCも借用検査も要らない
- 色なしstackfulコルーチン + structured concurrency。並列スコープに渡せるのは不変値かチャネルだけ
- エフェクト・エラーラベルはanalyzerがcall graphから導出し、公開境界に宣言を強制する
- 非nullデフォルト。`nil` は `T?` にしか住めない

### 位置づけ（2026-09-17）

Rustの2保証（メモリ安全・データ競合自由）を借用検査なしで。加えてエラーとエフェクトの網羅。コンパイルはGo並み。拒否とfixがLLMの作業単位。

- Rustと同じ2つをregionと「並列スコープには不変値かチャネルのみ」で保証する（docs/formal.mdの証明対象）。ライフタイム注釈も所有権の学習曲線も無い
- Rustが捕まえない2種類を拒否する: エラーの取りこぼし（ラベル集合の網羅で `default: panic` と握り潰しが消える）、エフェクトの黙った変化（「いつからネットワークを叩くようになったか」がdiffとゲートに出る）
- コンパイル速度は構造で決まる: 関数内推論のみ、単相化なし、意味が最適化器に依存しない、パッケージ境界の宣言で解析が切れる。Rust比一桁を計測で示す
- 正直な弱点: 実行速度は辞書渡しの未特化部・Handleの世代チェック・region越境のコピーでRustに負ける場所がある。「書き換えたらn倍 / 1/n」は比較対象が要り、Zig製のゲームとGo製の自作ツール1本の移植で数字を取る
  - ベンチの題材: 代表は1BRC（io + string + mapのコンパイラ形ワークロード。温度は ×10固定小数点のint — float不要）。対照群はCLBGのbinary-trees（アロケータのストレステスト — GC / malloc / regionを比べる、regionが構造的に有利なはずの土俵）とfannkuch-redux。参照実装がGo / Rustに揃っていて比較の正当性に説明が要らない。計測開始は正規バックエンドへの切替後（B-9 — 2026-09-27に済み）。reverse-complement / k-nucleotideはbyte詰め表現の後、n-body等はfloatの後。副作用: 1文字1ワードの借金とbyte型の未決に期限圧力が掛かる — 例が仕様を引っ張る思想どおり
- 弱点の対: 制約の利点を取りにいく最適化方針（2026-09-19）。Soberの決定済み制約はGoにもRustにも無い最適化のライセンスで、これをガンガン取りにいく。いずれも「意味は最も単純な1規則、性能は最適化器」（決め方の型4手目）に収まりdebugビルドで飛ばせる。インベントリ:
  - 上界の事前計算系（スタック上界計算の横展開）: コルーチンスタックを上界ぴったりで確保（guard page・プローブ不要 — Phase 5計画済み）。region上界の静的計算 → scopeのスタック降格: ループ・可変長を含まないscopeはregionサイズがコンパイル時定数 — mmapでなくフレーム上の領域に降格して開閉ゼロコスト（フレーム定数 + 呼び出し深さの集計をそのまま流用）。世界が閉じるのでフレーム融合・ホットパスのsub rsp統合が全体最適でやれる
  - region / escape系: escapeが構文で決まる → escapeしないallocのスタック昇格が解析でなく読み取り（Goのescape analysisの保守的近似が要らない）。子regionにゴミが無ければ境界コピーはregionの付け替えに（1 region 1ビルダー規律の利点 — language.md 21節）
  - 不変性系: constキーのimm mapリテラル → コンパイル時実体化（perfect hash / ソート済み配列をrodataへ — コンパイラのキーワード表が最初の受益者）。freeze済みは並列読み同期不要。imm要素のコピー省略（22節）
  - エイリアス決定性系: 値ヘッダ + cap再利用なし + 先端規則で別名解析が構文レベルに決まりload / storeの並べ替え自由度が広い。mutはpar境界を越えない → フェンス・atomic不要が自明
  - クローズドワールド + 辞書系: 間接呼び出し候補がnominal関数型で閉じる → devirtualization / inline。`block` しない関数に検査点不要。fixが書いた辞書定数 → 選択的単相化を「意味論でなく最適化」としてやれる（単相化なしの決定と両立）
  - 検査除去 → panic-report（追加2026-09-27、language.md 27節）: panicフリーは文法の性質でなく検証済みプログラムの性質として狙う。mem-reportと同型の `panic-report` —「このバイナリに到達可能なpanic点はN個、場所はpath:line」をリンク時に出す。analyzerの範囲証明 → 検査除去（検査済み = 最適化ライセンス）の出口を性能だけでなく言明にも使う。組み込みターゲット（panicの受け皿未決）は「panic-report = 0を要求するターゲットプロファイル」で受けられる — 文法を変えずにpanicフリー保証が機械の言明になる。棄てた案: 文法からpanicを消す（refinement型・借用検査・エラーラベルの嘘のいずれかが代金で、どれも棄却済みの方向 —「到達 = バグ」を値の世界に漏らすと `@errors` の信号が濁る）
  - 売りの言語化（2026-09-19）: GC無しの利点は「少ない」より「予測可能」。GCヘッドルーム（Goは実質ライブヒープの約2倍）・オブジェクトヘッダ・断片化が構造的に無く、コルーチンスタックは上界ぴったり（Goの初期2KB + 成長機構と桁が違う — SoberSQLの接続あたりメモリに直結）。
    並行処理プールの言語化（2026-09-19。このセッション最大の収穫候補）: 正確な主張は「Goのプログラミングモデル（stackful・色なし）のまま、Rust async並みのフットプリント」。対Go — 上界ぴったり予約 + スタック成長機構そのものが不要なのでmorestackプロローグ（全呼び出しに乗るスタック検査）も消える: メモリと呼び出しコストの両取り。ワーカープールの典型タスク（閉じた小さいcall graph）は数百バイト級で、1Mタスク × 256B = 256MB vs Goの2GB+ — 1〜2桁大きいプールが現実になる。対Rust — Rust asyncもfutureはぴったりサイズ（コンパイル時状態機械）なので差は大きさでなくモデル: stacklessで関数に色が付く（async / Pin / Send境界）のに対し、Soberはstackfulのまま同じ数字を出す。但し書き: `@recursion` 宣言つき関数を呼ぶタスクは宣言深さ分を予約（呼ばないタスクは払わない — 上界はspawn点ごとのcall graphで決まる）、native FFIはシステムスタック切替の例外（wasm FFIはエンジン管理で例外にならない）。region上界の静的計算が進むと最悪メモリ使用量がリンク時に出せる領域が広がる → 将来機能 `sober build --mem-report`（スタック上界 + 静的region + 動的regionのscope一覧のコンパイル時予算レポート。GC言語には原理的に出せない数字）。但し書き: regionのゴミはscope出口まで滞留（倍々成長で2倍有界 — 「予測可能」はこの有界性込みの主張。無界候補はselfhost検証V2で実測）。
    対Rustの言語化（2026-09-19）: 「GC無し・省メモリ」自体はRustと同着（Rustは即時解放で定常RSSはむしろ勝つ場面がある）。Rustに無いのはGCでなく閉じた世界 — スタック上界には (a) 再帰が機構で縛られる（`@recursion`） (b) 間接呼び出し候補が閉じる（nominal関数型） (c) コンパイル時実行が無い、の3つが要り、Rustは再帰自由・`dyn` でcall graphが開くためembedded向けツール（cargo call-stack系）も近似止まり。Soberはこの計算のために言語を設計しているので「コンパイラが保証する数字」になる。もう1点は「既定がarenaで安全性は型が担保」（Rustのarenaはライブラリ + ライフタイム体操で既定でない）+ 解放O(1)（drop連鎖なし — 大きな木のteardownで差が出る）。主張の正確な形: 「世界が閉じている + regionが既定だから、メモリが予測可能。GC言語には出せず、Rustでは言語外の努力と近似になる数字を、コンパイラが保証として出す」— 対Goは消費量、対Rustは保証の形で差別化。
    対Rustの戦線 — 速度（LLVM不採用の利点）: 対Rustの主張は2本立て — メモリは上の「保証の形」、速度は「LLVMが原理的に持てない知識 + コンパイル速度」。命令選択・レジスタ割り当て・自動ベクトル化の質ではLLVMに挑まない（μカーネルのピーク性能では戦わない）。勝ち筋は ① 証明による検査除去（analyzerの範囲証明 + 検査済み = 最適化ライセンス。消えたこと自体がpanic-reportの言明になる — Rustの境界検査除去はヒューリスティック）② regionの構造的知識（enter / alloc / leaveの対が構文で見える → スタック降格。bumpでは確保順 = メモリ順で走査の局所性が構造的に良い — binary-treesでmalloc版に勝ち得る根拠）③ 閉世界の完全devirt（間接呼び出し候補が常に既知 — trait object / dylibで閉じきれないRust LTOとの差）④ エフェクトの導出による合法なCSE / hoist ⑤ コンパイル速度を性能主張に含める（LLMの作業ループではビルド速度 = エージェントの反復速度 — Rustの最弱点で最も確実な戦場）⑥ 速度の予測可能性（下の段落）。既存の決定の延長で、新しい賭けは増やさない
    Webサーバ / アプリへの言語化（2026-09-20追記）: Apacheのapr_pool・nginxのngx_pool_t（リクエスト / 接続単位のpool + 一括解放）は「1リクエスト = 1 scope = 1 region、出口でO(1) teardown」と同型 — 高性能サーバがCの規約と職人芸で守る割り当て構造が、普通にハンドラを書くだけの既定意味論。主張の正確な形は「nginx並みの性能」（throughputはio実装品質の変数）でなく「nginxの割り当てアーキテクチャが既定」で、対Goの実利はGC pauseゼロのテールレイテンシ + 接続あたりメモリ（消費量の言語化にテール予測性を足す）。IO未決を (c) thread-per-coreに決めるとnginxのワーカーモデルそのものになり、割り当て構造だけでなくアーキテクチャ全体が端から端まで一致する（ワーカー固定と最も親和する候補でもある — 主張の強度がioの決定に連動する点をここに記録）。
    組み込みへの延長（2026-09-19）: 他言語の組み込み対応は本体からの引き算（Rustのno_std、C++ freestanding）で、引き算はエコシステムを二重世界に分ける。Soberは引くものが最初から無い（GC無し・libc非依存・syscall最小・静的単一バイナリ・スタック上界・regionが本体の意味論）ので、エコシステム全体が自動的に組み込み対応 — 主張は「組み込みが本命」でなく「サブセット無しで上（サーバ）から下（MCU）まで同じ言語」。mem-reportはMCUでは保証から必需品に格上げされ、regionは「mmap遅延ページ → 固定予算の静的アリーナ」の差し替えで意味論が変わらない。但し書き（現設計で組み込みに反する点）: チャネルの無限バッファ（メモリ無界 — 有界変種の未決をlanguage.mdに積んだ）、MMIO / volatile / 割り込み（`@layout` の延長線、未設計）、panicの受け皿、ターゲット（ARM / RISC-VはPhase 6）
    速度の予測可能性— mem-reportと同型の軸: 最速ではなく「速度が言明できる」で戦う。GC言語はpauseとheadroomでtail latencyが読めず、Rustですら最適化のヒューリスティック崖（境界検査が消えるかは書き方とLLVMの版次第）がある。Soberは「意味は最適化器に依存しない」+「検査済み = 最適化ライセンス」の2段階で、どの検査がなぜ消えたかが証明の帰結として言える — 崖がヒューリスティックでなく決定になる。出口は `perf-report` 構想（時間版mem-report。決定的スケジューラ・スタック上界・region上界と合成し「最大N KB・検査ゼロ・pauseゼロ」を言明）。一等地は組み込み（WCET）とSoberSQL（p99）。3本のレポート: mem-report（空間）・panic-report（失敗）・perf-report（時間）。キャッチコピー候補: 「サプライズは全部コンパイル時に、実行時はつまらない」 — Soberの名の由来として
- 第3の軸が本命: analyzerの拒否とfixがLLMの作業単位になっている。エージェントが書くコードでは、借用検査より網羅検査の方がバグ削減のnが大きく出るはず

## 非目標（強みの双対。2026-09-19）

向いていないユースケースはほぼ全部、強みと同じ制約の裏面として導出できる。機能要望をここで切る:

1. 動的性が主役のソフト（閉じた世界の裏面）: プラグイン、dlopen、JIT、ホットリロード常用、REPL的探索。スタック上界・DCE完全・mem-reportは全部「リンク時に世界が閉じる」に依存し、開けた瞬間に売りが全滅する。wasm FFIは檻つきの部分緩和まで。「世界はリンク時に閉じる」は決定2026-09-27（language.md 29節） — プラットフォーム境界のdylib（GPUドライバ・macOS libSystem・Windows system DLL等）は `@native` FFIの実装詳細であってリンクモデルの例外ではない（決定。動的リンクの強いユースケースを棚卸しした結果、残るのはOS / ドライバ境界だけで、FFIの枠に閉じられる）
2. 寿命が構文に従わないメモリパターン（region = LIFOの裏面）: 相互参照が絡む長寿命の可変オブジェクトグラフ — GUIのリテインドツリー + オブザーバ、undoグラフ、イベント駆動の寿命。GC言語の本領。Handle / Poolのはしごで書けるが「Goの見た目」から遠ざかる
3. 数値計算・HPC・ML（単相化なし + 演算子を開かない、の裏面）: 辞書渡しの未特化と演算子閉鎖で、エルゴノミクスと性能の両方が弱い。GPUはPlace経由でカーネルは別世界。非目標と明言する
4. アロケータ職人芸の極限系（regionが既定意味論、の裏面）: HFT・AAAエンジン級の自前アロケータ・レイアウト職人芸。Zig / Rustの領分で競合しない

1〜4は意味論に根差した本質的な不向き。以下2つは賭けの裏面（覆る可能性を残す）:

5. 雑に書いて捨てる探索コーディング: 宣言強制・網羅検査は「後で直すから今は雑に」と正面衝突。ただしfixが「雑に書く → 機械が仕上げる」を成立させるなら思想ごと逆転する（第3の軸の賭けそのもの）
   - 脱出口の構想（2026-09-19）: Dynamic Sober — Sober埋め込み専用の動的方言。既存設計に受け口が2つ空いている: (a) `Value` 型（language.md 16節）が相互運用契約そのもの —「全部の値が `Value` であるSober」と定義でき、境界の隔離と `shape[T]` 変換は決定済み (b) 閉じた世界と矛盾しない — インタプリタ（Sober製）にとってスクリプトはコードでなくデータで、region / Poolの固定予算を与えればメモリ予算つきスクリプティング（mem-reportがスクリプト込みで成立）。先例はLuaよりStarlark/Go（決定的・hermetic・ロード後freeze — freeze意味論ごと繋がる）。ホスト言語と同じ構文（Goの見た目）なのでLua埋め込みの二言語コスト（別構文・別データモデル・スタックAPI）を払わない。LLM時代の筋 = 段階的硬化: 型を省いて書く → fixが型を書き込んで静的Soberへ昇格（本項の賭けの実行路）。
     核の主張（2026-09-19追記）: 振る舞いは動的、検査は静的。analyzer層は最初から型に依存しない設計（エフェクト導出・エラーラベル・acquire/releaseは構文とデータフローの解析 — 12節の層の線引き）なので、全値 `Value` の方言にそのまま掛かる: 動的スクリプトに対して「ioを叩かない」「ラベル網羅に穴」「releaseが無い」が静的に言え、境界は `shape[T]` 契約の静的照合（sqlshapeが動的なSQLに静的判定を下すのと同じ姿勢）。ホストのregion予算と合わせて「動的スクリプトなのにメモリ予算とエフェクトが静的保証」— 既存動的言語の「後から型を貼る」（mypy / TypeScript）と別の軸で、段階的硬化は「検査は最初から静的、型付けは最後の仕上げ」という勾配になる（入場料が型でなくなる）。同梱analyzerによるロード時検証（2026-09-19追記）: 静的部分の情報（公開APIのshape / エフェクト / ラベル宣言 — モジュール未決 (2) のinterfaceメタデータと同じ成果物）とanalyzerをホストバイナリに同梱し、実行時にロードされるスクリプトを走らせる前に検証する — eBPF検証器の同型・言語統合版。ホストは受け入れポリシーを自分のエフェクト語彙で書く（「このプラグインのインターフェースはio禁止・メモリ1MB」）。静的単一バイナリなので同梱に動的リンク問題が無くDCEで使う検査だけ残る。mem-reportと合成すればスクリプトの予算適合もロード時判定。検証器の判定はセキュリティ境界になる（eBPF verifierと同じ構図）ので、Lean検証済みチェッカーの規律をアドミッション検証器の証明へ延長する含み。fixはロード時に使えない（拒否専用モード。fixは開発時の道具のまま）。題材の第一候補はビルドスクリプト（2026-09-19追記）: Starlarkの本家用途に戻る形で、同梱analyzerが本領を発揮する — hermeticity（ビルドキャッシュ未決の必要条件）をエフェクト検査で機械化（「時刻・環境変数・ネットワークを読まない」をロード時に拒否で保証 → スクリプト拡張を入れてもキャッシュキーが壊れない。Bazelが規約とsandboxで守るものを言語機構で守る）。ドッグフーディングの時期もビルドシステム整備（selfhost前後の本線）と噛み合い、SoberSQLストアドより繰り上がる。線引き: 既定は宣言的最小（go.mod相当 — 決定14と同じ思想）を保ち、Dynamic Soberは拡張が要る側（コード生成・アセット埋め込み・カスタムステップ)の受け皿に限定 — ビルド設定のTuring泥沼化はエフェクトゲートで塞ぐ。
     動機の言語化: 「ビルド = 実行なのにコンパイルが挟まる」違和感（Gradle .kts）への構造的な答え。.ktsは「安全性 = 型 = コンパイル」の等式に縛られconfigurationのコンパイルコストを払い、Groovyは即時性に寄せて検査ゼロ — 二択に見えるのは型検査がゲートだから。検査をanalyzerに分離済み（12節）のSoberでは両立する: 解釈実行は即時（スクリプトはデータのまま走る）、静的保証はanalyzerパス（構文 + データフローで型検査より桁違いに軽い）、判定は内容ハッシュでキャッシュ可能 — ビルドキャッシュのCASがビルド設定自身の検証結果もキャッシュする（Gradleがconfiguration cacheを後付けで苦労する部分が構造から出る）。他の顧客候補: SoberSQLのストアドプロシージャ、非目標1のプラグイン檻
6. Cエコシステムの海に乗る開発（完結の賭けの裏面）: GUIツールキット・OS API密結合。wasm檻経由のFFIでは借り物中心の開発はコスト高 — 引き受け済みのコスト

## 審査基準

やっていることが、そのまま書いてある — 素直に書けない機能は言語に入れない。analyzerに振るか、捨てる。（2026-09-19改訂。旧: 「Goの見た目で書けないなら入れない」— Go自体がおおむね素直なので代理指標として機能したが、逸脱の記録を見るとcap再利用・map参照ヘッダ・`v, ok :=` など「Goの形が意味に対して素直でない場所」では毎回Go側を棄てていた。本体の基準はこちら。「Goの見た目」は近似として引き続き有用）

倹約は美徳でなく構造材（2026-10-04に抽出 — 性能投資とフロントエンド接合の壁打ちで、継いだ倹約に力学的な意義が三つ立った）: ①最適化の自由度の源泉 — 書かれていない機構は選び直せる・約束していない観測面は保存義務がない（倹約 = コンパイラに残される自由の量。実証 = scanbは素直なバイトループにだけ挿せた・M12の手の語化は半分不採用）②約束の表面積の最小化 — 一級の意味論は撤回不能（Rubyのopen classがJITに永遠のガードのオーバーヘッドを課す型の罠）。糖衣は撤回可能なので、新機能は糖衣でインキュベートし、コアへの昇格に定理の証明を課す ③接合の変換先の資格 — 構文皮も別言語のフロントエンドも「Soberに落ちる」ことで検証と性能を相続する。落ちる先は小さく意味が確定しているほど良い — 倹約なコアだけがコンパイルターゲットの母艦になれる（LLVMがIRの倹約さで百言語の母艦になったのと同型・ただし相続させる財産に型と検証が含まれる）。

意味を持つものはソースにある。隠れてよいのは意味を持たない機械的なものだけ（2026-09-18に抽出。それまでの決定から自然に立っていた第2の基準）。生成コードはfixがソースに書く / 注釈は拒否しか起こさない / `shape[T]` は式で参照した分だけ出てグローバルな型テーブルを持たない / 名前対応は注釈ではなく `Rename` 辞書 / comptime・AST埋め込み・巻き戻し器・シグナルプリエンプション・GCは棄却、が全部この一つの帰結。隠れていてよいのは `Layout[T]` の暗黙渡し、deferの展開、regionのpush / pop、スタック切替、最適化器の特化のように、出力を理解するために読者が知る必要のないもの。理由は「LLMの作業単位」: ソースに無いものはLLMにも読者にもanalyzerにも見えず、3者が同じものを見ている状態を保つ。「暗黙に渡せば楽」という案が出たら、渡すものが意味を持つかどうかで裁く。

条件付きの制約を可能な限り排除する（2026-10-31ユーザー発意 — ビルド時DIの設計提案で「チャネルの端点は関数境界を越えない」「mut仮引数の関数は再帰できない」級の制約に立て続けに当たった壁打ちから）。「Aの場合はBできない」という形の規則は、仕様の表面積を機能数の積で増やす: 読者（人もLLMも）は機能単体でなく組み合わせの行列を覚えることになり、直交に書いたつもりのコードが組み合わせの角で拒否される。新しい機能や制約を入れるときは、(1) 条件なしで成立する形に直せないか（Bを常に許すか、Aを丸ごと入れないか）(2) 組み合わせ自体が構文上生じない形に再構成できないか、を先に探す。どうしても残る条件付きの制約は、健全性か決定性の定理に紐づくものだけにし、拒否の文面が「なぜその組み合わせが成立しないか」を言えること。既存の条件付き制約はこの基準の負債台帳として扱い、二分する: (a) 定理に紐づくもの（端点の境界 = SPSCの所有・mutの再帰 = 展開の停止 — 外すには再証明が要る）と (b) 実装の未達がそのまま規則の顔をしているもの（`mut map` のフィールドのCoreFragment・文面のない拒否など — ユーザー指摘2026-10-31「実装が追い付いてなくてそうなってるところが結構ある」）。(b) は制約でなく未実装として明示し、仕様の顔をさせない（docsに書くときは「今は」を付けて台帳に積む）。外せる機会（定理の再証明・表現の差し替え・実装の追いつき）が来たら外す側に寄せる。

規律を構造へ（2026-11-06 — importのタスクの設計提案から）。Goは構造の穴を規律で塞いだ（「packageは特徴的に名付けよ」「clientというpackageを作るな」「短く」）— モノレポとレビューの文化の中では働くが、規律の及ばないエコシステムの規模で穴が露出した（`s3types`・`metav1`・`httputil`）。Soberは規律を構造に翻訳する: 名前は構造から導く（修飾子 = importパスの全要素）・出所の格納場所は文法が決める（sober.mod — ソースに漏れない）・規則は検査できる形にする（packageパスの要素は小文字の識別子）。規律として残すのは、違反のコストが違反者自身に即時に返るものだけ（「浅く書け」— 深くすると自分の全使用行の綴りが長くなる）。メソッドが無いことがこの連鎖の根にある: メソッドが無い → packageが唯一の名前空間 → 参照の綴りが全荷重を受けられる → `.` の連鎖の意味が位置で一意（呼び出しの行が型の情報なしで静的に読める）。詳細とGoとの対照の表 = language.md 20節。

未決を片付けるときの手順。この日の決定（キャンセル、escape、スタック上界、エフェクト宣言、辞書解決、ジェネリクス、FFI、`@export`、Place越境）は全部この5手で済み、新しい型規則は一つも要らなかった。

1. 問いを層に分ける。コンパイラ（健全性）、analyzer（拒否と提案）、最適化器（見えない変換）、stdのどこの仕事かを先に決める。キャンセルは「配達と巻き戻し」、escapeは「意味論と最適化」に分かれた
2. 意味論は最も単純な1規則にする。「region境界越えはコピー」「切られたtaskは検査点で止まる（キャンセルは値にならない — 2026-10-05改訂。旧「`Cancelled` は `block` エフェクトのエラー面」）」「注釈は導出集合の上界」。例外や場合分けを意味論に持たない
3. エルゴノミクスはfixに振る。辞書の暗黙の解決なし、`Value` からの変換関数、Cヘッダ、stagingへの書き換え。人が打つ量を減らす手段は「言語が推論する」ではなく「道具がソースに書き込む」。生成物はビルド時の別物ではなく、レビューを通ったソース
4. 性能は最適化器に振り、意味に触れさせない。単相化、割り当て点の再標的、`get` の分岐消去。意味が最適化器に依存しないのでdebugビルドは最適化器を飛ばせる
5. 新しい型規則が要ると感じたら、設計の穴の信号。既存規則の組み合わせで済まないか先に探す。acquireのピン済み参照も「regionの狭め替え」で済んだ

運用: 決定を書くときは棄てた案を一行残す（後で同じ案を再検討する時間が消える）。決定がdocsのどの節に依存するかを併記する。

ランタイムに無いもの（それぞれ設計上の理由で消えた）: GC（→ region）、シグナルによる非同期プリエンプション（→ バックエッジの検査点。ランタイムはフラグを持つだけ）、パニックの巻き戻し器（→ エラーは値で `?`、deferはスコープ出口にインライン展開）、型情報テーブルとリフレクション（→ `Layout[T]` と `Shape[T]` は参照された型の分だけ出る静的データ。language.md 16節）、releaseのガードページ（→ スタック上界のリンク時計算）、netpoller（→ stdのioとExecutor）。リフレクションが無いのでリンク時のdead code eliminationが完全に効き、stdを厚くしてもバイナリは使った分だけ。SoberSQLをCライブラリとして組み込むときにランタイム込みで小さく収まる根拠。

## 実装計画

- Phase 0: （オラクル: parse → print → parseの不動点、命令エンコーダは `llvm-mc` と比較。docs/oracles.md）Zig基盤 — comptime PEGパーサージェネレータ（peg.zig）、lexer、CST→AST、AST↔JSON、x86_64 + ELF直接生成、`build / parse / codegen` 分離。文法（grammar.zig）とAST（ast.zig）はGo皮に作り直し
- Phase 1: （オラクル: `-O0` との差分実行。Lean評価器が出来たらそれとも）fibが動く — if / switch式、struct、`union`、`|>` と `_`、多値の分解、`for ... yield`、`defer`、ラムダ
  - 2026-09-18完了（`for ... yield` を除く）。`-O0` との差分実行は比較対象が無いので `examples/*.out` の期待値で代用。`for ... yield` はPhase 2へ送った: 価値は `Iter[T]` と `|> map |> collect` の合成にあり、型もジェネリクスも無いPhase 1でint専用の脱糖を書いても作り直しになる。ラムダのinline展開機構はPhase 1で出来ているので、型が付いた時点でその上に載せる。Phase 1の副産物: int / struct / unionだけの最小の型表（Phase 2のLean型検査器が正になったら、Zig側は脱糖とレイアウトだけを残す）
- Featherweight Sober（Phase 1と並行可）: docs/formal.md。型検査の規則を証明済みにしてからPhase 2に入る
- Phase 2: （オラクル: Lean型検査器・評価器、regionのpoison）型検査 — 関数内推論 + 双方向型検査、`T?` flow typing、regionのescape規則、並列スコープの不変値制約、ゼロ値 / definite initialization。型検査器はLeanで書き、別プロセスとして接続する（Zigは脱糖後のコアASTをJSONで渡す）。Zig再実装は後で、Lean実装を差分テストのオラクルにして行う（docs/formal.md「実装との照合」）
- Phase 3: （オラクル: Pool未返却カウンタ）std — Handle / Place / Pool / Iter。region-domain-pool.mdの1〜4節がここで検証される
- Phase 4: （オラクル: 計装ランタイムで観測 ⊆ 導出、fuzzでラベル観測）analyzer第1本 — acquire/releaseの局所照合（call graph不要）。続いてエフェクト導出、errorラベル導出、公開境界の宣言強制 + fix
- Phase 5: （オラクル: Leanトレース照合、TLA+、スタック高水位 ≤ 上界）コルーチン + structured concurrency、`parallel scope`、チャネル。スタック上界のリンク時計算と再帰SCCの深さカウンタ（language.md 11節）はここで入れ、コルーチンのスタックは上界どおりにregionから取る。3段階に分ける。マルチスレッドは5bで入る（5aは内部マイルストーン）
