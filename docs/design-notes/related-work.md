# 設計ノート: 先行研究 — Sober は何を継ぎ、何を変えたか

Sober の機構の多くには先行する研究や言語があります。この文書は機構ごとに「何を継いだか」「何を変えたか」を並べます。主張の範囲をはっきりさせるのが目的です — 個々の部品の多くには先行する研究があり、Sober に新しいのは、それらを組み合わせ、どれにも条件を付けずに保証する形で揃えたことです。

## 読み方

言語の歴史は、プログラムに観測を許す範囲を広げてきた歴史としても読めます。C は番地とメモリの並びを、Java はオブジェクトの同一性と monitor を見せ、一度見せた観測は使う人が現れた時点で取り下げられない約束になりました。Sober は、観測は道具の側（`task.Ledger()`・`--mem-report`・決定的な再生）に置き、意味論の観測の面は裁定した点だけに保ちます。下の表の「変えたこと」の多くは、この分け方から来ています。

もう 1 つの読み方は、元の形がなぜ広く使われなかったかです。

> 「良いアイディアの墓場は文脈に殺された形の鉱脈 — 掘る前に『殺した文脈はうちの前提で消えているか』を一問」

止めた文脈は、だいたい 3 つに分かれます — 全プログラムの解析が高い・開いた世界（動的リンク・FFI）との衝突・正しさを確かめる道具の不在。Sober の前提（世界はリンク時に閉じる・libc に依らない・オラクルと Lean の照合の密度）は、この 3 つを消す側にあります。各表の最後の列はその一問の答えです。今も広く使われている形については、その形の制約と、Sober でそれが消える理由を書きます。

## 1. メモリ — region

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| Tofte と Talpin の region 推論（ML Kit — 1994） | 値の寿命を region の入れ子で管理し、GC を使わない | region を推論しない。寿命は構文（スコープの入れ子 — ブロックごとに 1 つの region）から決まる。外の region へ出る値は境界で写す（`copyTo` — Lean で証明つきの明示の項） | 制約: 推論の結果が読めない（どこで解放されるかがプログラムの形から予測できない）。Sober は推論しないので、解放の位置はソースの形そのもの |
| Cyclone（Grossman ほか、PLDI 2002） | region を型に載せて、逃げる参照を静的に拒む | region の注釈と region 多相（∀ρ）を持たない（language.md 31 節で採らないと裁定 — 再訪の条件つき）。書けない形はコンパイルエラーになるだけ | 制約: region の注釈の重さが利用者に乗る。Sober は注釈ゼロを保つ代わりに、関数の境界の写しと上界の規則で受ける |
| Rust の所有と借用（同時代の設計 — 元になったものではない） | データ競合なしとメモリ安全を、実行時の GC なしで静的に | 寿命の注釈・借用の規則が無い。並列に渡せるのは不変の値とチャネルだけ | 制約: 寿命の注釈と借用の規則を利用者が学ぶ。Sober は書ける形を絞って規則ごと消す（比較の本体は [安全性の設計ノート](safe.md)） |

## 2. 共有状態 — domain

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| monitor（Hoare、CACM 1974。Brinch Hansen も同時期） | 状態と、それを触る手続きの直列化を 1 か所にまとめる | 本体は待たない・io なし・別の domain を呼べない。持ったまま待つ形が無いので、lock の順序のデッドロックは書けない。入る順は「録られる入力」 | 制約: 中の非決定と入れ子の wait。Sober は本体に課す制限（待たない・io なし）でどちらも書けなくし、順を入力として定理の中に入れた |
| Mutex（lock） | 直列化 | lock を値として見せない。直列化を「コードの領域の印」（critical section）でなく「データの宣言」にする。Lock の約束は「正しく取れば原子的」という条件付きで、守るのは利用者の規律 — domain は形で守る | 制約: lock の取り忘れ・順序・持ったままの待ちが利用者の規律に残る。domain は lock を見せず、本体が待たないので 3 つとも書けない |
| actor（Hewitt・Bishop・Steiger 1973・Erlang） | 状態を 1 つの持ち主に閉じ込めて、外からはメッセージで触る | 持ち主の task・返事の札・振り分けのループを持たない（language.md 11 節の棄てた案 A）。呼び手の task の上で本体を走らせるのが既定で、どこで走るかは観測できない | 制約: 返事の札という新しい同一性の値・持ち主の生死の約束・要求ごとの task の切り替え。domain は持ち主を持たないので、どれも要らない |
| CSP（Hoare、CACM 1978）・occam のチャネル | 共有せずに値を渡す | チャネルは送り手 1・受け手 1 に限り、到着の順を構造で消す。多対一の合流は domain が受け持つ | 制約: 多くの送り手から 1 つの状態への合流は、select か共有なしには書けない。Sober は select を入れず、合流を domain に分けた |

> 「本当に競合が要る部分は、ユーザーがそれを調停するコードを書くことを強制される」

暗黙の競合が書けないので、競合点は domain とチャネルを宣言した場所に限られ、grep で全部見つかります。

## 3. 決定性

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| Kahn のプロセスネットワーク（Kahn、IFIP 1974） | チャネルで繋いだ決定的な計算の結果は、スケジュールに依らない | Lean で証明した（formal.md 定理 2 ②）。domain の入る順をオラクルの入力として足し、「どのオラクルを固定しても」スケジュールに依らない形に拡張した。select（poll）は入れない — Kahn の定理を壊すのは「いま届いているか」の観測だから | 制約: 共有の状態が書けない。順を入力にすれば共有も定理の中に入る |
| 決定的な並列（Deterministic Parallel Java — Bocchino ほか、OOPSLA 2009・LVars — Kuper と Newton、FHPC 2013） | 並列の結果を既定で決定的にする | 効果の注釈を書かせない（imm が既定・mut は一意・並列に渡せるのは不変の値）。出力はワーカーの数に依らず同じバイト列 | 制約: 効果の注釈の負担。Sober は書ける形の側で受ける |
| DPOR（Flanagan と Godefroid、POPL 2005） | スケジュールの空間を、結果を変えうる順だけに絞って調べる | 検証の道具の側に置く（schedfuzz・SOBER_SCHED_SEED）。意味論が決定的なので、探索が要るのは実装の検証だけ | 制約: 探索の空間が大きい。利用者のプログラムの結果は順に依らないので、探索は rt と compiler の検証に限られる |

## 4. 効果

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| effect system（Lucassen と Gifford、POPL 1988） | 関数が何をしうるか（io・alloc・panic・非決定・待ち）を型と同じく静的に追う | 利用者は効果を書かない。analyzer が呼び出しのグラフから導き、公開の境界だけ宣言（`@effects` / `@errors`）を照合する。宣言は `sober fix` が書き込む | 制約: 注釈の量と、開いた世界での推論の限界。世界がリンク時に閉じているので、全プログラムから導けば足りる |
| 検査例外（Java） | 起こりうる誤りを署名に出す | error はラベルの集合で、analyzer が導く。取りこぼしは拒否。panic とは別 | 制約: 宣言を全部手で書く。Sober は導いて、公開の境界だけ照合する |

## 5. テストの差し替え — ビルド時 DI

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| リンクシーム（Feathers『Working Effectively with Legacy Code』2004） | 本番のコードに手を入れず、ビルドの段で依存の解決先を付け替える | テストのビルドの中だけで package を丸ごと double に差し替える（`@doubles`）。署名・型・効果・`@errors` を本物の宣言と照合する | 制約: 契約の検査が無く、代役が本物とずれても気づけない。Sober は loader が照合する |
| 実行時の DI（interface・コンテナ・注入） | 依存を外から与える | interface を持たないので、実行時の差し替えの層が無い。本番のビルドは double を読まない | 制約: どの実装が使われるかが実行時の配線で決まり、ソースから追えない。Sober の差し替えはビルドの中だけで、本番の配線は無い |

## 6. float — ビット決定性

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| IEEE 754 binary64 | 値・丸め・比較・特殊値の定義 | 型は `float` の 1 本（幅を名前に刻まない — 先例は JS の number）。演算と印字をビット決定的に揃え、libm を持たない（基本演算と sqrt） | 制約: 幅の混在と libm の実装差で、同じ式の結果が機械ごとに割れうる。Sober は型 1 本と libm なしで割れる源を持たない |
| 最短の往復表現の印字（Steele と White 1990・Burger と Dybvig、PLDI 1996） | 読み戻すと同じビットになる最短の 10 進 | Burger と Dybvig の free-format を整数だけの多倍長で実装（std/floatfmt）。綴りは Go の `strconv.FormatFloat(f, 'g', -1, 64)` と同じ | 制約: 多倍長の算術が要る。Sober は std の中の整数だけの多倍長で持ち、libc に依らない |

## 7. structured concurrency

| 元になった研究・言語 | 継いだこと | 変えたこと | 元の形の制約と、Sober でそれが消える理由 |
|---|---|---|---|
| structured concurrency（Sústrik のブログ "Structured Concurrency" 2016・Smith "Notes on structured concurrency, or: Go statement considered harmful" 2018 — Trio） | 子の task の寿命を scope の入れ子に閉じる | scope の寿命を region と同じ入れ子に揃えた（task の結果は scope の region へ写す）。Join が死を見ても scope を打ち切らない（Trio の nursery の顔は棄てた — 字面に出ない脱出になる）。キャンセルは例外でなく期限と io の口の `Expired` | 制約: 子の失敗を例外で scope へ伝える形は、字面に出ない脱出になる。Sober は死を値（`Try` の Outcome・scope の err）で見る |
| 緑スレッド・M:N（Rust は 1.0 の前に RFC 230〔2014〕で手放した） | 軽い task を少数の OS スレッドで回す | io_uring の上の M:N。libc を使わない | 制約: FFI と C のスタックとの衝突。libc に依らないので衝突の源ごと無い |

## まとめ

部品の多くには元になった研究や言語があります。Sober に新しいのは、それらを組み合わせたことと、言語が利用者に保証することのどれにも条件を付けないことです — 「正しく使えば安全」でなく「書ける形は安全」。並列のモデルでは、時間で守る（lock）から形で守る（不変の値・一意の mut・domain）への反転として現れます。

Sober の並列処理は、lock を使うモデルとは根本的に違うモデルです。利用者から見える違いは 3 つです。利用者のソースに lock・mutex・atomic は現れません（std の公開の口にもありません）。並列に渡せるのは不変の値とチャネルで、共有して書く状態は domain の宣言を通してだけ書けます。利用者が並列について守る不変条件として残るのは、値の寿命（region — スコープの入れ子）だけで、それも検査が見ます。設計の向きは lock のモデルと 3 点で逆です — 「正しく使えば安全」でなく「書ける形は安全」、時間の調停（いつ触ってよいか）でなく構造の調停（誰が値を持つか）、非決定を排除するのでなく記録して再生できる入力として扱うこと。
