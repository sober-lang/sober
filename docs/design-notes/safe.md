# 設計ノート: 安全

[README の柱「安全」](../../README.ja.md#安全) と [DESIGN 1. region](../../DESIGN.ja.md#1-region--寿命はスコープの入れ子に一致する)・[3. 閉世界](../../DESIGN.ja.md#3-閉世界と観測不能性--世界はリンク時に閉じる) の「なぜ」。

## GC も借用検査も無しで、なぜメモリ安全なのか

答え: 値の寿命をスコープの入れ子に一致させているからです。全部のブロックが region（割り当ての領域）で、ブロックを出ると、そこで作った値はまとめて解放されます。スコープの外へ出る値（戻り値・外の束縛への代入）は、外の region へ写されます。外の region が中の region を指すことが起きないので、解放済みの領域を指す参照（ダングリング）が作れません。

棄てた案: GC（停止とヘッドルームの代価・制御が裏口に追いやられる）・借用検査（寿命の注釈と所有権の学習の代価）。

関連: [言語仕様 11 節・21 節](../language.md)・[region / Domain / Pool](../region-domain-pool.md)

## 寿命の注釈が要らないのはなぜか

答え: 寿命が構文（スコープの入れ子）から決まるので、書き手が寿命を宣言する必要が無いからです。代わりに「書けない形」があります: 寿命が構文に従わない参照（スコープを越えて共有される可変な値）は、そもそも表せません。書けない形はコンパイルエラーになり、その形は写す・不変にする・チャネルで渡すのどれかに書き換えます。

関連: [言語仕様 21 節・31 節](../language.md)

## データ競合が起きないのはなぜか

答え: 並列のスコープ（`task.Run` の子・`task.Map` の要素の task）へ渡せるのが、不変の値（`freeze` したもの・不変の束縛）とチャネルだけだからです。`mut` の値は task の境界を越えません。チャネルの送り端・受け端は 1 つの task だけが所有し、子へ渡すと親からは使えなくなります。`freeze` できるのは他に別名の無い値だけで、`freeze` の後は元の変数から書けません（コンパイラが確かめます）。共有された可変の状態が無いので、データ競合は書けません。

関連: [言語仕様 11 節・18 節](../language.md)・[ツアー 7 節](../guide/tour.ja.md#7-並列--structured-concurrencyチャネル)

## その安全性はどこまで証明されているのか

答え: 言語のコアを形式化したモデル（Featherweight Sober）を Lean 4 で書き、領域の安全・データ競合自由・型の健全性と、並列の出力の決定性（Kahn のネットワークとしての合流性）を証明しています（`lean/`）。証明されているのは体系（モデル）の性質で、コンパイラの実装の性質そのものではありません。実装との距離は、コンパイラの型検査器と Lean の検査器の判定を大量の入力で突き合わせる照合（検証の網の一部）で縮めています。

関連: [形式化](../formal.md)・[オラクル](../oracles.md)

## エラーの取りこぼしをどう拒否するのか

答え: エラーはラベル（`type NotFound error`）で、関数は `(T, error?)` で返します。解析器が呼び出しのグラフからラベルの集合を導き、`switch err` の扱い漏れを拒否します。公開の関数は返しうるラベルを宣言し、package の境界では宣言と導出が照合されます。結果として、`default: panic` や握りつぶしで済ませる書き方が要らなくなります。

棄てた案: 例外（どの呼び出しが投げるかがソースに見えない）・Go の `error` interface（何が返るかが型に出ず、網羅を確かめられない）・行多相（OCaml の多相バリアント・Koka のエフェクト行 — 型の面が大きくなる）。

関連: [言語仕様 13 節](../language.md)・[ツアー 5 節](../guide/tour.ja.md#5-エラー--ラベルcatchswitch)

## panic はいつ起きるのか

答え: 2 種類だけです。1 つは「健全性の防衛」で、続けると安全性が破れるもの（不変にした値への書き込み・領域の上限の超過など）。もう 1 つは「到達 = バグ」で、範囲外の添字・明示の `panic(L{…})` のように、正しいプログラムでは届かないもの。失敗しうる普通の処理（ファイルが無い・入力が壊れている）は panic でなくエラーのラベルで返します。panic は理由（ラベル）と位置（ファイル:行:列）を出して終了します。

関連: [言語仕様 27 節](../language.md)

## なぜ select が無いのか

答え: 「いま届いているか」を観測する select（ポーリング）を入れると、並列の出力の決定性（ワーカー数やスケジュールに依らず同じ出力）が成り立たなくなるからです。優先度の制御はキャンセルと scope の構造で、複数の入力の合流はチャネルの設計で表します。

関連: [言語仕様 11 節](../language.md)

## なぜ再帰的な型（自分を含む struct・木）を宣言できないのか

答え: 今のコアの型に再帰型が無いためです。木は「平らな表 + 番号」で持ちます（コンパイラ自身の構文木も、std/json の文書もこの形です）。region の上では、ポインタで繋いだ木より平らな表の方が、写しも解放も単純になります。再帰型をコアに足すことは、形式化の側で席を用意してあります。

関連: [言語仕様 1 節](../language.md)

## 子の task が死んだら（panic したら）どうなるのか

答え: 死は値でなく構造で伝わります。`task.Run` の子が死ぬと、scope は出口で失敗（`ChildDied`）になり、親が受け取ります。`task.Try` で死を早く知ることはできますが、死を吸収して何もなかったことにはできません。死んだ task の壊れた途中の状態で利用者のコードを走らせないため、死んだ task の後始末（defer）は走りません。

関連: [言語仕様 11 節](../language.md)
