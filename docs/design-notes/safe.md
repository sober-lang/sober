# 設計ノート: 安全

[READMEの柱「安全」](../../README.ja.md#安全) と [DESIGN 1. region](../../DESIGN.ja.md#1-region--寿命はスコープの入れ子に一致する)・[3. 閉世界](../../DESIGN.ja.md#3-閉世界と観測不能性--世界はリンク時に閉じる) の「なぜ」。

## GCも借用検査も無しで、なぜメモリ安全なのか

答え: 値の寿命をスコープの入れ子に一致させているからです。全部のブロックがregion（割り当ての領域）で、ブロックを出ると、そこで作った値はまとめて解放されます。スコープの外へ出る値（戻り値・外の束縛への代入）は、外のregionへコピーされます。外のregionが中のregionを指すことが起きないので、解放済みの領域を指す参照（ダングリング）が作れません。

棄てた案: GC（停止とヘッドルームの代価・制御が裏口に追いやられる）・借用検査（寿命の注釈と所有権の学習の代価）。

関連: [決定の記録11節・21節](../language.md)・[region / Domain / Pool](../region-domain-pool.md)

## 寿命の注釈が要らないのはなぜか

答え: 寿命が構文（スコープの入れ子）から決まるので、書き手が寿命を宣言する必要が無いからです。代わりに「書けない形」があります。寿命が構文に従わない参照（スコープを越えて共有される可変な値）は、そもそも表せません。書けない形はコンパイルエラーになり、その形はコピーする・不変にする・チャネルで渡すのどれかに書き換えます。

関連: [決定の記録21節・31節](../language.md)

## データ競合が起きないのはなぜか

答え: 並列のスコープ（`task.Run` の子・`task.Map` の要素のtask）へ渡せるのが、不変の値（`freeze` したもの・不変の束縛）とチャネルだけだからです。`mut` の値はtaskの境界を越えません。チャネルの送り端・受け端は1つのtaskだけが所有し、子へ渡すと親からは使えなくなります。`freeze` できるのは他に別名の無い値だけで、`freeze` の後は元の変数から書けません（コンパイラが確認します）。共有された可変の状態が無いので、データ競合は書けません。

関連: [決定の記録11節・18節](../language.md)・[ツアー7節](../guide/tour.ja.md#7-並列--structured-concurrencyチャネル)

## その安全性はどこまで証明されているのか

答え: 言語のコアを形式化したモデル（Featherweight Sober）をLean 4で書き、領域の安全・データ競合がないこと・型の健全性と、並列の出力の決定性（Kahnのネットワークとしての合流性）を証明しています（`lean/`）。証明されているのは体系（モデル）の性質で、コンパイラの実装の性質そのものではありません。実装との距離はコンパイラの型検査器とLeanの検査器の判定を大量の入力で突き合わせる照合（検証の体系の一部）で縮めています。

関連: [形式化](../formal.md)・[オラクル](../oracles.md)

## エラーの取りこぼしをどう拒否するのか

答え: エラーはラベル（`type NotFound error`）で、関数は `(T, error?)` で返します。解析器が呼び出しのグラフからラベルの集合を導き、`switch err` の扱い漏れを拒否します。公開の関数は返しうるラベルを宣言し、packageの境界では宣言と導出が照合されます。結果として、`default: panic` や握りつぶしで済ませる書き方が要らなくなります。

棄てた案: 例外（どの呼び出しが投げるかがソースに見えない）・Goの `error` interface（何が返るかが型に出ず、網羅を確認できない）・行多相（OCamlの多相バリアント・Kokaのエフェクト行。型の体系が大きくなる）。

関連: [決定の記録13節](../language.md)・[ツアー5節](../guide/tour.ja.md#5-エラー--ラベルcatchswitch)

## panicはいつ起きるのか

答え: 2種類だけです。1つは「健全性の防衛」で、続けると安全性が破れるもの（不変にした値への書き込み・領域の上限の超過など）。もう1つは「到達 = バグ」で、範囲外の添字・明示の `panic(L{…})` のように、正しいプログラムでは届かないもの。失敗しうる普通の処理（ファイルが無い・入力が壊れている）はpanicでなくエラーのラベルで返します。panicは理由（ラベル）と位置（ファイル:行:列）を出して終了します。

関連: [決定の記録27節](../language.md)

## なぜselectが無いのか

答え: 「いま届いているか」を観測するselect（ポーリング）を入れると、並列の出力の決定性（ワーカー数やスケジュールに依らず同じ出力）が成り立たなくなるからです。優先度の制御はキャンセルとscopeの構造で、複数の入力の合流はチャネルの設計で表します。

関連: [決定の記録11節](../language.md)

## 再帰的な型（自分を含むstruct・木）はどこまで書けるのか

答え: 自分に戻る参照が、`[]T`・`map[K]V` の要素か、`T?` の中身か、関数型の仮引数・結果を通るなら書けます。たとえば次の形です。

- `type Tree struct { kids []Tree }`
- `type L struct { v int; next L? }`
- JSONの値の形のunion
- 互いをsliceで持つ型の組
- `List[T]`
- `type State func(n int) State`

値はimmの木で、下から組みます。regionの上では木は1つのregionに閉じ、関数の返り値などでregionを越えるときは木ごとコピーされます。

拒否するのは、自分を値でそのまま含む形です。フィールドに自分自身を直接持つ形や、`[N]T` を通る形がこれに当たります。値の大きさが無限になるためです。`T?`・`[]T`・mapを通す形か、表と番号で持つ形に書き直します。

関連: [決定の記録1節](../language.md)

## 子のtaskが死んだら（panicしたら）どうなるのか

答え: 死は値でなく構造で伝わります。`task.Run` の子が死ぬと、scopeは出口で失敗（`ChildDied`）になり、親が受け取ります。`task.Try` で死を早く知ることはできますが、死を吸収して何もなかったことにはできません。死んだtaskの壊れた途中の状態で利用者のコードを走らせないため、死んだtaskの後始末（defer）は走りません。

関連: [決定の記録11節](../language.md)
