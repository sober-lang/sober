# 設計ノート: 平凡

[READMEの柱「平凡」](../../README.ja.md#平凡) と [DESIGN 2. 式指向](../../DESIGN.ja.md#2-式指向--値は流れ構文は分岐しない) の「なぜ」。

## なぜメソッドが無いのか

答え: メソッドが担っていた仕事は、別の手段で足りるからです。名前空間はpackageが、カプセル化はpackageの可視性（大文字 = 公開）が、ドット記法の読みやすさは `x |> f(a)` が担います。残るのは暗黙のselfの束縛と、値 / ポインタのレシーバの規則・メソッドの集合の規則で、これは言語を大きくするだけでした。

棄てた案: Goのメソッド（レシーバの規則が増える）・UFCS（全部の関数が `x.f()` の候補になり、名前の解決が濁る）・拡張関数（名前の解決の入口が2つになる）。

関連: [決定の記録3節・4節](../language.md)

## なぜinterfaceも型クラスも無いのか

答え: interfaceは「関数値をフィールドに持つstruct」、実装は「そのstructの値（辞書）」で表せるからです。`Ord[T]{less: (a, b) => a < b}` を明示で渡します。どの実装が使われるかは呼び出しの場所に書いてあり、型から暗黙に解決する仕組みはありません。

型クラスが辞書渡しに足すのは、暗黙の解決・再帰的な合成・型ごとに1つの実装（コヒーレンス）の3つです。Soberはこれを言語に持たず、辞書の省略を道具（fix）が補う方向を取りました。

棄てた案: Rustのtrait + implブロック・Goの暗黙のinterfaceの満足（どの型がどのinterfaceを満たすかが宣言に見えない）。

関連: [決定の記録3節・25節](../language.md)・[ツアー4節](../guide/tour.ja.md#4-structunionジェネリクス辞書)

## なぜマクロもcomptimeも無いのか

答え: コンパイル時の計算は、読み手がソースから意味を追えなくなる最大の源だからです。Soberでは「意味を持つものはソースにある」を基準にしていて、生成が要るものは道具がソースに書き込み、レビューを通った普通のコードとして残します。

棄てた案: Zigのcomptime・Rustのマクロ・Goのgo generate（生成物がビルドの外の別物になる）。

関連: [決定の記録9節](../language.md)

## なぜifやswitchが値を持つのか（三項演算子が無いのはなぜか）

答え: 値を選ぶたびに一時的な `mut` を作らずに済むからです。`x := if c { a } else { b }` は、Goの `var x T; if c { x = a } else { x = b }` の置き換えです。ifが式なので三項演算子は要りません。`else` の無いifは値を持たず、文としてだけ書けます（無い場合の値を暗黙に作らない）。

関連: [決定の記録1節](../language.md)・[ツアー1節](../guide/tour.ja.md#1-値と束縛式)

## なぜ多値（タプル）を変数に入れられないのか

答え: 多値は「結果が複数ある」ことの表現で、構造を運ぶ組ではないからです。受け取れるのは分解（`a, b := f()`）とパイプの先の引数（`f() |> g(_, _)`）だけで、組のまま保存したり `.0` で取り出したりはできません。名前を持つべき組はstructで名付けます。これで匿名の積型が増えることと、エラーの扱いの先送りの両方を防いでいます。

棄てた案: 一級のタプル型（便利すぎて構造の名付けが消える）・多値を一切持たない（式指向と多値の戻りが両立しない）。

関連: [決定の記録2節](../language.md)

## なぜfor … yieldの結果を変数に入れられないのか

答え: `for … yield` が作る遅延の列（`Iter`）は、消費する場所（パイプの先や引数の位置）で展開されるからです。変数に入れたり返したりできる「逃げるIter」を許すと、捕捉した状態の寿命を型で追う必要が出ます。今は消費の場所でだけ使える形にとどめています。

関連: [決定の記録7節・25節](../language.md)・[ツアー3節](../guide/tour.ja.md#3-slicemapfor)

## なぜ同じ名前で束縛し直せない（シャドーイング禁止）のか

答え: 同じ名前が場所によって別の値を指すと、読み手が追う手間が増えるからです。束縛は既定で不変なので、値を更新したい場合は `mut` を付けるか、別の名前を付けます。

関連: [構文 決定11〜18](../syntax.md)

## なぜ書き換える引数に、呼び出しの場所でもmutと書くのか

答え: どの呼び出しが手元の変数を書き換えるかを、呼び出しの行だけで分かるようにするためです。`push3(mut xs, 7)` と書いてあれば、`xs` が変わりうるのはこの行です。同じ呼び出しに同じ変数を2つのmut引数として渡す（別名）ことは拒否されます。

棄てた案: ポインタと `&x`（どこで書き換わるかが型の流れを追わないと分からない）・C# のrefを仮引数だけに書く形。

関連: [決定の記録26節](../language.md)・[ツアー6節](../guide/tour.ja.md#6-mut引数とfreeze)

## なぜnullでなくT? なのか

答え: 「無いかもしれない」を型で区別するためです。`nil` は `T?` の値にしか住めず、使う前に `!= nil` で確認すると、その先では `T` として使えます。mapの引きは `V?` を返すので、「無い」と「ゼロ値」の取り違えが起きません。

棄てた案: 全部の型にnull（取り違えの温床）・Goのゼロ値の返り（無いことと0が区別できない）。

関連: [決定の記録15節・22節](../language.md)

## クロージャ（外の変数を捕まえる関数の値）はどこまで使えるのか

答え: 外の変数を捕まえたラムダは、名前付きの関数型（`type Adder func(n int) int` のような宣言）の値の位置に置くと値になり、関数の境界を越えて持ち回れます。値の位置は名前付きの関数型の仮引数と結果、structの関数型のフィールドです（例: `examples/closure_def_capture.sober`）。捕まえるのは作った時点の不変の値のコピーで、元の変数がその後に変わっても見えません。mutの束縛・同一性の型（`io.File` など）・`task.Scope` は、値の位置のラムダからは捕まえられません。匿名の関数型の仮引数に渡したラムダは、これまでどおり呼び出しの場所で展開されます（`twice((v) => v * 3, 2)` のような形）。値の位置のラムダでmutの変数の今の値を使いたいときは、先に不変の変数へコピーして（`kk := k`）それを捕まえます。呼び出しをまたいで状態を更新し続けたいときは、状態を呼び手が持ち、関数型にmut仮引数を書いて（`type Handler func(st mut App, ev int)`）呼ぶたびに `h(mut st, ev)` と渡します — ラムダはmutを捕まえないので、書き込みの先が呼び出しのマークに見えます（例: `examples/fn_mut_param.sober`）。ラムダは局所の変数に束縛することもできます（`f := (n int) => n + k`）。このfは値ではなく、呼ぶたびにその場所へ展開されるので、mutの変数もそのまま捕まえられ、更新は呼び手に見えます（例: `examples/local_lambda.sober`）。その代わりfを別の変数に入れる・structに格納する・返す、はできません — 値として持ち回るときは名前付きの関数型の位置に書きます。

関連: [決定の記録8節・25節](../language.md)
