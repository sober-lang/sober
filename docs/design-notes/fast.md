# 設計ノート: 高速

[README の柱「高速」](../../README.ja.md#高速) と [DESIGN 5. 素直に書いて速い](../../DESIGN.ja.md#5-素直に書いて速い--速くするための機構はコンパイラとランタイムの中だけ) の「なぜ」。

## なぜ「素直に書いたコードが最速形」と言えるのか

答え: 速さのための機構を、コンパイラとランタイムの中にだけ置くと決めているからです。利用者のコード・std の API・ベンチマークの Sober 側に、速くするための書き方を持ち込みません。「こう書くと速い」という作法が生まれたら、それは言語の欠陥として扱い、コンパイラかランタイムの側で直します。目標は、性能の民間伝承が 1 つも無い言語です。

棄てた案: 速度のための注釈（`inline` の指示など）・利用者に見えるチューニングの口・ベンチマークだけの手の込んだ書き方。

関連: [DESIGN 5](../../DESIGN.ja.md)

## ベンチマークは何と比べているのか

答え: 9 題材（1BRC・binary-trees・fannkuch-redux・fasta・k-nucleotide・mandelbrot・n-body・reverse-complement・spectral-norm）を、同じアルゴリズムを素直な形で書いた Go と Rust の双子と比べています。測るのは CPU 時間（task-clock）と最大 RSS です。GitHub Actions の 1 つの vCPU に固定して Sober・Go・Rust を交互に 5 周測り、周ごとの比の中央をとります。出力が一致することも毎回確かめます。手の込んだ最速の実装と比べるのではなく、「同じように素直に書いたとき」の比較です。Rust については、負けている題材に慣用的にチューニングした版も並べて差を見ています。

関連: [ベンチマーク](../bench.md)・`bench/<題材>/go`・`bench/<題材>/rust`

## どこで負けているのか

答え: 素直な Rust に対して、reverse-complement 1.47×・n-body 1.17× で負けています（逐次 9 題材・2026-10-25 の公式計測の CPU 時間）。 <!-- benchsync:notes-fast-loss -->

負けの帰属（分かっている分）は [ベンチマークの結果](../../bench/README.md) にあります。どれもコンパイラとランタイムの側で縮める対象で、書き方の工夫で埋めることはしません。

関連: [ベンチマークの結果](../../bench/README.md)・[計測の条件と規律](../bench.md)

## なぜ LLVM を使わないのか

答え: Sober の制約（閉じた世界・別名の決まり方・意味が最適化器に依らないこと）から得られる知識を、自分のバックエンドで直接使うためです。命令選択やベクトル化の質で LLVM と正面から競うのではなく、LLVM が原理的に持てない知識（スタックの上界・escape の構文的な決まり方・不変性）で勝つ方針です。LLVM を使わないことは、コンパイラを依存ゼロの単バイナリにすることと、ブートストラップを Zig とソースだけで閉じることにも役立っています。LLVM の出力は開発の中で差分のオラクル（正しさの照合）として使っています。

関連: [IR](../ir.md)・[設計の記録 — バックエンド戦略](../design-dev.md)

## なぜ C にトランスパイルしないのか

答え: C を間に挟むと、速さは借りられても「出力への約束」は借りられないからです。ワーカー数を変えてもバイト単位で同じ出力になる決定的な並列も、自己コンパイルの固定点（stage3 ≡ stage4）も、最適化や関数キャッシュのあり / なしで ELF が一致することの照合も、出力のバイト列を最後まで自分で決めていることを前提にしています。後段に C コンパイラが入ると、これらの判定が C コンパイラのバージョンとフラグに左右されます。関数単位で機械語を使い回すインクリメンタルコンパイルも、後段が翻訳単位ごとに作り直す形では成り立ちません。速さの面では、C にトランスパイルする言語が速い理由は「別名や寿命の事実を、人間には保守できない形の C に書き込めること」にあり、同じ事実は自分のバックエンドでも直接使えます（上の「なぜ LLVM を使わないのか」と同じ理屈です）。C 経由の利点として残るのは移植性ですが、それはクロスコンパイル（ロードマップ）で取る計画です。

関連: [オラクル](../oracles.md)

## GC が無いことの利点は「少ない」より何なのか

答え: 予測できることです。GC のある言語は、停止とヘッドルーム（生きているヒープの数倍の余裕）のせいで、tail latency とメモリの量が読みにくくなります。Sober では割り当てがスコープの出口でまとめて解放され、オブジェクトのヘッダもヘッドルームもありません。メモリの量はそのときに生きているスコープの中身でほぼ決まります。

関連: [設計の記録 — 位置づけ](../design-dev.md)

## 並列の出力が決定的なのはなぜか

答え: 標準出力の順を「spawn の木の先行順」に決めているからです。task ごとに出力を溜め、親の流れの spawn の位置に子の流れを差し込む順で書き出します。加えて、並列の値は不変の値とチャネルだけで受け渡し、select（ポーリング）を持たないので、値と出力がスケジュールに依りません。ワーカー数（`SOBER_WORKERS`）を変えても、同じバイト列が出ます。

関連: [決定の記録 11 節](../language.md)・[安全 — なぜ select が無いのか](safe.md#なぜ-select-が無いのか)

## task が軽いのはなぜか

答え: task の器が小さく、作り方が単純だからです。task ごとの記録とスタックは固定の大きさの 1 塊（ガードページつき）で、塊は使い回します。スタックを伸ばす機構（Go の関数の入口の伸張の検査と写し）を持ちません。task の間の受け渡しは不変の値とチャネルだけなので、同期の費用も小さく済みます。閉じた世界から分かるスタックの上界に合わせて器の大きさを決めることは、今後の作業として設計に入れてあります。

関連: [決定の記録 11 節](../language.md)・[ベンチマーク — 並列](../../bench/par/README.md)

## ジェネリクスは単相化されるのか

答え: 意味としては単相化を約束していません。ジェネリック関数の意味は「辞書を渡す」形で定義されています。型ごとに具体化したコードを作るかどうかは最適化器の判断で、意味に影響しません（debug ビルドでも同じ結果になります）。

関連: [決定の記録 9 節・25 節](../language.md)
