# x86レジスタ割り当て（src/compiler/lower/x86.sober）

src/compiler/lower/x86.soberの正規バックエンドが使う、線形スキャンから優先度順の貪欲彩色へ拡張した割り当て器の設計を1つにまとめる。
実装はコードcommentsに散り、設計判断は開発記録に散っていた。この文書はそれらの要約と決定の記録で、
コードと報告が食い違う箇所はコードを正とし、その旨を明記する。

対象ファイルはsrc/compiler/lower/x86.soberのほぼ全体（命令選択・CFG・生存解析・割り当てが1ファイルに同居 — B-1dの移植。src/stage1/ir_x86*.zig・
ir_live.zig・ir_cfg.zigが凍結した前身）。正しさの根拠はstage1が同じIRテキストからビルドしたELFとのバイト一致（scripts/elfeq.sh）で、
中間成分（区間・配置先）そのもののZigとの照合は無い（docs/ir.md 9.5節）。

## 0. 2つのバックエンドの使い分け

- `--backend=copy`（st.xcopy = true・e.opt = false）: 素朴な線形スキャン（1本の連続区間・追い出しは「endが最も遠い区間を落とす」・ヒントなし）。
  凍結したZigの割り当て器と1バイトも違わない出力を出す（elfeq・stagesのcrossがこれを見る）。性能投資の前（性能投資M4）の移植
- 既定（e.opt = true）: この文書が扱う最適化のバックエンド。区間分割・重み・優先度順の彩色・ヒント・2段階方式が全部ここに乗る
- 両者は同じデータ構造（xF）・同じ命令選択・同じ命令符号化を共有し、割り当てのアルゴリズムだけが分岐する（xAllocRegs内の `if e.opt { ... } else { ... }`）

## 1. パイプライン概観（xFunc — src/compiler/lower/x86.sober）

関数ごとに1回、次の順で走る:

```
xFoldScan（opt のみ — gep の番地の融合）
xOrder       // 到達するブロックを逆後順に並べ、opt なら冷たい領域を末尾の 1 区画へ寄せる・ループの範囲 lpR を記録
xLive        // 値ごとの生存区間（線形の外包）+ 重み（wt/wc/hu）+ 冷たい領域の末尾の触れ（tS/tE）
xPieces      // 部分区間の表（S1b）を恒等で作る + 末尾の外包があれば 2 本目の部分区間 + 運搬値の穴（xHolePieces）
xHints       // opt のみ — 兄弟・辺・演算のヒント表
xFloatClass  // opt のみ — xmm に割り当てる値の集合
xAllocRegs   // 一段目: 区間を並べ替え、opt なら xPrioAlloc（優先度順の貪欲彩色）・でなければ素朴な線形スキャン
[xSplitLoops → xPrioRealloc → xUnsplitSpilled]  // opt かつ spill が出たときだけ: 二段目（差分の再割り当て）
xAllocFrame  // 退避域・spill 先の変位・区間を持たない値の番地（1 回だけ）
[命令符号化・終端の配置・線の跨ぎの詰め物]
```

分割しない関数は1段階目の結果がそのまま最終で、2段階目の仕事は「圧のあるループを素通りする値がある関数」だけに閉じる。

## 2. レジスタ集合と呼び出し規約

- 呼び出し規約は自前（ABIは揃えない — オラクルは観測等価であってバイナリ一致ではない。docs/ir.md 6節）: 引数は全部スタック
  （呼び手が後ろからpush、calleeは `[rbp + 16 + 8k]`、callの後に呼び手が `add rsp, 8n`）・戻り値はrax。
  参照で渡す仮引数（Kワードを超えるimmの集成値 — docs/ir.md 6節）はスタックの1ワードが番地で、calleeはフィールドを `[番地 + 8k]` から読む
- 割り当て可能なGPRは10本、すべてcallee-saved: `rbx, r12, r13, r14, r15, rsi, rdi, r8, r9, r10`（xAllocReg — 割り当てる順。
  syscallの引数に使うrsi/rdi/r8〜r10は後ろへ置く）
- 一時レジスタはrax / rcx / rdx / r11の4本で、割り当てには使わない（xDivRem・xParallelMoveの循環の解消・符号拡張などが使う）
- xmmは8本（xX0+8〜15）が既定。関数がscanb（UTF-8検査のSSE2命令）を含まなければxmm2〜7も割り当てに使える14本（xNXmmWide）。
  scanbはxmm0〜7を作業に使うため、含む関数はこれらを呼び手の値のために壊さない（xHasScanB・xAllocFrame）。入口で退避するのは本体が実際に書く
  xmm2〜7の和（xBlkXmm — 本体の出力の仕方の隣に置く: 出口が「x >=u 128」だけのscanbはxmm0だけで退避なし・他のscanb / 数え上げ / UTF-8の検査器は
  xmm1〜7・crcfoldはxmm0〜5）— utf8.Checkの入口の24命令が消えた。テスト = examples/xmm_live_across_blocks（関数値で呼ぶ — 呼び手がf64をxmm2〜7に
  持ったまま各形の本体を跨ぐ）。割り当ての組の広さ（xNXmmWide）は今も「scanb / crcfoldを含むか」で決める（広げると割り当てと配置が動く — 別のコスト）
- フレーム = push rbp; mov rbp, rsp; sub rsp, F。`[rbp - …]` にIRスロット（入口でrep stosqゼロ初期化 — 最適化のバックエンドは0を観測できるワード〔同じブロックで先に書かれないワードのload・番地が逃げる点で書き済みでないワード〕を覆う最小の区間だけ〔zeroinit.sober — rep stosqのタスクのフェーズ1 2026-10-11〕。区間が16ワード以下ならrep stosqでなくxor eax + mov [rbp - …], raxの列〔フェーズ2 — xZeroStores。コンパイラ自身の自己buildのcycles −1.8%。棄てた案: pxor xmm0 + movdquの列・T = 32 — report-495〕。移植版のバックエンドは全ワードのまま〔elfeq〕。棄てた案: 全ワードを外す — 毒の実験〔report-488〕で零は観測されなかったが、IRの約束を破る形を判定なしで置かない）→ 退避域 → spillの順
  - 零初期化の沈め（格納場所の往復レーンのフェーズ4b (b1-z) — xZeroSink / xZeroSinkCalc・最適化のバックエンドで区間16ワード以下）: 入口から、区間に重なるスロットの番地（slotaddr）を
    持たないブロックだけを辿った領域Eにret（早期return）があれば、零初期化を入口でなくEの出口の先のブロック（前線）の頭で吐く。Eの中では区間のワードを指す
    番地が作られない（定義が使用を支配するので定義のブロックだけ見ればよい）ので、呼び出しを含んでも区間のワードは読まれも書かれもしない。条件: Eの外からEへ
    戻る辺が無い・前線の前任が全部E・前線は4つまで（どのパスでも前線をちょうど1回通る）。前線は空の中継として飛ばさない（xFwdTo）。毒のオプションは入口に残す。
    routingのmatch（早期return 66,102 / 83,631回）で命令 −1.67%。テストの限界: 零の位置の誤り（前線で出力しないミュータント）は毒のオプションつきでも母集団で観測されない
    （report-488の「零は観測されていない」と同じ — 要零の判定が保守的）。判定は単体テスト（zeroinit_testのTestZeroSink）で直に見る
  - スロットの彩色（F-1のフェーズ2 — slotcolor.sober xSlotColor・最適化のバックエンドだけ・report-1003）: 要零が空（zeroinit — 入口の0を観測する読み取りが無い）で番地が逃げないスロットどうしが、生存が重ならなければフレームの同じワードを使う。番地の使い方の分類はzeroinitと同じ（load / storeの定数の変位・定数のgep・callの実引数のうちsretの受け皿〔全ワードの書き〕・mut仮引数〔F_MUTP — 呼び出しの間だけ読み書き〕・rtのコピーとrelocate〔読み書き〕）で、それ以外は逃げ。生存 = スロット単位の後ろ向きのデータフロー（全ワードの書き = sretの受け皿と、読み取りを挟まずに全ワードを覆うstoreの列の最初のstore — そこで死ぬ）。干渉 = 書きの点で生きている別のスロット + 入口で生きているスロットどうし。彩色 = 大きさの降順のfirst-fit（決定的）。要零のスロットと逃げるスロットはフレームの頭に宣言の順で固めて置く — 入口の零初期化の区間がその中に収まる（serveTlsConn 32624 → 1376 B）。門は持たない（全部の関数を彩色する）。棄てた案: 彩色の候補が128ワード未満の関数は並びを変えない門（解析の仕事を +0.06 Gに抑えた）— コピーが減ってスロットが門の下に落ちると彩色が外れて枠が増える崖になった（Dispatch 1,088 → 1,344 B）。門を外したコストは判定の仕事 +0.57%（stage3の自己build +0.624 G）・cycles +1.1%（pipelined 8配置 × 4周 — store → loadの転送の失敗〔ls_bad_status2.stli_other〕がリクエストあたり1.07 → 2.27に増えた分に起因）。sretの転送と組むとベースライン並み（+0.2%・命令 −3.1%）で、門を残すと転送の後で崖を踏む（+4.0%）。テスト: ミュータント「戻りの辺の生存を落とす」はoptdiff・「mutの実引数を全ワードの書きに数える」はstages（自己buildのstage3がpanic）が鳴らす。棄てた案: 要零のスロットも共有して生存の始まりで零にする（零初期化の沈めの器が要る — フェーズ3で扱う）
  - フレームの内訳の計測ツール（F-1のフェーズ0 — report-1003）: 開発用のオプション `sober build --frame-stat`（1本の経路）が関数ごとに `frame <関数> <フレーム B> <スロット B> <零初期化 B> <退避 B> <spill ほか B> <spill の部分区間の数>` をstdoutへ（xFrameStat）。scripts/framestat.sh（gate framestat）がscripts/framestat.listの上限〔実測 × 1.01〕と照合する — フレームの大きさは出力を変えないのでoptdiffでは鳴らない
- 命令選択はオペランドを全部読んでから結果を書く（割り当て器が「同じ位置で終わる区間のレジスタを始まる区間へ渡してよい」前提を置くための規約）

## 3. 位置づけ（吐く順の通し番号）

- xOrderが到達するブロックを逆後順（post-orderの逆）に並べ、吐く順に通しの位置番号を振る: ブロックの頭 = bpos（偶数）、
  命令k番目 = `bpos + 2*(k+1)`（偶数）。分割点（境界）は奇数の位置（「次のブロックの頭 − 1」）に取り、問い合わせの位置（命令・ブロックの頭）は
  すべて偶数なので境界で迷わない（xSplitLoops・xHolePiecesの分割点の規約）
- optのときはxOrderが追加で2つの並べ替えをする:
  1. 冷たい領域を末尾の1つの領域へ寄せる（3.1節）
  2. ループの深さ（xLoopDepth）とループの範囲（lpR）を、並べ替え前の逆後順で計算してから新しい位置へ移す
     （並べ替え後だと末尾から本体へ戻る合流の辺が偽の「後ろの辺」になり、ループの深さの判定を誤る）

### 3.1 冷たい領域の検出と末尾配置（S3a/S3b — xColdBlocks・xColdChain・xColdMark）

- 起点 = (a) exitで終わるブロック（panicの点）(b) 遅いパスのrt（`rt.slice_grow` / `slice_grow8` / `grow_try` / `map_grow` /
  `region_relocate` / `region_relocate8` — xSlowRt）を呼ぶブロック。`rt.region_alloc` は確保の主要なパスでもあるので起点にしない
- 冷たい辺 = 条件分岐の片側だけが、単一入口・単一出口のブロックの列（`br` だけを辿る — 終端がcondbrならそこで列が切れる）を通って起点に届くとき、その側
- 広がり方: 冷たい辺の行き先から前向きに「前任（後ろの辺を除く）が全部冷たい」で広げる
- 起点をユーザーの呼び出し（再帰など）に取らないのは、熱い呼び出しを冷たいと誤読しないため
- 末尾へ寄せるのは「ループの外（深さ0）かexitで終わるもの」だけ（逸脱 — 設計は「冷たい領域は全部寄せる」だったが、ループの中の冷たい領域を
  寄せると合流ブロックの仮引数の合体が崩れる実害が出たため末尾配置を見送った。重みの補正（3.2節）にはループの中の冷たいマークもそのまま使う）
  - 棄てた案: 冷たい領域を全部（ループの中も）末尾へ寄せる — revcompで合流ブロックの仮引数のレジスタが熱いパスの実引数と逆に入れ替わり、
    1文字ごとの後ろの辺に3命令の入れ替えが発生（命令 +3.3%・cycles +13%）。
  - 棄てた案: 冷たいブロックの判定をブロック単体（遅いパスのrtを呼ぶブロックだけ）にする — 冷たいパスの中の速いパス（先端でのappendの
    インライン）の使用が深さの重みのまま残り、1BRCのmainで挿入のパスでだけ働く値が重み129のまま熱い部分のレジスタを占めた
  - 棄てた案: Ball–Larus型の静的分岐予測（「呼び出しへ進む側は起きにくい」）— ユーザーの呼び出しを起点にし、再帰・熱い呼び出しを冷たいと誤る
   
- 末尾の触れは本体と別の外包（xTouchの `tS`/`tE` — 4.3節）: 1本の連続区間のまま末尾へ寄せると外包が関数の終わりまで伸び、
  熱い値と全部重なった（fannkuch 23.2 → 56.5 G）
- 本体 ⇄ 末尾の境界のコピーは辺ごと（xSplitMoves — 6節）。分割点は「末尾の始まり − 1」の1か所（e.cutsに足す）

## 4. 生存区間

### 4.1 線形の外包（xLive・xTouch）

- Zig版の移植の規律から唯一逸脱した部分（docs/ir.md 9.5節）: ブロック数 × 値の数のビット集合で不動点を反復する代わりに、上向きに露出した
  使用から前任へ辿る経路探索（SSAのpath exploration）。到達するブロックのlive-in/live-outは最小不動点と一致するので区間は同じ —
  バイト一致（elfeq）がそれを示す。メモリは使用の総数に比例し、stage1の巨大関数の爆発（src/compiler/appが589 s / 29 GB）を構造的に持たない
- 値ごとに1本の線形の外包 `[ivS, ivE]`（最初の触れ〜最後の触れ。live-inのブロックの頭・live-outの前任の終わりも触れる）。
  穴は無い（兄弟の枝の片方でだけ生きる値も、吐く順でもう片方を跨げば両方で「生きている」扱いになる — 構造の要点4）
- 冷たい末尾の領域（3.1節）に入ってからの触れだけは別の外包 `tS`/`tE`
- remat（imm32定数・スロットの番地 — 10.1節）は区間を持たない（`xTouch` が早期リターン）

### 4.2 部分区間の表現（S1b — 区間分割レーン）

値ごとに1本だった区間を「部分区間」へ拡張する際の設計判断:

- 区間の番号空間を値の番号と共有する: 値vの最初の部分区間の番号はv自身、続きは `pnx` の連鎖（番号 `nv` 以降・開始の昇順）。`pv` = 部分区間 → 値、
  `npc` = 部分区間の総数。部分区間が1本の値は `pnx[v] = -1` で、今までの「値ごとに1本」と出力が完全に同じ
  - 棄てた案: 値ごとの部分区間の別表（CSRの `[開始, 終わり, 置き場]`）— 割り当て器の全読み出し箇所を別表へ書き換える面積に対し、番号の共有なら
    `ivS`/`ivE`/`loc`/`xPrioAlloc` がそのまま部分区間を扱え、「1本の間は出力不変」が自明になる
- 割り当ての単位は部分区間（`xAlloc`/`xPrioAlloc`/`xPrioFits`/`xSyscall` の生存の走査は全部部分区間の番号で回る）。値の属性
  （重み・floatクラス・ヒント）は `pv` 経由で値へ移して読む
- spill先は値ごとに1つ（`spd` — 同じ値の部分区間で共有。最初にspillされた部分区間の順に変位を配る）
- 配置先の読み出しは位置つき `xLocAt(e, v, p)`（部分区間の連鎖を開始の順に辿り「終わり ≥ p」の最初を取る。区間が1本なら `e.loc[v]` の速いパス）:
  命令の被演算子・結果は `e.pos`、終端と辺の読み出し元はブロックの終わり、辺の書き先は行き先のブロックの頭、入口引数の読み出しは入口の頭

### 4.3 部分区間を作る3つの経路

`xPieces` は恒等（値ごとに1本）を作るだけで、分割するのは次の3箇所:

1. 末尾の領域の外包（3.1節 — 本体の触れが無ければそのまま1本、あれば2本目の部分区間。重み1）
2. 運搬値の穴（T2 — xHolePieces・下記4.4節）
3. 2段階目のループ境界分割（S2 — xSplitLoops・5節）

### 4.4 運搬値の穴（T2 — xHolePieces）

- 動機: ループの頭の仮引数（運搬値）がループの後ろでしか使われない場合、線形の外包がラッチまで伸びて戻り辺の実引数と重なり、
  同じレジスタを取れず戻り辺にコピーが残った（葉の `mov r14, rbx`）
- 形: 本体の区間を、生きているブロック（live-in・頭）の吐く順の連なりごとの部分区間に分割する（間は穴 — 値はそこで死んでいる）。
  連なりの終わりは、出ていく辺の先で生きていればブロックの終わり、でなければブロックの中の最後の使用（xHoleEnd）。部分区間の重みは値の重みのまま
  （どの連なりも同じ）。穴をまたぐ辺のコピーは既存のxSplitMovesがそのまま出す
  - 注記（第1タスク (d) ① の試行）: この「値の重みのまま」は、部分区間の数だけ重みを重ねて持つ水増しに見えるが、今の貪欲彩色の下では
    境目の結合の代わりとして働いている（中に使用の無い運搬値の部分区間がレジスタに居続け、境目のコピーが熱いループに出ない）。部分区間ごとの中の重み
    （L1のC* と同じ規則）に直すとfannkuch +2.0%・mandelbrot +1.0%・1brc +1.5%（命令）で退行し、境目の費用の判定（13節4）を足しても戻らなかった。
    （差分は開発記録に保存 — L2型の選び方を作るときの部品）
- 連なりの切り方（区間のタスクのフェーズ1 R1 — report-528）: 吐く順で続くブロックの列でも、値がブロックから出ていかない（終わりがブロックの終わりより前 —
  ラッチの手前で死ぬ運搬値）ところで切る。運搬値の部分区間が更新値の定義の前で終わり、更新値（戻り辺の実引数）が仮引数と同じレジスタを取れる
  （logagg mainの `lea r8,[rbx+1]; mov rbx,r8` — 72.9万回）。連なりの終わりの数えと分割は1回の走査（判定の仕事を半分に）
  - 単独では2題材が退行した（report-522 2.2 — シーソー）。対策2つと組で入れた: 予約（8節 — mandelbrotの戻り辺の循環）・穴の部分区間の
    ループ境界分割（5.1節 — revcompの内側ループの枠の占有）
- 効果: 葉の熱いループが12 → 8命令（コピーの連鎖が全部消え、運搬値どうしが同じレジスタに合体 — 可換の入れ替えも不要になった）。
  cycles（layvar 8配置中央）: fasta −12.7%・revcomp −11.5%・knucleotide −5.1%・1brc −3.6%
- 副作用で見つかった潜在バグ: xSplitLoopsの分割点の併合が、重複を除いた結果を前の列の先頭へ書き戻すだけで末尾を切り詰めておらず、
  値をまたいで重複する分割点があると昇順が崩れてxSplitMovesの二分探索が分割点を見落とし、辺のコピーが抜けた（自己ビルドしたコンパイラが
  `parser.parametersN` を誤コンパイルして実発）。修理 = 併合結果を新しい列として作り直す
- コスト: gran（葉）題材の予測ミスが0.55 M → 4.5 Mに増える（検査点の間引きのカウンタが、ループが短く速くなったことで予測を外すようになった —
  割り当ての問題ではなく間引きのカウンタ側の問題。別のタスクへ申し送り）

## 5. 2段階方式によるループ境界分割（S2 — xSplitLoops・xPrioRealloc・xUnsplitSpilled）

### 5.1 動機と最終形

1段階目（分割しない）の結果でspillが出たとき、圧のあるループを素通りする値だけを境界で分割して2段階目を回す（2段階方式・
で完了）。

- 圧のあるループ = 1段階目でspillした値の定義・使用がループの範囲（吐く順の `[頭, 体の最後]`）の中にあるループ。組（int/xmm）ごとに
  spillした値の数を数える
- 素通りの値 = 外包が範囲を丸ごと含み、範囲の中に定義も使用も無い値。候補は値の1本目の部分区間と、運搬値の穴（4.4節）で分割された値の本体の
  部分区間（区間のタスクのフェーズ1 R1 — 穴の2本目以降が内側のループを素通りすると、値の1本目しか見ない形ではその部分区間が分割されず、値の重みのまま
  内側のループのレジスタを塞いで熱い一時値2本をspillに落とした: revcompの外側の運搬値 — report-528）。範囲の手前と後ろ（奇数の位置）で分割する。真ん中の部分区間は重み0
  （最後に割り当てる — ループの中だけspillするか兄弟のヒントで同じレジスタを得る）
- 本数の上限: ループ・組ごとに「1段階目でspillした値の数」まで。素通りの値を優先度の低い順（1段階目で先にどかされる側）に先着で枠を取る
- 入れ子は、値の使用の間の隙間ごとに、隙間に丸ごと入る最も外の圧のあるループで分割する
- 2段階目は差分の割り当て（xPrioRealloc）: 1段階目のレジスタごとの列（`aL`/`aB`/`aC`/`aN`）をそのまま持ち越し、分割した値の外側の部分区間を
  1段階目のレジスタに固定（`pfix` ≥ 0）して足し、残り（真ん中・1段階目でspillした値の中の部分区間）だけを優先度順に割り当て直す
- 分割しない関数は1段階目の結果がそのまま最終 = 今までと1バイトも変わらない

### 5.2 棄てた形

- ループの中で使う値も分割する（内側ループの出入りごとにレジスタ間のコピー）: fannkuchの命令23.2 → 32.9 Gで棄却
- 素通りの値を圧と無関係に全部分割する: ループの中の値が素通りの値のレジスタを先に取り、得るもの無しのコピーが出入りごとに発生
  （fannkuch +16%・knucleotide +8%）。真ん中の重みを0にしても「そのレジスタがループの中で空いているとき」しか兄弟ヒントが効かず、
  ループの中の値に番号順の最初のレジスタを先取りされる
- 2段階目で全部を割り当て直す（固定を置かない）: 分割した値の外側の部分区間は重みが分かれて優先度が下がり、1段階目でレジスタだった値が
  熱いループごとspillした（knucleotideのrt.map_findでspill 14 → 23・cycles +5〜8%）→ 1段階目の固定（pfix）を導入
- 分割する候補にspill済みの値も含める: 優先度の低い順に選ぶと1段階目ですでにspillしていた素通りの値が枠を先に取るが、
  レジスタを持っていないので分割しても何も明け渡さない（fannkuchのmainで命令 +1.0%）→ 候補は1段階目でレジスタを持っていた値だけに限定
- 真ん中・spillした値の中の部分区間を重みどおりに優先度へ混ぜる: revcompのcycles +10.6%（熱い一時値を押し出し、運搬値が
  毎反復store → loadの連鎖になった）→ 1段階目でspillした残りの後に余りの枠だけを取る（「形2」）形へ修正

### 5.3 T1（spillした値自身の分割）

区間分割レーンの素通り限定（5.1節）では拾えない、spillした値そのものの分割:

- 候補: 1段階目で丸ごとspillした値（末尾の領域の部分区間を持たない）のうち、区間がどれかのループと重なるもの
- 分割する場所: 使用ごとに最も内側のループを取り、そのうち入れ子にほかの選ばれたループを持たないものの境界で分割する。条件は
  「値の区間がループの外へはみ出す」と「1段階目の割り当てで、どれかのレジスタがループの範囲で空いている（楽観）」の両方
- 外側の部分区間はspillに固定（`pfix = -2`）。内側の部分区間（`pfix = -3`）と分割した値の真ん中は、1段階目でspillした残りの
  後に余りの枠だけを取る（5.2節の教訓の再適用）
- 2段階目の後、全部spillのままの値は1本に畳み戻す（xUnsplitSpilled — spill先は値ごとに1つなのでコピーは不要。残すと連鎖をなめ続け、
  自己ビルドの仕事が +0.5%増えた）
- 条件分岐のコピーが要る側がループの出口（深さが下がる辺）なら、そのコピーを関数の末尾へ出す（辺の外置き — 熱いループの本体に出口のコピーを
  残さない）。棄てた案: 外置きを辺の向きで絞らない — revcompの熱いラッチまで末尾へ出て毎反復jmpが2本になった
- 効果: gran（葉）の命令 −13.9%。pwtの自己ビルド仕事は +0.43%（ラチェットのコストつきで受容）

### 5.4 区間分割レーンの決算

- 1BRCの冷たいパスのコスト（+4%）はS3aで回収。冷たいブロックの末尾配置の壊滅（Aの対象）はS3bの2本の外包で解消
- 「展開を増やすと割り当てが劣化する」という仮説は成り立たなかった: 展開を増やすとコンパイラ自身の命令数はむしろ2〜4%減り、
  自己ビルドの悪化は全部「展開で増えたIRを処理するコンパイル時の仕事」だった。割り当ての問題ではなくインライナの予算の問題
- fannkuchのGo比1.02× への端数は、S2・S3・T1・T2のどれでも動いていない（熱いループの割り当ては変わるが命令数は同じ — 検査点の分岐予測や
  ループの形の問題で、割り当て器の守備範囲の外）

## 6. 重み（xWeigh・xWeighArgs・xColdBlocks）

- 値の重み `wt` は、定義・使用の出現ごとに `8^depth`（深さ4で頭打ち = 4096。xWeighの `w` テーブル）を加算する
- 辺の実引数は、行き先の仮引数がその値自身（恒等実引数 — 後ろの辺で変わらない変数）なら重みに数えない（配置先が同じならコピーは0命令 —
  S3a・xWeighArgs）
- 冷たい補正（S3a）: 「ループの中の熱いブロックに使用が無い値」（`hu = 0` — 定義・恒等実引数・ループ外の使用は `hu` に数えない）だけ、
  重みを `wt` から「冷たいブロックを深さ0で数えた `wc`」に置き換える
  - 棄てた案: 冷たいブロックの重みを全部の値で深さ0にする — 熱いパスと遅いパスの両方で使う値の重みが下がり、長い区間が短い熱い一時値を
    追い越してrevcompの内側ループでspillが増えた（cycles +18.3%）。hu=0の値だけに絞ることで回避
  - 棄てた案: 優先度を密度（重み ÷ 長さ）にする — 全題材で +5〜20%の退行で棄却
- 動機となった実例: 1BRCのmainで、冷たいパス（mapへの新規挿入）でしか働かないループの頭の仮引数が、冷たい使用も
  深さの重みのまま数えられて重み129に達し、熱い部分のレジスタを1本占有していた。重みの補正後は約22まで下がり、熱い一時値
  （重み16〜24）に負けてspillされる側に回った
- `xSpillCost`（= 重み ÷ 区間長。長さは256で頭打ち）は移植版のバックエンド（線形スキャン）の追い出し判定だけに使う。optの優先度順
  彩色（xPrioAlloc）は使わない（6.5節既知の弱点も参照）
  - 頭打ちが無いと、関数の端から端まで生きループの中で使われる値（sliceのlen/base）が長さで割ると安く見えspillされた
    （fannkuchの内側ループ — M6で発見）。64/1024も試したが結果は同じ

## 7. 優先度順の貪欲彩色（M8 — xPrioAlloc・xPrioSort・xPrioPick・xPrioFits）

- 順序: 重み `pwt`（部分区間の重み）の降順、同点は区間の長い順、さらに同点は値の番号の小さい順（決定的 — xPrioSort）
- 彩色: 優先度順に1本ずつ、重ならないレジスタへ（ヒントのレジスタを先に試す — xHintReg）。置けなければspill
  - 棄てた案（移植版のバックエンドの素朴な線形スキャン）: 「その時点のactive集合の中で最安を落とす」局所的な選び方 — 内側のループで重く使う
    長命の値（sliceのbase）を短い一時値より先に落としていた
- 重なりの判定: `s < e'` かつ `s' < e`（end ≤ startは共有可 — 同じ点で終わる区間と始まる区間は重ならない）
- O(log n) 化（S1a）: レジスタごとの割り当て済み区間を開始の昇順の列に持つ（割り当て済み区間どうしは重ならず開始も違うので
  「終わり ≤ 次の開始」。重なりうるのは「開始 ≤ sの最後」と「開始 > sの最初」の2つだけ）。枠は平らな配列（満杯なら倍の枠を取り直す —
  区間の数 × 32を関数ごとにゼロ埋めすると自己ビルド +0.6 Gだったため）
- 追い出し（区間のタスクのフェーズ2 D2 — xPrioEvict）: 置けない部分区間vは、各レジスタで重なる先客の費用の和がvの費用の半分以下なら先客を列から外して
  vを置き、先客をヒープへ戻して優先度の順に置き直す（別のレジスタが空いていればそこへ・無ければspill）。1つの部分区間が追い出されるのは1回まで（XEV_N）
  - 追い出せる先客は「運搬値の穴（4.4節）で分割された値の、中に使用の無い部分区間」だけ（定義と境目のコピーだけの素通りの区間）。費用 = 中の触れの重み（定義）+
    隣の部分区間がレジスタ（か未処理）なら境目のコピー1本（xPcCost）。vの費用は、穴の部分区間なら同じ式・ほかは部分区間の重み
  - 動機: フェーズ3'（report-524）の後の1brc mainで、leaの結果（区間2命令・中の使用10万回）がspillに落ち、5本のレジスタを中に使用が0回の素通りの
    部分区間（値の重みを丸ごと持つ — 13節2）が塞いでいた（report-525 3節）。命令: 1brc −1.85%・knucleotide −1.23%・routing −0.09%・jsonapi −0.03%・
    logagg +0.015%（report-526）
  - 棄てた案（report-526）: 中に使用のある先客も追い出す形 — 静的な深さの重みは兄弟の分岐（毎周どれか1つだけ走る）を全部熱く数えるので、分岐に散った使用の
    和と境目1本の比較が実回数と逆になり、ヒントで合体していた辺のコピーのずれも費用の外（knucleotide +2.8%・logagg +0.9%・jsonapi +0.3%。余裕2〜3倍でも
    logagg +0.27〜0.39%）。余裕なし（和 < 費用）— jsonapiのParseで同じ点で定義される2値の僅差の入れ替えが連なり +0.34%。部分区間ごとに覆うブロックだけを
    遅延で走査して中の触れを数える形 — 長い部分区間を何度も舐めて自己buildの判定の仕事 +3.1 G（関数を1回走査する形は +0.28 G）。連鎖の上限N = 2 / 4 —
    12題材のELFも判定の仕事もN = 1と同じ

## 8. ヒント（xHints・xHintEdge・xHintReg・兄弟優先）

優先度順の彩色で「どのレジスタを選ぶか」だけに作用し（彩色の順そのものは変えない）、次の優先順位で空きレジスタを探す（xHintReg）:

1. 同じ値の割り当て済みの部分区間（隣（前後）を先に — 境界のコピーを消すのが目的）、無ければほかの兄弟部分区間
2. 値のヒント（`hP`/`hA1`/`hA2`/`hOp` — 辺の実引数 → 行き先の仮引数、仮引数 → 入りの実引数2本まで、演算の結果 → 左の被演算子）

組（int/xmm）をまたぐヒントは無視する（`xHintLoc` が `xIsXmm` の一致を見る）。ヒントが無い／空きが無ければ、通常どおり空きレジスタの先頭を取る。

予約（1段階目だけ — 区間のタスクのフェーズ1 R1・report-528）: 辺の実引数をレジスタrに置いたとき、行き先の仮引数が運搬値（ループの頭の仮引数）でまだ置かれて
いなければrを予約し、ヒントの無いほかの部分区間は空きの先頭を選ぶときrを後回しにする（xPrioPick — 仮引数の1本目を処理したら解く）。
運搬値の更新値は重く仮引数より先に置かれるので、更新値の側に仮引数のヒントを持たせても効かない（仮引数はまだ配置先が無い）。予約が無いと、穴で縮んだ
別の仮引数が空きの先頭としてそのレジスタを取り、仮引数どうしの配置先が戻り辺で1つずつずれて並行コピーが循環になる（mandelbrotのxmmの φ 4本 —
r11を中継ぎに5回のコピー・cycles +58%）。
- 棄てた案: 予約を合流の仮引数（前向きの辺）にも掛ける形 — mandelbrot・revcomp・fannkuchは得だがknucleotide +1.7%・routing +0.5%・1brc +0.4%（命令）
- 判定の仕事: レジスタを舐める形は自己build +0.24 G — 予約のあるレジスタのビット（free[64]）で畳んで +0.02 G

## 9. 合流の並行コピー（xParallelMove・xEdgeMoves・xSplitMoves）

- 辺の実引数 → 仮引数のコピーは並行コピーとして出す（xParallelMove）: 準備の整ったコピー（書き先を他の生きているコピーが読まない）から
  順に処理し、循環がある場合は1本を `r11` へ退避してから進める（循環の解消）
- optは辺のコピーの位置（コストの数え方）を見ず、「実引数と仮引数が同じ配置先ならコピーは0命令」として扱う（xEdgeMovesが判定し、
  不要な辺を `xFwdTo` で空の中継として飛ばせる）
- 分割された値（部分区間を持つ値）の辺ごとのコピー（xSplitMoves）: 辺の両端（元の終わり・行き先の頭）を覆う部分区間の配置先が違う値だけを足す。
  死んだ値でも、覆う部分区間があれば書き先が外包の中で確保されているのでコピーしてよい
  - 例外 = 行き先の仮引数: 行き先の仮引数の列にある値は、辺の仮引数のコピー自体がその値を書くので外す（外さないと仮引数のコピーと
    二重に書いてしまう — S2で誤コンパイルが起きた実例の一般形。判定は当初「最初の部分区間が行き先の頭で始まる」だったが、S3bで
    「行き先の仮引数の列にあるか」（`xIsParamOf`）に一般化した）
  - 関数の引数の格納場所（呼び手が積んだ番地）へ書くコピーは省く（入口からずっとその値を持っている）
  - 書き先 = 読み出し元のコピー（実質恒等）は `xParallelMove` が出さないので `xEdgeMoves` の判定からも外す（数えるとコピーの無い辺で
    条件分岐の向きが反転する）
  - spill先が既に正しい辺のreg → memのコピー（store）は出さない（第1タスク (d) ③ — xSlotValid）: SSAの値は変わらないので、spill先が
    値を持っていれば書き直しは要らない。分割された値ごとに前向きの「すべてのパスで」の不動点 — 入り(b) = 前任の出の論理積（入口は偽）・出(b) = bの終わりで部分区間に
    覆われ、かつ（spill先にいる ∨（入り(b) ∧ b ≠ 定義のブロック））。結果はxF.svOk（分割された値 × ブロック）。定義のブロックは外包の始まりのブロックで
    代用できない（吐く順で定義より前のブロックが外包に入る — gatesのjson_decodeで捕捉した潜在バグ）。fannkuch命令 −0.38%・cycles −0.8%。
    自己buildのコスト +0.32 G（ratchet 60.7 → 61.0）。これでbce④（13節）の損の主因が消え、bce④ は得に転じた

## 10. spill（1か所原則 — xAllocFrame・xGet/xGetInto/xPut）

- spill先は値ごとに1つ（4.2節）。同じ値の複数の部分区間がspillされても、変位は共有する（最初にspillされた部分区間の順に配る）
- spill先の合流（格納場所の往復レーンのフェーズ4a — opt・xSpillJoin / xJoinSlots）: 辺の実引数と行き先の仮引数がどちらもspill先を持ち、区間が
  重ならないなら、同じ変位を配る（1か所原則は「合流した値の組で1か所」）。辺のコピーが「同じ配置先」になり、9節の0命令の扱いが効く
  （jsonapiのParseの戻りの辺のspill先どうしのコピー — mem → mem）。割り当て（どの値がレジスタに載るか）は変えない
  - 干渉は値の全部の部分区間（レジスタに置いたものも — 分割された値のspill先はxSlotValidの前提でそこでも値を持つ）で見る。部分区間の間の
    穴（運搬値の穴・本体と末尾の領域の間）は値が死んでいるので数えない。外包（最初の始まり〜最後の終わり）で見る初版は、末尾の領域で
    使う値が全部の組を締め出して効きが1/4だった（jsonapi −0.7%対 −3.1%）
  - 重なりの定義はレジスタの共有（xPrioFits）と同じ。辺のコピーが仮引数の配置先へ書く点（前任の終わり）は仮引数の区間の外だが、その辺の上で
    値が要る別の値は行き先の入口で生きていて仮引数と重なるのでグループに入らない（xLiveのoptのコメントと同じ理屈）。グループは16値まで・深いループの辺から併せる
  - 届かない形: 合流のブロックの仮引数が、ループの頭の仮引数（そのコピーを受け取る）と、ループを出るパスで同時に生きている形（値は同じでも区間が
    重なる）。値の等しさを見る合流（copy coalescing）は入れていない
- spillの枠の彩色（F-1のフェーズ1 — xSpillColor・opt・report-1003）: 合流の後、spill先を持つグループ（合流のグループ・グループでない値は1つ）の区間 = グループの全部の値の全部の部分区間（レジスタに置いた分も — xSlotValidの前提）の外包（穴は使わない）で、重ならないグループどうしが同じ枠を使う。重なりの規則はxIvMeet / xPrioFitsと同じ（レジスタの共有と同じ干渉なので、辺のコピーの書き点の論証も合流と同じ）。算法 = 線形走査（始まりの順・同じ位置はグループの番号の順 — 安定なマージ・終わりが始まり以下の枠を空きの列へ戻してから配る・v128は16 Bの別の列）— 決定的。serveTlsConnのspill 21976 → 2816 B・自己buildのフレームの和1.14 → 0.96 MB。コスト = 自己buildの命令 +0.09 G（計算 — 出来たコードは安くなる側）。移植版のバックエンドは今まで通り値ごとに専用（elfeq）。棄てた案: 部分区間の穴まで共有する（xSlotValidの前提を崩す）・位置の桶（関数の位置の数に比例する表 — +0.2 G）
- 定義直後の読み直しの省略（フェーズ4a — opt）: xPutがフレームへstoreした直後（表の位置が動いていない）に同じ値をxGet / xGetIntoで読むなら、
  storeの読み出し元のレジスタをそのまま使う（xGetは読み出し元がscratchと同じときだけ）。ブロックの頭で消す（別の前任から入るパスではレジスタに値が無い）
  - レジスタ版（フェーズA — report-509）: xPutが値をレジスタへコピーした直後（`mov rsi, rax`）に同じ値をコピーの読み出し元へ読むxGetInto（`mov rax, rsi` — 戻り値のraxなど）は省く
- 吐くときのscratchの中身の覚え書き（フェーズBのD1 — report-512・opt）: rax / rcx / rdxが今持つ値（SSAの値 — spill先の変位ではない）を
  xFに覚え、xGetが同じ値をまた同じscratchへ読むなら読み込みを省く（routingのRouteの6ワードのloadごとの基底 `mov rax, [rbp-…]` の読み直し）
  - 白名簿の形: 覚え書きを引き・書くのは白名簿の命令（定数・load / store・番地を出さないgep / slotaddr — xMemoOp）を吐いている間だけ。名簿の外の
    命令の頭とブロックの頭で全部消し、終端の前で止める。名簿の外の吐き方（xDirectBinのrax経由・並行コピーの中継・rtの展開ほか）が
    scratchを書くのを1つずつ追わない — 漏れが誤コンパイルになる
  - 名簿の中でscratchを書く箇所はxGet（xMemoHit — 引いたうえで以後vを持つと記す）と、結果を書いた直後のxPut（xMemoSet）の2つだけ。
    raxを結果の書き先に使うパス（imm64の定数・配置先がgprでないload）はどれも直後にxPut(res, rax) を通る
  - 鍵が値なので、配置先（部分区間）やspill先の共有（xSpillJoin）に依らない。xGetの「scratchへ書くパス」（rematの即値・lea・xmmのmovq・
    spill先のload）は1か所で覚え書きとフェーズ4aのEを引く
  - テスト: ミュータント「ブロックの頭で消さない」「呼び出しの頭で消さない」「xPutで更新しない（= 結果の書き先raxで消さない）」をoptdiff --mutが殺す
  - 棄てた案: 名簿の外の吐き方ごとに書いたレジスタを消す形（箇所が散っていて漏れの危険が大きい — report-508 2.2）。R3（並行コピーのコピーで
    書き先がすでに同じビットを持つなら省く）はこの部品に乗らない — 辺のコピーは名簿の外で、コピーの時点で被演算子のレジスタを知る別の仕組みが要る
    （report-512 / 513 — PINS）
- 吐き方の命令選択（フェーズA — xDirectBin — 割り当ては変えない）: 定数倍は3番地形の `imul d, x, imm`（`mov rcx, imm; imul d, rcx` の即値の読み込みとdへのコピーを省く）。
  右の被演算子が結果のレジスタにある可換の演算（add / mul / and / or / xor）は `op d, 左` で（rax経由の `mov rax, 左; op rax, d; mov d, rax` を省く）。subは今までどおりrax経由
- フレームは `[frameTop)` の下に退避域、その下にspill域。関数の引数（仮引数）がspillされた場合は、呼び手が積んだ
  `[rbp+16+8k]` をそのままspill先にする（storeは不要）
- 区間を持たない値（到達しないブロックでしか定義されない）も番地だけは有効にしておく
- spillした部分区間は、区間内の全使用でload・定義でstoreする（共有の宛先1か所に対するstore/load — 二重化はしない）
- 退避対象は「割り当てに使ったレジスタ」に限らない: スロットのゼロ初期化を使う関数は `rdi` を、syscallを含む関数はその引数レジスタ
  （`rdx` を除く）を、scanbを含まない関数でxmm2〜7も割り当てに使った場合はその分を、それぞれ割り当てとは無関係に退避する

### 10.1 remat（作り直す定数 — M5）

- `e.remat[v] = 1`: 値が `OpConst` のimm32範囲の定数 → 区間もレジスタ/spill先も持たず、使う点ごとに即値を作り直す（`xMoveImm`）
- `e.remat[v] = 2`: 値が `OpSlotaddr`（スロットの番地）→ 使う点で `lea rbp + 変位` を作り直す。1.0× アタックのタスクで、番地がspillされ
  多値の結果のコピーのたびにフレームから番地を読み直していた実例（1BRCのmain）への対策
- 大域の番地（`OpGlobal`）とその `ptoi` / `itop` も `e.remat[v] = 1` の札つき即値（札の種類2 = 後埋めの大域の番地・`constV` = 大域の記録の番号）。
  使う点ごとに `mov r32, imm32`（ゼロ拡張 — 番地は0以上2^31未満なので64 bitの符号拡張の形より2バイト短い）を出し、関数の終わりに後埋めの表へ移す。
  GVNが関数の頭へ合流させた番地（とptoi）が関数の全体に生きて枠へ積まれていた（自己buildのreplayKeyOfでptoiの枠の区間736）。
  ただしループの外で定義し、それより深いループの中で使う番地（xGlobLoop — 融合したgepの被演算子・終端の実引数も使う点に数える）は作り直さず区間に乗せる。
  決めるのは並べた順のブロックの深さ（e.ldep）だけで、割り当ての結果には依らない。
  棄てた案: spillするときだけ作り直す（割り当ての結果に依る条件が増える）。ループの中でも作り直す（命令 −0.7%だがpipelinedのcycles +2.3〜3.0%・分岐の転向 +37%）
  LICMはglobaladdrを巻き上げる（ループの外で定義・区間に乗る側へ寄せる）。棄てた案: 巻き上げずループの中で番地を作る（命令 −0.6%だがpipelinedのcycles +4〜5%）
- `xSrcLoc` が並行コピーの読み出し元として `xRemat + 2*v` のマーク（偶数・`xSpill` より大きい・どの書き先とも重ならない）を返し、
  `xParallelMove` が種類ごとに `lea`/即値の書き込みへ振り分ける

## 11. floatのクラス（xFloatClass）

- floatの演算を1つも持たない関数はxmmのクラスを立てない（早期リターン）。立てないとintのブロック仮引数の循環までxmmに置かれ、
  使うたび `movq` で汎用レジスタへ往復していた（フェーズ6 P4-6で発見）
- 候補は「float 2項演算の結果」「floatの `OpConst`（rematでない）」「floatの `OpLoad`（foldingされていない）」「ブロック仮引数」。
  intの演算・比較・番地計算・分岐条件に使われる値は不動点反復でxmmのクラスから外す（storeの値・呼び出し引数・retは外さない —
  外すとspectral-normが2.7倍遅くなった実例あり）
- この修理の前は、fannkuchの端数の正体が「優先度」ではなく「floatクラス判定の穴」だった（ブロック仮引数がintの比較に使われても
  xmmのまま扱われ、長さと添字の比較のたびに `movq` が入っていた）

## 12. 冷たいパス・熱いパスをまたぐ値の判定（既知の脆さの背景 — xColdChainの構文依存）

`xColdChain` は「条件分岐の片側から、`br` だけの単一入口・単一出口のブロックの列を辿って起点に届くか」で冷たさを判定する。起点に届く前に1つでも
条件分岐（`condbr`）があると、そこで列が切れて手前は熱いまま扱われる。この判定は構文的（列の形）であって意味論的（必ず遅いパスを通るか）
ではないため、呼び出しがブロック1つ分動くだけで冷たいマークが広範囲に消える・現れることがある（14節参照）。

## 13. 既知の弱点（2026-10時点）

最適割り当てオラクル（最小費用流による厳密解L1との比較）のタスクで特定された、現在の設計の限界。どれも「直す」ではなく「現状の記録」として
挙げる — 直す候補はに材料として並んでいるだけで、決定済みではない。

1. 冷たい領域の判定が構文に依存する（12節）: `xColdChain` の「`br` だけの単一入口・単一出口のブロックの列」という条件は、冷たいパスの途中に
   分岐が1つ入るだけで列が切れ、その手前のブロック群が丸ごと熱い扱いに戻る。mapfuseのタスク（コミット5678b37f）で、`region_relocate8`
   の呼び出し位置が1ブロック動いただけで13ブロックの冷たいマークが消え、熱いループの一時値6本がspillに回った（knuc cycles
   −14.3%・命令 −30.6%の得と引き換えに、1brcが割り当ての非単調で +6.5%退行）
2. 部分区間の重み = 値の重みのまま（穴・分割のどちらでも）: 運搬値の穴（4.4節）や2段階目の分割（5節）で作られる部分区間は、
   重みを「その部分区間の中の定義・使用」で数え直さず、値全体の重み（真ん中は例外で0）を引き継ぐ。冷たい領域が構文判定で見誤られると
   （上記1）、この重みがそのまま誤って熱い値に波及する。ただし中の重みへ直す形は今の貪欲の下では逆効果（4.4節の注記・下の4）
3. 優先度順の貪欲彩色に追い出しが無い（7節 — 2026-10のフェーズ2で「穴の素通りの部分区間」だけは追い出せるようにした。一般の追い出しは静的な重みの下では逆効果）: 一度置いた区間は、後から来たどれだけ重い区間にも明け渡さない。最小費用流オラクル
   （L1）との比較では、1BRCのmainでgreedyが既に32.5%（hd版）、mapfuse後は58.2%（mf版）のギャップを持つ。最適解は長い
   区間（熱いブロックを丸ごと跨ぐが使用の疎な値）をspillにして短い熱い一時値をレジスタに残すが、greedyは重みの降順で先に長い
   区間を置いてしまい、短い一時値を締め出す。冷たい領域の誤判定（弱点1）は引き金に過ぎず、増幅しているのはこの順序の脆さ
  
4. 合流の継ぎ目のコピー（辺の並行コピー）はコスト・優先度のモデルに入っていない: ヒント（8節）は彩色の「色の選び方」だけに効き、
   割り当ての優先順位（7節の重み順）自体はコピーの本数を見ない。最小費用流オラクル（L1）も同じ理由でこの費用を見ておらず
   greedyとL1のギャップは「コピーの増減」を含まない下界にとどまる。
   境目の費用まで入れたL2（ウィンドウごとのブロック単位reg / mem・定義でのstore・ラグランジュ緩和 + 値ごとのmin-cut + 分枝限定）の証明つき最適との
   差は1brcのmainで −11.8%・fannkuchで −6%（回収の見込み）。第1タスク (d) で出口の冗長なstoreは消した（9節 — ③）が、取るかどうかの判定に境目の費用を
   入れる形（②）は9題材で無効果、部分区間ごとの重み（①）は逆効果だった（4.4節の注記）。教訓: 正直な費用モデルは、選び方がL2型（境目を挟む部分区間を
   結合して解く）でないと逆効果になる — 貪欲の順序が費用モデルの歪みを前提に釣り合っている
   - 第1タスクの後の再測定（同じウィンドウ・配置先は第1タスクの前と同一）: fannkuchのmain k66〜121でgreedyの配置先のコピーの費用が
     579 → 507（③ のコピー — 理想のコピーと一致。コピーのギャップ72は全部詰まった）。1brcのmain k13〜66・k35〜44は元からコピーのギャップ0（741 / 280）。
     残る差は配置先の選び方: fannkuch 507対L2の証明つき最適90・1brc k13〜66 741対165・k35〜44 280対42 — 第2タスク（選び方）の領分
5. 重みは命令数のモデルで、cyclesの代理にはならない: fannkuchのように分岐予測ミス律速の題材では、割り当ての重みの差が
   そのままcyclesに化けるとは限らない。レーンの各タスクはこの前提で「命令数 + 熱いコードの同一性」を
   判定の指標にしており、cyclesは配置（アラインメント・関数の先頭位置）で ±3〜4%揺れる参考値にとどめている
6. 境界検査の消去（bce④）で起きた非単調の正体は「境目の型」: `a[i] = a[i + 1]` の2本目の検査を消すと検査の命令は0.22 G減るのに、
   消えた比較の区間が無くなったことでgreedyの順序が動き、運搬値v46の3本目の部分区間がr10を取って入口のload・出口のstoreがループの頻度で入った
   （fannkuchが差し引き損）。最小費用流（L1）・L2の最適の側は単調（検査を消して悪くなることは無い）— 非単調はgreedyの費用モデルの産物と証明された。
   ③で出口のstoreが消えた木ではbce④ はfannkuch −0.19%（差し引き得）で採用した
7. 計測の注意: 1brcのinstructions:uはASLRで二峰（同じELFで −0.45%の下の峰がときどき出る）。命令の比較は `setarch -R` で数える
